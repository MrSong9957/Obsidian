# 验收歧义与判定口径（规格澄清后更新）

本文件记录 `frozen/spec.md` 与 `frozen/run-constraints.md` 中未定、冲突或需要验收方选择口径的地方；**不修改规格，也不代表实现方可以自行选择外部行为**。脚本对每项的实际处理写在下文，最终验收报告必须引用这些口径。

2026-10-24 规格作者对 A1/A3/A4 作出澄清后，下列对应条目已按澄清后的 `frozen/spec.md` 更新；A14 的 1 MiB 边界也按现行措辞确认。其余条目保留原判定。

行号均指 `frozen/spec.md`（2026-10-24 版）。

## A1. 含原始空格的 URL：1.1 与 1.3 的冲突（已解决）

- L21（澄清后）：`url` 只禁止 ASCII 控制字符（0x00–0x1F、0x7F）以及 scheme 和主机名中的空格；路径、查询、片段中的普通空格合法，必须按第 1.3 节编码。
- L55–56：`Location` 编码规则要求空格按 UTF-8 百分号编码，示例输入 `https://example.com/路径?x=中 文#片段` 含一个原始空格，并给出必须得到的 `%20` 结果。
- L77（第 2 节）：把“scheme/host 带空格、含控制字符的 URL”列为非法输入，并明确“路径里的普通空格是合法的，要编码”。
- 规格作者已明确：旧版“URL 不能含 ASCII 空白”的表述不再适用，路径/查询/片段中的普通空格必须接受并编码。

脚本处理：`ENC-04` 对两个 URL 都严格要求 `201`、随后 `302`，且原始 `Location` 精确匹配；不再接受 `400 invalid_url`：

1. 第 1.3 节示例：`https://example.com/路径?x=中 文#片段` →
   `https://example.com/%E8%B7%AF%E5%BE%84?x=%E4%B8%AD%20%E6%96%87#%E7%89%87%E6%AE%B5`；
2. 普通空格 URL：`https://example.com/a b?c=d e#f g` →
   `https://example.com/a%20b?c=d%20e#f%20g`。

`VALID-05` 用 `ht tp://example.com/x`、`https://exa mple.com/x`、`https:// example.com/x`、`https://example.com /x` 等测试 scheme/host 空格；`VALID-07` 测试 0x00、0x1F、0x7F 及 tab/LF/CR 等控制字符。路径空格合法由 `ENC-04` 覆盖。其他状态、或接受后 `Location` 不正确，均判失败。

## A2. 缺少 `url` 字段的错误码

L29 只规定“字段类型不对”用 `invalid_request`，L30 规定 URL 不符合规则用 `invalid_url`；`url` 缺失属于哪一种未定义。脚本接受 `400` 且 `error` 为 `invalid_request` 或 `invalid_url`，并在 `VALID-04` 中记录。

## A3. 超过 1 MiB 请求体（已固定）

现行 L19 明确：请求体最多 1 MiB；超过 1 MiB 返回 `400 {"error":"invalid_request"}`，不能崩溃。脚本 `VALID-14` 严格要求 `400` 且错误体精确为 `{"error":"invalid_request"}`；其他 4xx、连接关闭、超时、崩溃均判失败。该错误响应也纳入 `VALID-13` 的单字段错误体检查。`VALID-15` 随后确认服务仍能响应统计请求。恰好 1 MiB 的请求体由 `CREATE-13` 要求接受。

## A4. SIGTERM 退出时限（已固定）

现行 L11 明确“收到 SIGTERM 后 5 秒内退出”。脚本实测从发送 SIGTERM 到进程退出并释放监听端口的时间，要求 **≤ 5.0 s**；实际值写入证据，同时检查端口已关闭。5 秒边界按包含上界理解；无法区分恰好 5.000 s 附近的调度误差时，以实测值和原始日志为准。

## A5. “只有一个进程”的口径

L11：被测服务只允许一个进程。若启动命令是 `sh -c './server'` 且 shell `exec`，只有一个进程；若启动命令保留包装 shell/启动脚本，则存在多个进程。

脚本以“持有监听 socket 的进程及其后代”为服务进程树（`/proc/net/tcp{,6}` 的 LISTEN inode → `/proc/*/fd`），要求进程树内非僵尸进程数为 1；包装脚本若在服务进程树外，不计入服务内存，但也不作为服务进程。若实现用多进程共享监听端口，会检测到多个 listener/进程并判失败。启动命令应尽量直接执行二进制。

## A6. 数据库文件/父目录的创建时机

L10 要求“DB 文件不存在时自动创建，父目录不存在时也创建”，未说是在启动时还是首次写入时。脚本在首次成功创建链接之后检查父目录与 DB 文件是否存在（`START-03`、`START-04`），避免把“延迟到首次写入”误判为失败。

## A7. 成功响应 `Content-Type` 的参数细节

L13 规定 `application/json; charset=utf-8`。脚本比较时忽略 `;`、`=` 周围空白和 charset 的大小写，但要求媒体类型为 `application/json` 且带 `charset=utf-8`；其他 charset（如 `iso-8859-1`）没有测试，规格也未说明。

## A8. URL scheme 大小写

L21 字面只接受 `http://` / `https://`。`HTTP://`、`Https://` 是否接受未定义；脚本不测试，避免把 RFC 语义强加给规格。

## A9. “必须有主机名”的判定范围

L21 未定义 hostname 的语法边界（`localhost`、IPv4/IPv6 字面量、端口、userinfo、单标签主机等）。脚本只测试明确无主机的 `http://`、`https://`、`https:///path`、`http://?x=1`，以及普通主机名。

## A10. “正好到期”边界无法用纯 API 精确构造

L34：`expires_at <= 当前时间` 即过期，L42 又说正好到期算过期。用 1 秒 TTL 时，创建/请求时刻的亚秒偏差无法控制；直接改数据库被 L74 禁止。

服务端时间按 Unix 秒向下取整。脚本等到 `expires_at + 0.35 s` 再断言 `410` / `expired=true`；此时仍在 `expires_at` 这一秒内，正常情况下服务端 `now == expires_at`，因此实际检查的是规格要求的 `<=` 而不是 `<`。但调度/请求延迟可能让服务端落到下一秒，无法像直接改库那样精确锁死边界，所以只把“已过期”一侧的结论写入报告。TTL=1 的创建可能因跨秒导致剩余时间不足，脚本最多重试 5 次以取得剩余 ≥0.4 s 的样本，TTL 参数不变。

## A11. 错误响应的 `Content-Type`

L13 只规定“成功响应”的 `Content-Type`；L28–32 只规定错误体字段。脚本不检查 4xx/5xx 的 `Content-Type`。

## A12. 路由的方法与尾斜杠

规格只定义 `POST /api/links`、`GET /api/links/<code>`、`GET /<code>`；`POST /<code>`、`GET /api/links`、`GET /api/links/`、`HEAD`、`OPTIONS`、`405` 均未定义。脚本不测试。

## A13. 保留别名的大小写

L22 写保留别名是 `api`、`health`，同时别名区分大小写。`API`、`Health` 是否也保留未定义；脚本只测试小写 `api` / `health`。

## A14. 1 MiB 的边界含义（已明确）

现行 L19 的“最多 1 MiB；超过 1 MiB 返回 `400 {"error":"invalid_request"}`”按包含上界理解：脚本要求恰好 1,048,576 字节的 JSON 请求体被接受（`CREATE-13`），1,048,577 字节以上返回 `400 invalid_request`（`VALID-14`）。

## A15. p95 的取整与三轮回中位数的顺序

运行约束固定 `p95 = sorted[ceil(0.95*n)-1]`，单位 ms，保留两位。脚本先把每轮 p95 四舍五入到两位，再取三轮中位数，并按两位比较阈值；先取中位数再四舍五入的差异不超过 0.005 ms，未单独处理。

## A16. 内存计量口径

L66 说读“服务进程”的 `VmHWM`，上限 10240 KiB；L11 禁止多进程规避。脚本对监听进程树内所有非僵尸进程的 `VmHWM` 求和并检查 ≤10240 KiB，同时要求进程数为 1；单进程时两者等价。包装脚本若在树外不计入。

## A17. 重启后 `short_url` 的端口

重启时脚本仍用 `PORT=0`，系统可能分配新端口；规格只要求创建时的 `short_url` 使用当时实际端口，未要求重启后保持旧端口。脚本不比较重启前后的 `short_url`，只比较 `code`、`url`、`clicks`、`created_at`、`expires_at`。

## A18. `alias` 的“字符”与字节

L22 写“4–32 个字符”，字符集限定 ASCII，因此字符数等于字节数；多字节别名因字符集不合法被拒绝，没有单独歧义。

## A19. 多个字段同时非法时的错误优先级

例如 URL 和 alias 同时非法、JSON 合法但字段类型错误且 alias 也非法，规格没有规定先返回哪个 `error`。脚本每次只制造一个非法点，避免依赖优先级。

## A20. 预热请求的并发方式未规定

运行约束只写“先预热 50 次”/“先预热 20 次”，未说预热是否并发。脚本采用单连接串行预热；只有 3 轮正式测量按固定的 50 客户端并发。若要求预热也必须 50 并发，需由规格作者补充。

## A21. 1000 条预置的创建并发未规定

运行约束只规定短码、URL 和“压测前先创建”，未规定串行或并发。脚本用 20 个并发客户端创建 1000 条；这不影响后续固定的 50 并发跳转/创建测量参数。

## A22. HTTP/1.1 keep-alive 的验证范围

规格要求支持 keep-alive，未要求 HTTP pipelining。脚本在同一连接上顺序发送两次请求，验证第二次仍得到完整响应；不测试流水线并发请求。

## A23. SQLite 文件格式检查

L11 要求使用 SQLite。脚本在首次成功创建后读取 `DB_PATH` 前 16 字节，要求为 `SQLite format 3\0`（`START-07`）。这是只读检查，不修改数据库；若实现使用 SQLite 但文件尚未落盘，可能受 A6 的创建时机影响。

## A24. 超时与固定参数的边界

- 启动行等待默认 30 s（`--startup-timeout` 可调，但不影响任何性能阈值）。
- 单次 HTTP 请求超时 15 s（压测连接 20 s），仅用于避免挂死；不是性能判定。
- 跳转 p95 / 创建 p95 / VmHWM 的阈值、并发数、轮次、预热数完全固定在 `acc_perf.py` 顶部，没有命令行覆盖项，测试后不得调整。

## A25. 未规定的其他边界

以下未定义，脚本不测试，也不应作为验收失败理由：

- JSON 对象重复键、JSON 之后有多余字节、BOM。
- Unicode 归一化（NFC/NFD）后的 URL 是否视为同一 URL。
- 对已过期链接并发跳转时的点击数（只要求“不能再增加”）。
- 404/410/409 响应是否必须带 `Content-Type`。
- 服务器是否允许 `Connection: close`（keep-alive 测试只要求同一连接能连续两次请求）。
- 端口/主机名的 IPv6、userinfo、默认端口写法。

## A26. `PORT=0` 的“系统分配”如何核验

L10 只要求 `PORT=0` 时由系统分配端口，没有规定端口范围。脚本设置 `PORT=0`，解析启动行后检查端口落在 `/proc/sys/net/ipv4/ip_local_port_range`（本环境为 32768–60999）内（`START-01`），并实际连接该端口（`START-02`）。这能排除“忽略 `PORT=0`、绑定常规固定端口”的实现；若实现手工选了范围内的固定端口，仅靠单实例无法区分。脚本没有并发启动第二个实例做端口冲突测试；`/proc` 范围不可读时该子检查放行并在证据中记录 `kernel_range=null`。

## A27. 启动行“立即刷新”的时限

L10 要求启动成功后立即打印并刷新启动行，但没有数值上限。脚本在 `--startup-timeout`（默认 30 s，可调）内从 stdout 读取并 fullmatch；能在进程仍运行时读到该行，即证明它没有等到进程退出才刷新；`START-06` 记录实际耗时。没有另设更严格的“立即”阈值；超时则启动失败，其余检查全部显式记为 NOT EXECUTED。
