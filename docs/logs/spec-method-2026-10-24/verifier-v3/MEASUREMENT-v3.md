# MEASUREMENT-v3：验收脚本 v3 测量口径说明

- 版本：**验收脚本 v3 / 实验新版本**（verifier-v3，2026-10-24 第三轮）
- 谱系：**v2（verifier/，冻结）→ rev（verifier-rev/，v2 + 取样器修复 REV-1）→ v3（本目录）**
- 本目录 = `verifier-rev/` 8 文件的全套副本，唯一替换：`acc_perf.py` 的压测客户端实现。
  其余 7 文件与 rev 逐字节一致（见 `SCRIPT-SHA256-v3.txt`；rev 仅改过 `acc_functional.py` 的
  TTL 取样对齐，v3 原样继承）。

## 与 v2/rev 口径的差异（仅此一项）

**压测客户端的并发载体**：每轮的 50 个并发客户端由"单 Python 进程内 50 个线程"改为
"50 个独立单线程进程（multiprocessing，fork 上下文）"。

不变的部分：

- 负载形态：跳转 50 客户端 × 每轮 500（每客户端 10）、预热 50、3 轮；创建 50 × 每轮 100
  （每客户端 2）、预热 20、3 轮、每轮不同 URL；轮起点 barrier 同步。
- 连接与计时：每客户端一条持久连接，`connect()` 在 barrier 前完成（TCP 建连不计入）；
  计时起止 = `time.perf_counter()` 包住请求写入 → 响应读完（客户端观测往返），与 v2 完全一致。
- 预热形态：单连接串行（A20），逐字节未动；预置 1000 条仍用 20 线程（A21 fixture，不参与计时）。
- p95 口径：`sorted[ceil(0.95*n)-1]`（acc_core 冻结实现）、每轮两位舍入、三轮取中位；阈值
  10.00/15.00ms；VmHWM ≤10240 KiB 口径——全部未动。
- 全部 81 项检查计划与业务断言未动。

随之的一个行为差异（已在校准计划 0.2/I6 预先声明）：**错误请求不再进入延迟样本**
（v2 中错误请求的延迟同时计入样本并单独记错）。任一错误仍独立导致 PERF-02/PERF-04
失败，判定语义不变。

## 为什么换客户端（依据）

verifier-diag（第二轮任务 D）：50 Python 线程客户端对最小 302 回显服务器的跳转 p95 中位
= 15.88/14.94 ms——客户端机制自身开销已达/超过阈值，PERF-03 在该口径下对任何服务端不可达。

本轮校准（`../verifier-calib/`，计划 SHA-256 `36cbd365…` 定稿后未改）：

- 压测代码验证 3 组（p95 公式/舍入、sleep 5ms 计时、按比例 500/断连的错误计数与取样）全部通过后才开始测量；
- 2×2 矩阵（线程/进程客户端 × C 最小回显/被测产物，跳转+创建，每格 3 次完整冻结协议）：
  - 线程×回显 跳转 p95 中位 15.20 ms（复现 diag 基线，且换独立 C 回显后不变 ⇒ 下限来自客户端机制）；
  - **进程×回显 跳转 p95 中位 1.42 ms（三次重复 1.41/1.42/1.45，极差 2.8%）**；
  - 进程×产物 跳转 2.77 ms、创建 2.76 ms（对回显有区分度）；线程×产物 17.24/17.29 ms（无区分度）；
- 预写采纳判据"替代客户端回显跳转 p95 中位 ≤5.00ms 且稳定（极差 ≤ 均值 30%）"**满足** ⇒ 采纳，
  生成 v3 并执行一次完整验收。

## 结果边界（重要）

- **原 v2 冻结口径的验收结果保持"未通过"不变**（首轮 75/81、二轮 79/81，仅 PERF-03/05 失败）；
  v3 的结果是新口径下的独立成绩，不与 v2/rev 成绩拼接或互相覆盖。
- v3 依据的规格契约（`frozen/spec.md` §1.4、`frozen/run-constraints.md` 测量参数）未做任何修改；
  变化的只是契约未规定的一项实现选择（并发载体，校准计划 0.2/I1）。
- v3 定位为"验收脚本 v3 / 实验新版本"：其 PERF-03/05 通过与否是 v3 口径下的判定，供规格作者/
  编排方裁决测量口径时对照使用。
