# s10 - Team Protocols：结构化的团队握手协议

> 源码：`agents/s10_team_protocols.py`
> 核心洞察：**同一个 request_id 关联模式，用在两个不同的领域**。

## 问题：团队通信需要协议，不能只发文本

s09 实现了队友之间可以发消息，但只是纯文本。问题是：

- 队长想关闭某个队友，怎么确保对方真的关了？
- 队友想做一个大改动，怎么先请示队长获批？

这需要**请求-响应**模式。s10 用同一个设计模式解决了这两个问题。

比喻：这就像异步 HTTP 请求。你发一个请求出去（带一个唯一 ID），对方处理完后用同一个 ID 回复你。你靠这个 ID 把请求和响应关联起来。

## 1. Request Trackers：用字典追踪请求状态

```python
# 两个字典，分别追踪两种请求
shutdown_requests = {}    # {request_id: {"target": name, "status": "pending"}}
plan_requests = {}        # {request_id: {"from": name, "plan": "...", "status": "pending"}}

# 线程锁保护字典操作（多线程同时访问）
_tracker_lock = threading.Lock()
```

每种请求都有三种状态：`pending` -> `approved` / `rejected`。

这就是一个简单的**有限状态机（FSM）**。

## 2. Shutdown 协议：优雅关闭

### 流程图

```
Lead (队长)                          Teammate (队友)
+---------------------+              +---------------------+
| shutdown_request     |   ------->   | 收到请求            |
| {request_id: "a1b2"} |              | 决定：同意还是拒绝？ |
+---------------------+              +---------------------+
                                              |
+---------------------+              +-------v-------------+
| 检查 tracker        |   <-------   | shutdown_response    |
| status="approved"   |              | {request_id: "a1b2"} |
+---------------------+              +---------------------+
        |
        v
  队友线程停止
```

### Lead 端：发起关闭请求

```python
def handle_shutdown_request(teammate: str) -> str:
    req_id = str(uuid.uuid4())[:8]          # 生成 8 位唯一 ID
    with _tracker_lock:
        shutdown_requests[req_id] = {"target": teammate, "status": "pending"}
    BUS.send(
        "lead", teammate,                   # 从 lead 发给 teammate
        "Please shut down gracefully.",
        "shutdown_request",                 # 消息类型
        {"request_id": req_id},             # 附带 request_id
    )
    return f"Shutdown request {req_id} sent to '{teammate}'"
```

要点：
- `uuid.uuid4()[:8]` 生成短 ID，足够唯一
- 先在 tracker 中注册（status="pending"），再发消息
- 消息类型 `"shutdown_request"`，附带 `request_id`

### Teammate 端：响应关闭请求

```python
# 在 _exec() 中处理 shutdown_response 工具
if tool_name == "shutdown_response":
    req_id = args["request_id"]
    approve = args["approve"]
    with _tracker_lock:
        if req_id in shutdown_requests:
            shutdown_requests[req_id]["status"] = "approved" if approve else "rejected"
    BUS.send(
        sender, "lead", args.get("reason", ""),
        "shutdown_response",
        {"request_id": req_id, "approve": approve},
    )
```

要点：
- 队友收到请求后，LLM 自主决定同意还是拒绝
- 更新 tracker 状态，然后发回响应消息

### Teammate 端：批准关闭后的行为

```python
# 在 _teammate_loop 中
if block.name == "shutdown_response" and block.input.get("approve"):
    should_exit = True      # 标记退出

# 循环结束后
member["status"] = "shutdown" if should_exit else "idle"
```

## 3. Plan Approval 协议：先请示再动手

方向和 Shutdown **反过来了** -- 是队友主动发起，队长审批。

### 流程图

```
Teammate (队友)                      Lead (队长)
+---------------------+              +---------------------+
| plan_approval        |   ------->  | 收到计划文本         |
| {plan: "重构认证模块"} |              | 审阅：批准还是拒绝？ |
+---------------------+              +---------------------+
                                              |
+---------------------+              +-------v-------------+
| 收到审批结果         |   <-------  | plan_approval        |
| 按结果行动           |              | {approve: true}      |
+---------------------+              +---------------------+
```

### Teammate 端：提交计划

```python
if tool_name == "plan_approval":
    plan_text = args.get("plan", "")
    req_id = str(uuid.uuid4())[:8]          # 生成唯一 ID
    with _tracker_lock:
        plan_requests[req_id] = {"from": sender, "plan": plan_text, "status": "pending"}
    BUS.send(
        sender, "lead", plan_text,
        "plan_approval_response",            # 注意：发给 lead 的 inbox
        {"request_id": req_id, "plan": plan_text},
    )
    return f"Plan submitted (request_id={req_id}). Waiting for lead approval."
```

### Lead 端：审批计划

```python
def handle_plan_review(request_id: str, approve: bool, feedback: str = "") -> str:
    with _tracker_lock:
        req = plan_requests.get(request_id)
    if not req:
        return f"Error: Unknown plan request_id '{request_id}'"
    with _tracker_lock:
        req["status"] = "approved" if approve else "rejected"
    BUS.send(
        "lead", req["from"], feedback,
        "plan_approval_response",
        {"request_id": request_id, "approve": approve, "feedback": feedback},
    )
```

## 对比两个协议

| 维度 | Shutdown 协议 | Plan Approval 协议 |
|------|-------------|-------------------|
| 发起方 | Lead（队长） | Teammate（队友） |
| 响应方 | Teammate | Lead |
| 请求 tracker | `shutdown_requests` | `plan_requests` |
| 消息流向 | Lead -> Teammate -> Lead | Teammate -> Lead -> Teammate |
| 关联方式 | request_id | request_id |

**本质上是同一个模式**，只是发起方向相反。

## 关键设计总结

1. **request_id 关联**：每个请求生成唯一 ID，响应必须带上同一个 ID，这就是异步系统里经典的 correlation ID 模式
2. **tracker 字典**：内存中的状态追踪，用线程锁保护并发访问
3. **方向对称**：关闭是自上而下（lead -> teammate），审批是自下而上（teammate -> lead），但代码结构完全一样
4. **LLM 做决策**：不管是同意关闭还是批准计划，都是 LLM 自主判断，不是硬编码逻辑
5. **状态机模式**：`pending -> approved/rejected`，简洁而确定
