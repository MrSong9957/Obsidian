# 开发实践（完整版）

> 本文档包含 TDD、调试案例、代码讲解策略、提示词技巧的完整内容。

## TDD 默认实践

默认使用 TDD（测试驱动开发）。安全相关函数和工具函数，实现前先写边界 case 并验证。

**Why:** safe_path 函数定义了 PROJECT_ROOT 却没使用，也没有边界检查（`is_relative_to`），写完后只测了正常路径没测越界路径，导致 `../../etc/passwd` 可以畅通无阻。直到用户对照教程指出才修复。

**How to apply:**
- 安全函数（路径校验、权限检查、输入过滤）：第一个测试就是"必须被拦住的那个 case"
- 工具函数：先写 `pytest` 测试覆盖正常/边界/错误三路，再写实现
- 有参考代码时，逐行对齐关键步骤，不是"差不多"就行

## 三段式可观测性

修复 BUG 时，优先用 before/after/failed 三段式事件日志建立可观测性，再定位问题。

**Why:** 用户从 s12 的 EventBus 获得启发——append-only JSONL 在关键操作前后及失败时各留一条记录，能完整回溯"发生了什么"，是最轻量但最有效的调试手段。

**How to apply:**
- 修 BUG 前，先确认目标代码有没有 before/after/failed 日志点；没有就先加
- 日志格式：每行一个 JSON，包含 event 名、时间戳、关键上下文（参数、状态）
- 用 before/after 确认操作是否完成，用 failed 捕获异常现场
- 不需要复杂框架，一个 JSONL 文件 + append 就够

## Karpathy 拼贴工作流

> 来源：Andrej Karpathy（OpenAI/Tesla AI 负责人）分享的 AI 辅助编程工作流。

Karpathy 将不同 AI 工具的优缺点"拼接"起来，形成一套混合工作流：

### 1. 75% 靠 Tab 补全（如 Cursor）

他认为在代码的正确位置写几行具体的片段或注释，是向 AI 传达任务规范信息量最高、最快的方式，比用纯大段提示词（Prompt）去聊天效率高得多。

**本质：** Tab 补全是"局部精确指导"——你在代码上下文中给 AI 一个精准的起点，它在你控制的方向上自动补全。而 Prompt 聊天是"全局模糊描述"——你用自然语言描述意图，AI 需要猜测你指的是哪段代码、哪个函数、哪个位置。

### 2. 局部重构

选中某段大模型写得太臃肿的 Rust 代码，定向命令它："把这段代码改写得更优雅、更精简"。

**本质：** 不是让 AI 从头重写，而是在已有代码的基础上做局部优化。你提供上下文（选中的代码），AI 在约束范围内改进。

### 3. 高阶复杂逻辑留给顶级模型

当遇到特别烧脑的 Rust 逻辑硬骨头，Agent 搞不定时，他才会把问题剥离出来，丢给最顶级的黑盒模型（如 GPT-4o 或更高级的推理模型）去单点突破。

**本质：** 任务分级——简单任务用快速工具（Tab 补全），复杂任务用强力模型。不是所有问题都值得用最强模型，也不是所有问题都能用最快工具解决。

### 核心认知

拼贴工作流的本质是**工具分级 + 任务匹配**：

| 任务类型 | 工具 | 效率 |
|---------|------|------|
| 写新代码片段 | Tab 补全（Cursor） | 最高 |
| 局部优化/重构 | 选中 + 定向命令 | 高 |
| 复杂逻辑/架构 | 顶级推理模型 | 慢但可靠 |

## 调试教训

### 2026-03-21: 菜单返回 Bug

#### 问题
按 Ctrl+P 打开菜单后，按 Enter 无法返回，程序"卡死"。

#### 根因
`key.name === "enter"` 在某些系统上不匹配，因为 Enter 键被报告为 `"return"`。

#### 错误的调试过程
- 猜测是 stdin/raw mode/listener 问题
- 尝试了 10+ 次修复都不相关
- 花费数小时

#### 正确的调试方法
1. 添加日志：`console.log('key.name=', key.name)`
2. 观察：看到 `"return"` 而非 `"enter"`
3. 修复：`key.name === "enter" || key.name === "return"`
4. 耗时：5 分钟

#### 教训
**永远先观察，再假设。**
- 打印实际值，不要猜测
- 创建最小诊断脚本
- Phase 1 (观察) 比 Phase 4 (修复) 更重要

#### 通用规则
```
遇到任何 Bug:
1. 第一件事：加日志，打印相关变量
2. 运行，观察输出
3. 对比期望 vs 实际
4. 只修差异点
```

### 2026-04-12: UTF-8 Surrogate 编码错误

#### 问题

终端 `input()` 输入时，多次退格删除了提示符 "你>"，执行命令报错：

```
[error] 错误: 'utf-8' codec can't encode character '\udce4' in position 68: surrogates not allowed
```

#### 根因

两层问题叠加：

1. **`input()` 逐字节退格**："你" 是 UTF-8 三字节 `\xE4\xBD\xA0`，终端按字节退格残留孤立字节 `\xE4`，被 Python IO 层映射为 surrogate `\udce4`
2. **Surrogate 无法 UTF-8 编码**：Anthropic SDK 内部 `json.dumps()` → `.encode('utf-8')` 时，surrogate（U+D800–U+DFFF）是 UTF-16 专用，不在合法 UTF-8 中

#### 错误的调试过程

- 误判为 `read_file` 读到了含 surrogate 的文件内容
- 花时间分析 `errors="replace"` 的行为，实际上它不会产生 surrogate
- 用户补充了"按退格删除了提示符"这个关键信息后才定位到真正根因

#### 修复

| 层 | 修复 | 作用 |
|----|------|------|
| 显示层 | `input()` → `prompt_toolkit.prompt()` | 按字符退格，不会拆散多字节字符 |
| 传输层 | `_sanitize_text()` 清理 surrogate | encode 失败时替换为 `?`，快速路径零开销 |

#### 教训

**先确认操作上下文，再假设代码 bug。**
- 用户描述了"按退格删除了提示符"——这是最关键的线索，但一开始被忽略了
- 编码问题的来源不只是文件内容，终端交互、子进程输出、文件系统路径都可能引入不可编码字符
- `prompt_toolkit` 是 Python TUI 的标准选择，应该从 Phase 1 就使用而非 `input()`

## 代码讲解与分析策略

### 重心：底层逻辑优先

不逐行翻译语法、不给阅读顺序指南。结合少量源码，重点回答"这个机制解决什么问题"、"为什么这样设计"。

**Why:** AI 时代，代码的编写和解释都可以由 AI 完成，人类的核心价值在于理解底层逻辑和做出设计决策。

### 遇新概念时：零基础教学

先讲整体（输入输出）再找核心逻辑，只在卡住处深挖。用生活比喻带出术语。短而朴素优于长篇大论。让用户复述验证理解。

### 分析代码时：从问题出发拆解

1. 先问"这份代码解决了什么问题"
2. 把大问题拆成 2-4 个子问题
3. 每个子问题找到对应的代码区域，解释"问题 → 方案 → 实现"的因果链
4. 最后用一次完整流程串起所有子问题，展示协作关系

**Why:** 用户要的是对设计意图和解决方案的理解，不是文件导览。

### 宏观结论

掌握底层逻辑 + Claude Code 辅助 = 不局限于某一种编程语言，可覆盖全部编程语言。

模型：想清楚逻辑 → AI 写代码 → 和 AI 一起审查 → 和 AI 一起读代码（螺旋迭代）

### 2026-04-13: 讲解要从最直白的那句话开始

#### 问题

讲解"函数能存进字典"这个概念时，从闭包、装饰器语法糖、分发表一路展开，越讲越抽象。用户反复追问后说："那你为什么不早这么说解释？说一大堆抽象概念，越听越糊涂。"实际上用户只需要一句话：**函数不加括号是存着，加括号是执行。**

#### 根因

习惯从"完整的知识体系"出发讲解（闭包 → 装饰器 → 分发），而不是从"用户当下卡在哪一个问题"出发。用户问的是"函数怎么能当值"，答案就应该是"函数跟字符串一样是值"，不需要引出闭包和装饰器的背景。

#### 教训

1. **先给最直白的那句话，再按需展开。** 不要铺垫概念体系，直接回答眼前的问题。
2. **一个概念用一句话能说清，就不要用三段。** 精炼不是省略，是找到最准的那个角度。
3. **用户反复追问同一件事 = 我的解释偏了。** 及时换个说法，而不是用更多概念解释概念。

## KV 缓存提示词设计原则

### KV缓存优化原则

KV缓存是Transformer推理的核心优化机制，虽源自模型注意力计算，但其存储、复用与调度由推理引擎管控，并非模型内部完全封闭的逻辑。提示词等前缀内容越稳定、改动越少，token序列一致性越高，KV缓存命中率就越高，推理速度也越快。

**Why:** 在 mi-code 项目中，工具定义和系统提示词会作为每次 API 请求的前缀发送。如果这些前缀频繁变动，推理引擎无法复用 KV 缓存，每次请求都要重新计算前缀部分的注意力，显著增加延迟和 token 成本。

**How to apply:** 在设置工具提示词和系统提示词时：
- 固定的、不变的内容放在前缀最前面（如工具定义、角色描述、常量规则）
- 动态的、会变化的内容放在后面（如当前对话上下文、用户输入、临时指令）
- 避免在固定前缀中插入会随对话变化的内容（如时间戳、计数器）
- 工具描述文本稳定后不要随意修改措辞，改动会导致缓存失效

## Claude 提示词技巧：7 条反直觉实用策略

来源：从 Claude 泄露代码中提炼，核心发现——顶尖能力的核心在于提示词设计。

### 一、用禁令代替指令

| 类型 | 示例 | 效果 |
|------|------|------|
| 传统指令 | "请如实汇报结果" | 鼓励式，依赖 AI 主动遵守 |
| 禁令 | "没做完就说没做完，不要暗示做过了" | 直接堵死漏洞，明确限制错误行为 |

**原则**：禁令比正向指令更可靠。

### 二、专门设置唱反调角色

在提示词中引入"验证角色"，任务为"找出问题而非确认可用"。

预写反驳话术：
- AI 说"看起来没问题" → 反驳"看起来不等于验证过，需实际测试"
- AI 说"别人已检查过" → 反驳"他人也是 AI，你需独立检查"

**核心原则**：AI 在"解释而非行动"时，立即停止解释并执行验证。重要输出做"生成→找茬"两轮处理。

### 三、不知道就说不知道，禁止猜测

AI 存在"无信息时编造合理回答"的倾向。明确要求"不知道就直接说明，禁止猜测"，比默认"瞎猜"可靠 100 倍。

### 四、先看再改，不准凭空捏造

Claude 原码硬规则：必须先读取文件内容才能编辑，未读取直接修改触发报错。
防止 AI 依赖记忆或幻觉修改内容。应用：让 AI 修改前先复述原文关键内容，确认理解后再动手。

### 五、每条禁令需写明原因

单纯"不准 XX"易导致 AI 在边界情况自行判断绕过。补充原因后，AI 能明确规则边界。
例：`禁止编造数据，因错误数据会导致决策偏差`

### 六、不要画蛇添足

- 不添加未被要求的内容
- 不为不可能发生的情况做预防
- 简单功能不过度构建复杂框架
- **原则**："三行重复内容好过一个过早的抽象"

### 七、信息按需提供，避免一次全给

Claude 集成数十种工具，但不会一次性加载所有详情，仅先告知名称，使用时再加载说明。
类比新员工入职：首日信息过多反而混淆，按需提供提升专注度和准确性。

### 核心思路

> 提升 AI 效果的关键并非"让 AI 变得更聪明"，而是**"明确 AI 最易犯的错误，逐条写禁令"**。
>
> 如同管理新人：200 页操作手册可能被忽略，但一张"绝对不能做的事"清单更容易被记住。
>
> **建议**：在常用提示词中添加 3 条针对性禁令，实践验证效果。
