# 学习方法参考

> 这是 [[learning]] 的补充文档，包含详细方法论、编程原理和深度实践指南。

## 四层认知分离法详解

### 第 1 层：你做设计，AI 做打字

**你的工作：**
1. 把需求拆成 5-10 分钟的小任务
2. 每个任务写出伪代码/逻辑草图
3. 明确输入、输出、边界条件

**AI 的工作：** 把你的伪代码翻译成真实代码

**关键动作：** 用自然语言描述逻辑细节，而不是描述结果。

```
❌ "写个排序"
✅ "写一个函数，输入是整数列表，用快排，选第一个元素为 pivot，
   小于 pivot 的放左边，等于的放中间，大于的放右边，
   递归直到长度 <= 1。"
```

这逼你先理解算法，而不是让 AI 选算法。

### 第 2 层：你做验证，AI 做实现

**你的工作：**
1. 写测试用例（预期行为）
2. 审查生成的代码，逐行理解
3. 发现问题后指出具体错误

**AI 的工作：** 实现代码、修复你说出的问题

**关键动作：** 先写测试，再让 AI 写实现。测试就是你对"正确行为"的理解。如果测试写不对，说明你还没想清楚。

```
你：写一个测试，验证 fibonacci(0)==0, fibonacci(1)==1, fibonacci(7)==13
AI：[写测试代码]
你：现在实现 fibonacci 函数让它通过
AI：[写实现]
你：这里为什么要用递归？改成迭代会不会更好？解释一下空间复杂度的差异
```

### 第 3 层：你做诊断，AI 做修复

这是学习最深的一层——**调试**。调试中的因果推理是手写编程最宝贵的认知收益。

**你的工作：**
1. 观察错误现象
2. 形成假设（哪里可能出错）
3. 设计验证假设的实验

**AI 的工作：** 执行你的诊断指令，报告结果

**对话模式：**
```
你：运行这个函数，输入 [3, 1, 2]，结果不对
AI：输出是 [1, 2, 3]，期望是 [3, 2, 1]
你：我觉得是 pivot 选的位置有问题，打印一下每一轮的 pivot 值和分区结果
AI：[添加日志，运行]
你：看到了，第二轮 pivot 选了 1 导致分区不对，应该选中间元素
AI：[修改代码]
你：再跑一次 [5, 3, 7, 1] 验证
```

**你始终在做因果推理**，AI 只是你的手和眼。

### 第 4 层：你做决策，AI 做评估

**你的工作：** 提出架构/方案选择，给出理由

**AI 的工作：** 指出你方案的优劣，提供替代方案

```
你：我想用字典存缓存，用 LRU 策略淘汰，自己实现双向链表
AI：可以，但 Python 有 OrderedDict 内置 LRU。自己实现的好处是学习链表操作，
    但生产代码建议用标准库。你想要学习还是生产效率？
你：学习，自己实现
AI：那从 Node 类开始？每个节点需要 key, value, prev, next 四个属性
你：为什么需要 key？value 不够吗？
AI：因为 LRU 删除最久未用的节点时，需要同时从字典里删除对应的条目，
    没有 key 就无法反向查找字典键。
你：原来如此，那先写 Node 类，再写双向链表的 add/remove/move_to_head 操作
```

## 自检清单

每次编程会话结束前，问自己：

- [ ] 我能解释每一行代码的作用吗？
- [ ] 我知道为什么用这个算法/数据结构，而不是其他选择？
- [ ] 遇到 bug 时，我是先猜原因还是直接让 AI 修？
- [ ] 测试是我写的还是 AI 写的？我理解每个测试在验证什么吗？
- [ ] 如果没有 AI，我能手写出这个程序的核心逻辑吗？

如果任何一个答案是"否"，说明跳过了认知过程，需要补课。

## 与其他方法的关系

- **TDD**：认知学习法天然兼容 TDD——写测试本身就是第 2 层"你做验证"
- **调试铁律**：第 3 层"你做诊断"对应调试铁律"没有根因调查，不实施修复"
- **极简主义**：拆小任务自然导向最小实现
- **[[dev-practice.md|开发实践]]**：本方法是开发实践的核心编程策略

## 编程第一性原理

### 三个基本张力（所有设计决策的本质）

**1. 状态 vs 变换** — 数据应该被"改变"还是被"替换"？
- 状态是复杂度的根源。有状态 = 需要追踪历史 = 更难推理
- 设计第一问："能不能不可变？" 如果能，选不可变。如果不能，集中管理
- Rust 默认不可变、Haskell 纯变换、C 指针直接改内存、React 推动 immutable

**2. 结构 vs 行为** — 是"数据拥有操作"还是"操作处理数据"？
- OO: `dog.bark()` vs FP: `bark(dog)`
- 选择标准：什么变化频繁？数据变多用对象，操作变多用函数
- 没有"谁对谁错"，只有"什么变化频繁"决定什么结构更好

**3. 同步 vs 异步** — "我要等结果"还是"结果好了告诉我"？
- 同步简单但阻塞，异步高效但复杂
- 选择标准：等待时间是否可接受？不要为了"先进"而异步

### 五个基本操作（所有程序都是这五个的组合）

1. **序列（Sequence）** — 先做 A 再做 B。因果关系、时间顺序
2. **选择（Selection）** — 如果 X 则 A 否则 B。分支、条件、决策
3. **重复（Repetition）** — 对每个 X 做 A。遍历、迭代、递归
4. **抽象（Abstraction）** — 给"做 A 然后 B"取个名字叫 C。压缩复杂度
   - 唯一目的：降低理解成本。如果抽象后更难理解，抽象就是错的
5. **组合（Composition）** — 把 C 和 D 组合成 E。从小东西构建大东西

调试时只需搞清哪个层面出了问题：序列错？选择错？重复错？抽象错？组合错？

### 一个元规律

**复杂度是唯一真正不可逆的敌人。**

所有软件工程实践——设计模式、架构分层、测试、代码审查、CI/CD——全是为了对抗复杂度。
本质复杂度（问题本身的复杂度）无法消除，只能管理。（Fred Brooks, 1975, 至今未变）

## AI 时代语言学习哲学

以 Rust 为例得出的通用结论：

**语法表象 vs 内核哲学**
- Rust 语法近 C 系外表（花括号、分号），但所有权/借用/生命周期自成一体
- 学语言不是学语法，是学核心范式

**编译器严格性 = AI 迭代的正反馈信号**
- 强类型 + 所有权 → 编译器精确报错 → AI 据此修复 → 循环至通过
- Python 等动态语言的问题：代码能跑，但隐含内存/类型/并发错误，且无编译器告诉你
- Rust 的严格是结构优势，不是阻碍——"能编译即可靠"

**翻译路径**
- AI 翻译源码可行：人类审查核心范式，AI 处理语法和样板
- "动态语言版 Rust 编译器"不可行：语义模型存在根本矛盾
- 前提：理解目标语言的核心范式（所有权、手动内存、并发模型）

**学习方法进化**
- 传统：先系统学语法 → 再做习题 → 在 AI 时代显得低效
- AI 时代：按需学习（边写边问）→ 即时验证（编译错误贴给 AI）→ 个性化练习（AI 针对错误生成）
- 核心不变量：所有权、借用、生命周期必须亲自理解——审查 AI 代码的基石

**结论**：哲学驱动 + AI 辅助 = 未来多语言开发的主流形态。花少量时间理解核心哲学，依靠 AI 完成语法翻译，聚焦系统设计与安全审查。

## L2 深度实践：验证能力

### 三个层次

1. **能发现不对** — 跑完看到结果不对，知道出 bug 了
2. **能设计怎么发现** — 写代码前就想好"如果这里错了，我怎么发现"
3. **能判断什么值得验证** — 知道哪些地方最容易出错，把验证精力投到刀刃上

### 四个日常练习

- **先猜后跑** — 在运行代码前，先猜结果会是什么。猜错了 = 心智模型有偏差，这是最有价值的学习时刻
- **给 AI 做 Code Review** — 每次拿到 AI 代码，读一遍，找问题。一开始只能找到风格问题，慢慢能发现逻辑漏洞
- **写失败测试** — 别只写"正常路径能跑"的测试，故意写"如果输入错误会怎样"的测试
- **橡皮鸭** — 对着 AI 解释你的代码逻辑，解释不清楚的地方 = 理解不够的地方

### 进步的信号

- 开始能预判"这里大概会出 bug"
- Code Review 时能说出"为什么错"而不只是"这里不对"
- 写测试时开始想边界条件，不只是快乐路径

### 关键认知

**L2 不是"写测试"，是"如果代码错了，我怎么发现"。** 测试只是验证的一种手段，审查、日志、手动检查都是验证。核心习惯：每写一段代码，都问自己"如果这里有 bug，我会怎么发现？"

## L3 深度实践：系统思维

### 三种常见表现

1. **改一处坏另一处** — 修了登录 bug，结果注册坏了。没看到共享状态
2. **顺序敏感** — 先装 A 再装 B 能跑，反过来不行。不知道隐含依赖
3. **边界模糊** — "这个逻辑放 A 模块还是 B 模块？"说不出所以然。不知道模块的真正职责

### 为什么不能直接练

L3 是 L1（理解组件）和 L2（验证行为）叠加后的副产品。就像"全局观"不能单独训练——先理解局部，才能看到全局。

**加速 L3 的习惯：**
- 改代码前画依赖地图 — "这个函数被谁调用？它调用了谁？"
- debug 时追链条 — "这个值从哪里来？经过了哪些变换？"
- 经常问"删了这个模块会怎样" — 答不上来说明没理解它的角色

## L4 深度实践：工程判断

### 本质

**用最简单的方式，实现所有的必要功能。** 面对多个选项时，选最合适的——不是最好的、不是最新的，是这个具体场景下最合适的。

### 判断三种事

1. **做不做** — 这个需求值不值得做？收益多大？不做会怎样？
2. **怎么做** — 方案 A 还是方案 B？各自什么代价？
3. **什么时候做** — 现在做还是以后做？先做核心还是先做边缘？

### 判断力三阶段

- **靠规则** — "听说用 X 比较好" → 跟着规则走，不理解原因
- **靠权衡** — "X 的优点是 A，缺点是 B，这个场景下 A 更重要" → 能做取舍
- **靠直觉** — 看到问题就能判断，因为积累了很多"上次这么做结果怎样"的经验 → 灵活运用，成为架构的支配者

### 涌现机制

L4 从前三层涌现：
- L1 让你知道**有哪些选项**（工具箱里的工具）
- L2 让你知道**每个选项的后果**（用过、验证过、知道效果）
- L3 让你知道**选项之间的连锁反应**（选 A 会影响 B）

三层叠加 → 判断力自然涌现。实践多了，经验够了，就知道在什么场景下选什么工具。

## L5 深度实践：AI 工具精通

### 三个层次

1. **提问者** — "帮我写个 X" → 拿到代码直接用。依赖 AI 判断，自己不验证
2. **协作者** — 能审查 AI 输出，发现问题，指导修改。你和 AI 各有所长，共同推进
3. **指挥者** — 你设计整体方案，拆解任务，指定每个工具的边界，让 AI 在你的框架内执行

### AI 擅长 vs 不擅长

**擅长：** 生成代码、查找信息、解释概念、处理重复性工作、快速原型
**不擅长：** 判断"该不该做"、理解业务上下文、处理模糊需求、对齐多组件行为

### 第三层做法的完整流程

以设计一个 head 工具（读取文件前 N 行）为例：

1. **你决定工具边界** — 和 AI 讨论：参数有哪些？文件路径、行数、默认值？错误处理（文件不存在、权限不足）？
2. **确认接口** — 确定 `execute(params)` 的输入输出格式
3. **让 AI 写测试** — 根据确认的接口生成测试用例
4. **你审查测试** — 检查是否覆盖正常路径、边界条件、错误处理
5. **让 AI 写实现** — 在测试框架内写代码
6. **跑测试验证** — 全部通过 = 功能实现

### 关键分工

**你决定"测什么"，AI 决定"怎么写代码"。** 测试定义"正确"的标准，代码只是满足标准的手段。用单独的智能体隔离开发和测试也是可行的——测试智能体和开发智能体分工明确，互不干扰。

## L6 深度实践：多领域深度

### M 型技能 vs T 型技能

- **T 型** — 一个领域深 + 多个领域浅。传统推荐
- **M 型** — 多个领域都有真正深度。L6 追求的目标

M 型的价值在**组合创新**：领域 A 的解决方案，在领域 B 完全没人想过。不是"懂一点 A 再懂一点 B"，是"在 A 有足够深度，能看出 B 的问题用 A 的方法能解"。

### 跨领域组合的实际价值

- **编程 + 设计** → 能做出审美在线的产品
- **编程 + 领域知识**（金融/医疗/教育）→ 理解需求背后的真实问题，不只翻译需求
- **编程 + 写作** → 好的文档和 API 设计，降低团队沟通成本

### 前提：第二个领域必须是真正的深度

"了解一点"不算。真正深度 = 能独立做判断、能识别好坏、经验能反哺编程。

浅尝辄止的跨领域 = 什么都懂一点但什么都不精 = AI 时代最容易被替代的人。

## 代码讲解策略

- 底层逻辑优先，遇新概念零基础教学（生活比喻带出术语）
- 从问题出发拆解：大问题拆 2-4 个子问题，解释因果链
- 先给最直白的那句话再展开；用户反复追问 = 解释偏了
- 分析时从问题出发拆解，不从概念出发堆砌

## DORA 2025 关键结论

- AI 不修复团队，它放大已有状态
- 吞吐量上升，稳定性下降
- 基础工程实践是 AI 产生正面效应的前提条件
