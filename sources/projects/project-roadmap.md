# Email Assistant 项目发展规划

## 起始分析（2026-05-11）

### 自身条件

- 有技术能力、有充裕时间
- 目标人群明确：AI 开发者 × 效率工具党
- 产品本身缺乏直接付费场景

### 三条发展路径（递进关系，非互斥）

## 方案 A：开源项目 + Build in Public（推荐先做）

**核心思路**：邮件助手本身不卖钱，但「一个开发者用 AI 从零打造实用工具」这个过程本身有价值。

**具体行动**：
- 把项目打磨成高质量开源项目（README、文档、安装脚本、视频 demo）
- 在 GitHub、抖音、即刻上做 build in public——记录开发过程、踩坑、设计决策
- 定位："AI × 终端工作流" 的实战案例，而不是"又一个邮件客户端"
- 变现：不需要直接变现。品牌建立后，自然带来咨询、合作、工作机会

**利弊**：
- 利：零成本启动、完美契合学习目标、内容素材源源不断
- 弊：收入间接且慢、需要持续输出

## 方案 B：AI Skill 开发框架

**核心思路**：从 email_cli.py 提取出通用的「用 AI Agent 接管日常工具」模式，做成脚手架。

**具体行动**：
- 从 email_cli.py 提取出通用的 Skill 骨架（配置管理、CLI 结构、provider 适配）
- 做成一个 Claude Code Skill 模板/脚手架：`skill create --template email-assistant`
- 让其他开发者可以用同样的模式快速构建日历助手、RSS 助手、记账助手等
- 定位：给 AI 应用开发者的脚手架工具

**利弊**：
- 利：从「一个工具」升级到「一种方法论」，影响力放大；框架类项目在开发者圈容易传播
- 弊：需要额外的抽象设计工作；框架需要社区采纳才有价值

## 方案 C：AI 邮件助手 SaaS

**核心思路**：做成 Web 产品，用户绑定邮箱，AI 帮你管理邮件。类似 Superhuman 但 AI 原生。

**具体行动**：
- React/Vue 前端 + Python 后端，复用现有 IMAP/SMTP 逻辑
- 多用户、多邮箱支持、AI 摘要/分类/自动回复
- 订阅制收费

**利弊**：
- 利：有直接收入路径、技术栈全覆盖的学习体验
- 弊：竞争激烈（Superhuman、Shortwave、Copilot 都在做）、获客难、运维成本高、不适合作为第一步

## 推荐执行顺序

**A → B → 视情况决定是否 C**

- 先用 1-2 个月集中做 A，积累内容和受众
- 当社区里有人开始问"我也想做一个类似的"时，B 就是自然的下一步
- C 是最远的目标，除非 A+B 阶段发现了明确的市场信号，否则不急着做

## 关键判断信号

- 触发 B 的信号：社区有人问"我也想做一个"
- 触发 C 的信号：A+B 阶段发现明确的市场需求/付费意愿

## Build in Public 内容策略（2026-05-11）

### 核心定位

不是在推销一个邮件工具，而是在展示「一个人用 AI 能做出什么」。内容的主角是 AI + 开发过程，邮件助手只是载体。

### 内容形式与平台

| 平台 | 内容形式 | 目的 |
|------|----------|------|
| GitHub | 项目本身、Wiki、Issue 讨论 | 技术 credibility 的根基 |
| 即刻 / Twitter(X) | 短帖，开发进展、踩坑瞬间 | 圈子曝光、互动 |
| 抖音 / B站 | 2-5 分钟短视频，录屏+讲解 | 触达更广的技术受众 |
| 公众号 / 博客（可选） | 长文，设计决策深度解析 | SEO 沉淀、深度信任 |

### 内容节奏（前 2 个月集中期）

- 每周 1-2 条短帖：GitHub star 里程碑、解决了一个有趣的 bug、AI 生成的代码 review 对比
- 每 2 周 1 个视频：演示功能、安装教程、从零实现某个功能的录屏
- 1 个月 1 篇长文：比如「我用 Claude Code 做了一个邮件助手，以下是学到的事」

### 关键原则

- 不做产品宣传，做开发日记
- 重点展示「遇到问题 → 分析 → 解决」的思维过程，这比成品更有吸引力
- 抖音/B站视频开头 10 秒必须有 hook：「我用 AI 写了一个能帮我管邮件的终端工具」
