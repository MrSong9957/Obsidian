# s04 子代理

## 核心问题

Agent 执行复杂任务时，对话历史会越来越长。模型要在几百条消息里找上下文，容易"眼花"——回复变慢、注意力分散、甚至搞混不同任务的信息。

怎么让模型在处理子任务时保持清晰的头脑？

## 解决方案：开一个全新的上下文

**给子任务一个干净的 `messages=[]`，让它在独立上下文里工作。子代理干完活后，只把摘要返回给父代理。**

```
父代理 messages = [                子代理 messages = [
  {"user", "帮我调查 bug"},           {"user", "检查 error.log 里最近的错误"},  ← 干净的
  {"assistant", ...工具调用...},      {"assistant", ...工具调用...},
  {"user", ...大量工具结果...},       {"user", ...工具结果...},
  {"user", ...更多工具结果...},     ] ← 用完就丢弃
  ... 已经很长了
]
           │                                      │
           │  调用 task("检查 error.log")          │  运行子循环
           │ ─────────────────────────────────►   │  最多 30 轮
           │                                      │
           │  ← 返回摘要："发现 3 个 NullPointer   │
           │      错误，都在 UserService.java"     │
           │                                      │
父代理 messages 追加一条摘要，不追加子代理的整个历史
```

> 比喻：你是一个项目经理（父代理），接到一个大任务。你派一个实习生（子代理）去调研某个细节。实习生自己有独立的笔记本（新 messages），不跟你的笔记本混在一起。实习生干完回来口头汇报一句（摘要），你把这句话记在自己的笔记本上。实习生的笔记本扔掉（上下文销毁）。

## 完整数据流

```
┌─────────────────────────────────────────────────────────────┐
│  父代理 (Parent Agent)                                       │
│                                                              │
│  messages = [                                                │
│    {"user", "帮我调查这个 bug"},                               │
│    {"assistant", [tool_use("task", "检查 error.log")]},       │
│    {"user", [tool_result("发现 3 个 NullPointer 错误...")]},  │ ← 只有摘要
│  ]                                                           │
│                                                              │
│  PARENT_TOOLS = CHILD_TOOLS + ["task"]                       │
└──────────┬──────────────────────────────────────────────────┘
           │ task 工具触发
           ▼
┌──────────────────────────────────────────────────────────────┐
│  子代理 (Subagent)                                           │
│                                                              │
│  sub_messages = [                                            │
│    {"user", "检查 error.log 里最近的错误"},   ← 全新的上下文   │
│  ]                                                           │
│                                                              │
│  CHILD_TOOLS = [bash, read_file, write_file, edit_file]      │
│  没有 task 工具 → 不能再派子代理（防止无限递归）               │
│                                                              │
│  while stop_reason == "tool_use":  ← 独立的 agent_loop       │
│    bash("tail -100 error.log")                               │
│    read_file("src/UserService.java")                         │
│    ...                                                       │
│                                                              │
│  return "发现 3 个 NullPointer 错误，都在 UserService.java"   │
│                                                              │
│  sub_messages 被丢弃                                         │
└──────────────────────────────────────────────────────────────┘
```

## 源代码逐段解析

### 1. 两套系统提示词

```python
SYSTEM = f"You are a coding agent at {WORKDIR}. Use the task tool to delegate exploration or subtasks."
SUBAGENT_SYSTEM = f"You are a coding subagent at {WORKDIR}. Complete the given task, then summarize your findings."
```

父代理和子代理的系统提示词不同：
- 父代理被告知"你可以派任务"
- 子代理被告知"完成指定任务后总结发现"

### 2. 共享的工具函数

`run_bash`、`run_read`、`run_write`、`run_edit` 和 `TOOL_HANDLERS` 字典跟 s02、s03 完全一样，不再重复。父子代理共享同一个文件系统（`WORKDIR` 相同），所以工具函数是同一套。

### 3. CHILD_TOOLS vs PARENT_TOOLS

```python
# 子代理的工具集：4 个基础工具
CHILD_TOOLS = [
    {"name": "bash", ...},
    {"name": "read_file", ...},
    {"name": "write_file", ...},
    {"name": "edit_file", ...},
]

# 父代理的工具集：基础工具 + task 调度
PARENT_TOOLS = CHILD_TOOLS + [
    {"name": "task",
     "description": "Spawn a subagent with fresh context. It shares the filesystem but not conversation history.",
     "input_schema": {
         "type": "object",
         "properties": {
             "prompt": {"type": "string"},
             "description": {"type": "string", "description": "Short description of the task"}
         },
         "required": ["prompt"]
     }},
]
```

关键设计决策：

```
CHILD_TOOLS  = [bash, read, write, edit]       ← 没有 task
PARENT_TOOLS = CHILD_TOOLS + [task]            ← 父代理多了 task

为什么子代理没有 task？
→ 防止递归派生：子代理不能再派子代理，否则可能出现无限嵌套
→ 这是最简单的递归防护：工具层面直接不可用
```

### 4. run_subagent：子代理的独立循环

```python
def run_subagent(prompt: str) -> str:
    # ① 全新的对话历史——只有一条用户消息
    sub_messages = [{"role": "user", "content": prompt}]

    # ② 独立的 agent_loop，最多 30 轮
    for _ in range(30):  # 安全上限，防止无限循环
        response = client.messages.create(
            model=MODEL, system=SUBAGENT_SYSTEM, messages=sub_messages,
            tools=CHILD_TOOLS, max_tokens=8000,  # 用 CHILD_TOOLS，没有 task
        )
        sub_messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason != "tool_use":
            break    # 模型说完了，跳出循环

        # 执行工具调用
        results = []
        for block in response.content:
            if block.type == "tool_use":
                handler = TOOL_HANDLERS.get(block.name)
                output = handler(**block.input) if handler else f"Unknown tool: {block.name}"
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(output)[:50000]})
        sub_messages.append({"role": "user", "content": results})

    # ③ 只返回最终文本摘要——子代理的整个历史被丢弃
    return "".join(b.text for b in response.content if hasattr(b, "text")) or "(no summary)"
```

三个关键步骤：

```
① sub_messages = [prompt]     → 全新上下文，父代理的几百条消息对子代理不可见
② for _ in range(30)          → 安全上限，跟 while True 等价但不会真的无限
③ return 摘要                  → 子代理可能执行了 20 轮工具调用，但父代理只看到一句话
```

> `"".join(b.text for b in response.content if hasattr(b, "text"))` 这行从模型最后的回复里提取所有文本块拼起来。`hasattr(b, "text")` 过滤掉 tool_use 块（它们没有 text 属性），只保留纯文本。

### 5. agent_loop——task 的特殊处理

```python
def agent_loop(messages: list):
    while True:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=PARENT_TOOLS, max_tokens=8000,  # 用 PARENT_TOOLS
        )
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return

        results = []
        for block in response.content:
            if block.type == "tool_use":
                if block.name == "task":
                    # task 工具 → 派子代理，不是普通工具调用
                    desc = block.input.get("description", "subtask")
                    print(f"> task ({desc}): {block.input['prompt'][:80]}")
                    output = run_subagent(block.input["prompt"])  # 启动子代理
                else:
                    # 其他工具 → 走普通分派
                    handler = TOOL_HANDLERS.get(block.name)
                    output = handler(**block.input) if handler else f"Unknown tool: {block.name}"
                print(f"  {str(output)[:200]}")
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(output)})
        messages.append({"role": "user", "content": results})
```

和 s02/s03 的 agent_loop 对比，唯一区别是 `task` 工具的特殊处理：

```python
if block.name == "task":
    output = run_subagent(block.input["prompt"])   # 走子代理
else:
    handler = TOOL_HANDLERS.get(block.name)        # 走普通分派
    output = handler(**block.input)
```

两种工具调用方式的对比：

| | 普通工具（bash/read/write/edit） | task 工具 |
|---|---|---|
| 执行方式 | 调用函数，立即返回 | 启动新的 agent_loop |
| 上下文 | 共享父代理的 messages | 全新的 messages=[] |
| 返回内容 | 工具的原始输出 | 子代理的文本摘要 |
| Token 消耗 | 只有工具调用本身 | 子代理整段对话的 token |

## 实际运行示例

用户输入：`调查一下为什么登录功能报错`

```
=== 父代理第 1 轮 ===

模型决定派一个子代理去调查:
  tool_use(name="task", input={
    "prompt": "调查登录功能报错原因。检查最近的错误日志和相关代码。",
    "description": "调查登录 bug"
  })

=== 子代理开始运行（父代理在等待） ===

  子代理第 1 轮: bash("grep -r 'login' /var/log/ | tail -20")
  子代理第 2 轮: read_file("src/auth/login.py")
  子代理第 3 轮: bash("grep -r 'NullPointer' src/auth/")
  子代理第 4 轮: read_file("src/auth/session.py")
  子代理第 5 轮: 模型分析完毕，stop_reason = "end_turn"
                返回摘要："在 session.py 第 42 行，logout() 方法没有清除
                          session token，导致重新登录时状态冲突。"

  sub_messages 被丢弃（5 轮对话、几百行日志输出全部消失）

=== 父代理第 2 轮 ===

父代理拿到的 tool_result 只有摘要:
  "在 session.py 第 42 行，logout() 方法没有清除 session token，
   导致重新登录时状态冲突。"

父代理 messages 里没有子代理那几百行日志，上下文保持干净。
父代理可以决定：修复它，或者再派一个子代理去修。
```

## s04 vs s09：两种子代理模式

| | s04 子代理（本篇） | s09 teammates |
|---|---|---|
| 生命周期 | 临时：spawn → 干活 → 销毁 | 持久：创建后一直存在 |
| 上下文 | 用完即弃 | 保留对话历史 |
| 适合场景 | 一次性调查、探索 | 长期协作、多轮交互 |
| 递归防护 | 工具层面移除 task | 权限控制 |
| 通信 | 单向返回摘要 | 双向消息通道 |

> s04 的子代理更像"临时工"——干完活就走，不留痕迹。s09 的 teammates 更像"长期同事"——有持续的记忆，能互相沟通。

## 关键 Python 知识点

### 列表拼接

```python
PARENT_TOOLS = CHILD_TOOLS + [{"name": "task", ...}]
```

`+` 运算符拼接两个列表，返回新列表。这是函数式的做法——原列表不会被修改。如果用 `CHILD_TOOLS.append(...)` 就会修改原列表，导致子代理也能看到 task 工具。

### for 循环的安全上限

```python
for _ in range(30):  # 安全上限
    ...
    if response.stop_reason != "tool_use":
        break
```

`while True` 可能无限循环（如果模型一直调用工具）。`for _ in range(30)` 加了硬上限：最多 30 轮，到了就强制停止。`_` 是惯用写法，表示"不需要用循环变量"。

### hasattr() 检查属性

```python
"".join(b.text for b in response.content if hasattr(b, "text"))
```

`response.content` 里混合了两种类型的块：`text` 块（有 `.text` 属性）和 `tool_use` 块（没有 `.text` 属性）。`hasattr(b, "text")` 过滤出文本块，避免访问不存在的属性时报错。

---

## 一句话总结

**给子任务一个干净的上下文，干完只返回摘要——进程隔离天然带来了上下文隔离。** 父代理永远不用背着子代理的垃圾数据前行。
