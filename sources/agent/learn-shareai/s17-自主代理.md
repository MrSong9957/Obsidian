> _一个团队真正开始"自己运转"，不是因为 agent 数量变多，而是因为空闲的队友会自己去找下一份工作。_

## 这一章要解决什么问题

到了 `s16`，团队已经有持久队友、邮箱、协议、任务板。但还有一个明显瓶颈：

**很多事情仍然要靠 lead 手动分配。**

所以这一章要解决的核心问题是：

**让空闲队友自己扫描任务板，找到可做的任务并认领。**

## 最小心智模型

```
WORK
|
| 当前轮工作做完，或者主动进入 idle
v
IDLE
|
+-- 看邮箱，有新消息 -> 回到 WORK
|
+-- 看任务板，有 ready task -> 认领 -> 回到 WORK
|
+-- 长时间什么都没有 -> shutdown
```

**空闲时，按规则检查两类新输入：邮箱和任务板。**

## 关键数据结构

### 1. Claimable Predicate

```python
def is_claimable_task(task: dict, role: str | None = None) -> bool:
    return (
        task.get("status") == "pending"
        and not task.get("owner")
        and not task.get("blockedBy")
        and _task_allows_role(task, role)
    )
```

4 个条件缺一不可：任务还没开始、还没人认领、没有前置阻塞、角色满足认领策略。

## 最小实现

### 第一步：让队友拥有 WORK -> IDLE 的循环

```python
while True:
    run_work_phase(...)
    should_resume = run_idle_phase(...)
    if not should_resume:
        break
```

### 第二步：IDLE 里先看邮箱

如果有人明确找我，优先处理"明确发给我的工作"。

### 第三步：如果邮箱没消息，按角色扫描可认领任务

```python
unclaimed = scan_unclaimed_tasks(role)
if unclaimed:
    task = unclaimed[0]
    claim_result = claim_task(
        task["id"],
        name,
        role=role,
        source="auto",
    )
```

自治不是"空闲了就乱抢一条"，而是按角色、状态和阻塞关系挑出真正允许接手的工作。

### 第四步：认领后先补身份，再把任务提示塞回主循环

```python
ensure_identity_context(messages, name, role, team_name)
messages.append({
    "role": "user",
    "content": f"Task #{task['id']}: {task['subject']}",
})
messages.append({
    "role": "assistant",
    "content": f"{claim_result}. Working on it.",
})
return True
```

### 第五步：长时间没事就退出

## 为什么认领必须是原子动作

with claim_lock:

## 如何接到前面几章里

这一章是前面几章第一次真正"串起来"：

* `s12` 提供任务板
* `s15` 提供持久队友
* `s16` 提供结构化协议
* `s17` 让队友在没有明确点名时也能自己找活

**从"被动协作"升级到"主动协作"。**

## 一句话记住
