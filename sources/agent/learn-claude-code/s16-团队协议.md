> _有了邮箱以后，团队已经能说话；有了协议以后，团队才开始会"按规矩协作"。_

## 这一章要解决什么问题

`s15` 已经让队友之间可以互相发消息。但如果所有事情都只靠自由文本，会有两个问题：

* 某些动作必须明确批准或拒绝
* 多个请求同时存在，系统很难知道"这条回复对应哪一件事"

最典型的场景：队友要不要优雅关机、某个高风险计划要不要先审批。

结构其实一样：一方发请求，另一方明确回复，双方都用同一个 request_id 对上号。

**一层结构化协议。**

## 最小心智模型

```
1. 协议消息
   { "type": "shutdown_request", "request_id": "req_001", ... }

2. 请求追踪表
   requests = { "req_001": { "kind": "shutdown", "status": "pending" } }
```

## 关键数据结构

### 1. ProtocolEnvelope

```python
message = {
    "type": "shutdown_request",
    "from": "lead",
    "to": "alice",
    "request_id": "req_001",
    "payload": {},
    "timestamp": 1710000000.0,
}
```

### 2. RequestRecord

```python
request = {
    "request_id": "req_001",
    "kind": "shutdown",
    "from": "lead",
    "to": "alice",
    "status": "pending",
}
```

建议落盘到 `.team/requests/req_001.json`，这样请求状态可恢复、协议过程可检查。

### 3. 状态机

```
pending -> approved
pending -> rejected
pending -> expired
```

## 最小实现

### 协议 1：优雅关机

```python
def request_shutdown(target: str):
    request_id = new_id()
    requests[request_id] = {
        "kind": "shutdown",
        "target": target,
        "status": "pending",
    }
    bus.send("lead", target,
             msg_type="shutdown_request",
             extra={"request_id": request_id},
             content="Please shut down gracefully.")
```

### 协议 2：计划审批

完全同一个请求-响应模板。**本章最重要的不是"关机"或"计划"本身，而是同一个协议模板可以反复复用。**

## 协议请求不是普通消息

| 类型 | 解决什么 | 典型字段 |
| --- | --- | --- |
| 普通消息 | "说了什么" | `from` / `to` / `content` |
| 协议消息 | "这件事走到哪一步了" | `type` / `request_id` / `payload` |

## MessageEnvelope、ProtocolEnvelope、RequestRecord、TaskRecord 的边界

| 对象 | 回答什么问题 |
| --- | --- |
| `MessageEnvelope` | 谁跟谁说了什么 |
| `ProtocolEnvelope` | 这是不是结构化请求或响应 |
| `RequestRecord` | 这件协作流程现在走到哪一步 |
| `TaskRecord` | 真正的工作项是什么、谁在做、还卡着谁 |

## 一句话记住

**团队协议的核心，是"请求-响应 + request_id + 状态表"。**

## 1. 核心痛点：为什么需要结构化协议？

在基础的多 Agent 协作中（如松散的 [Agent Teams](https://learn.shareai.run/zh/s15/) 机制），主导者（Lead）与队友（Teammate）之间只有自由文本收发，这在以下两个高频场景中会暴露严重问题：

* **体面关机 (Shutdown)：** 如果 Lead 直接强行杀死某个队友线程，队友写了一半的文件可能会残留在磁盘上，导致系统状态损坏。需要一种“先发起请求、后收尾、确认后再退出”的握手机制。
* **计划审批 (Plan Approval)：** 队友如果想重构核心模块，属于高风险操作。应该先让 Lead 审查计划，审批通过后再动手，而不是直接去改。

这两个场景的结构完全一样：**一方发请求，另一方给回复，且请求和回复必须通过同一个 `request_id` 关联。**

---

## 2. 核心架构与协议状态机

为了让多 Agent 之间的握手有据可查，系统引入了 `ProtocolState` 状态机来追踪每一个请求的生命周期（经历 `pending → approved / rejected` 状态流转）。

### ① 请求状态追踪数据结构

```python
@dataclass
class ProtocolState:
    request_id: str          # 唯一 ID，如 "req_004281"
    type: str                # "shutdown" | "plan_approval"
    sender: str              # 发起方
    target: str              # 接收方
    status: str              # pending | approved | rejected
    payload: str             # 计划文本或关机原因
    created_at: float        # 时间戳

# 全局请求追踪字典
pending_requests: dict[str, ProtocolState] = {}

```

---

## 3. 四步协议核心流程

以 **Lead 请求队友 Alice 关机** 为例，完整通信与握手链路如下：

```
Lead                                                          Alice (Teammate)
  |                                                                  |
  | -- 1. 发起请求 (携带唯一 ID) ----------------------------------> |
  |                                                                  |
  |                                                        [处理任务并进入 idle]
  |                                                        [收到请求，收尾工作]
  |                                                                  |
  | <-- 2. 回应响应 (携带相同 ID) ---------------------------------- |
  |                                                                  |
  v                                                                  v
[3. match_response 校验并关闭请求]                                 [4. 优雅退出线程]

```

## 4. 核心功能代码实现

### ① 消息路由分发（队友端 `dispatch_message`）

队友的收件箱（Inbox）不仅接收普通文本消息，还接收协议消息，由该函数按消息类型（`type`）分发给不同的处理器：

```python
def handle_inbox_message(name, msg, messages):
    msg_type = msg.get("type", "message")
    req_id = msg.get("metadata", {}).get("request_id", "")
    
    # 收到关机请求
    if msg_type == "shutdown_request":
        # 队友回复关机响应，确认释放资源
        BUS.send(name, "lead", "Shutting down.", "shutdown_response", 
                 {"request_id": req_id, "approve": True})
        return True  # 返回 True，停止队友自身的智能体循环，优雅退出
        
    # 收到计划审批的答复
    if msg_type == "plan_approval_response":
        approve = msg["metadata"].get("approve", False)
        messages.append({
            "role": "user", 
            "content": "[Plan approved]" if approve else "[Plan rejected]"
        })
        return False  # 返回 False，继续当前的智能体循环

```

### ② 协议响应匹配与类型校验（Lead 端 `match_response`）

当 Lead 收到队友的回复时，通过此函数进行类型双重校验，防止恶意的消息意外闭合了错误的请求：

```python
def match_response(response_type, request_id, approve):
    state = pending_requests.get(request_id)
    if not state: 
        return
        
    # 类型安全校验：一个 shutdown_response 绝不能意外 approve 一个 plan_approval 请求
    if state.type == "shutdown" and response_type != "shutdown_response": 
        return  # 类型不匹配，跳过
    if state.type == "plan_approval" and response_type != "plan_approval_response": 
        return  # 类型不匹配，跳过
        
    if state.status != "pending": 
        return  # 已解决，跳过重复处理
        
    # 更新 FSM 状态机
    state.status = "approved" if approve else "rejected"

```

### ③ 统一收件箱消费机制 (`consume_lead_inbox`)

为了避免 Lead 读走了消息却漏掉更新协议状态，系统使用统一消费函数：先拦截并路由协议消息，再返回剩余普通的文本内容供大模型理解：

```python
def consume_lead_inbox(route_protocol=True) -> list[dict]:
    msgs = BUS.read_inbox("lead")
    
    if route_protocol:
        for msg in msgs:
            meta = msg.get("metadata", {})
            req_id = meta.get("request_id", "")
            msg_type = msg.get("type", "")
            
            # 如果是响应协议，优先拦截并匹配校验
            if req_id and msg_type.endswith("_response"):
                match_response(msg_type, req_id, meta.get("approve", False))
                
    return msgs  # 返回处理后的消息，通常随之注入到下一轮大模型上下文 history 中

```

### ④ 队友空闲循环（Idle Loop）

之前的队友执行完自己的轮次就直接强退了。在协议保护下，队友在 LLM 返回 `non-tool_use` 后不会退出，而是进入**挂起轮询等待状态**：

```
LLM 返回非 tool_use 
  └──> 进入 idle 状态 (每秒轮询自身 inbox)
        ├──> 收到 shutdown_request ──> 回复 shutdown_response ──> 彻底退出线程
        └──> 收到新任务消息 ───────> 将消息注入到 messages ──> 重新激活 LLM Turn

```

## 5. 教学版 vs. 生产级 Claude Code 源码的差异

* **三向通信关机流：** 生产级源码中（`teammateMailbox.ts`），关机是三向通信。Lead 发送 `shutdown_request` $\rightarrow$ 队友回复 `shutdown_approved`（或 `shutdown_rejected` 并附带原因）$\rightarrow$ 系统最终广播 `teammate_terminated` 信号，自动清理正在运行该 Agent 的终端窗格（Tmux / iTerm2）并解除其名下的任务分配。
* **严格的执行门控 (Permission Gating)：** 教学版只演示了消息的提交和状态转换。在 Claude Code 实际工程中，队友处于计划模式时，如果没有触发 `ExitPlanModeV2Tool` 并获得 Lead 审批通过，底层的 `bash` 和 `write_file` 等所有高危写工具均会被框架机制彻底**锁死拦截**。
