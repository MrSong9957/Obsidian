> _"队友之间要有统一的沟通规矩"_ -- 一个 request-response 模式驱动所有协商。

## 问题

s09 中队友能干活能通信, 但缺少结构化协调：

**关机**: 直接杀线程会留下写了一半的文件和过期的 config.json。需要握手 -- 领导请求, 队友批准 (收尾退出) 或拒绝 (继续干)。

**计划审批**: 领导说 "重构认证模块", 队友立刻开干。高风险变更应该先过审。

两者结构一样: 一方发带唯一 ID 的请求, 另一方引用同一 ID 响应。

## 解决方案

```
Shutdown Protocol           Plan Approval Protocol
==================          ======================
Lead     Teammate           Teammate     Lead
  |         |                   |          |
  |--shutdown_req-->|           |--plan_req------>|
  | {req_id:"abc"} |           | {req_id:"xyz"}  |
  |         |                   |          |
  |<--shutdown_resp-|           |<--plan_resp-----|
  | {req_id:"abc",  |           | {req_id:"xyz",  |
  |  approve:true}  |           |  approve:true}  |

Shared FSM:
  [pending] --approve--> [approved]
  [pending] --reject---> [rejected]
```

## 工作原理

1. 领导生成 request_id, 通过收件箱发起关机请求。

```python
shutdown_requests = {}

def handle_shutdown_request(teammate: str) -> str:
    req_id = str(uuid.uuid4())[:8]
    shutdown_requests[req_id] = {"target": teammate, "status": "pending"}
    BUS.send("lead", teammate, "Please shut down gracefully.",
             "shutdown_request", {"request_id": req_id})
    return f"Shutdown request {req_id} sent (status: pending)"
```

2. 队友收到请求后, 用 approve/reject 响应。

3. 计划审批遵循完全相同的模式。一个 FSM, 两种用途。

## 相对 s09 的变更

| 组件 | 之前 (s09) | 之后 (s10) |
| --- | --- | --- |
| Tools | 9 | 12 (+shutdown_req/resp +plan) |
| 关机 | 仅自然退出 | 请求-响应握手 |
| 计划门控 | 无 | 提交/审查与审批 |
| 关联 | 无 | 每个请求一个 request_id |
| FSM | 无 | pending -> approved/rejected |

# 新版 System Prompt

根据 [Learn Claude Code](https://learn.shareai.run/zh/s08/) 课程第 **s10 System Prompt（运行时提示词装配）** 章节的正文，其核心概念、工作原理与教学版代码实现提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 在传统的 LLM 应用开发中，开发者习惯将所有的提示词（Identity 设定、任务目标、代码规范、工具列表、全局变量等）全部硬编码写成一个巨大的静态字符串塞给大模型。当面对复杂的软件工程智能体系统时，硬编码会带来灾难：
1. **破坏缓存：** 只要 CWD（当前工作目录）或任务状态发生一丁点改变，整个提示词的哈希签名就会彻底改变，导致大模型的 **Prompt Cache（提示词缓存）完全失效**，费用暴涨。
2. **逻辑耦合：** 工具、技能（Skills）、记忆（Memory）的代码逻辑与提示词深度交织，难以维护。


* **解决思路：** **“运行时动态装配，从不硬编码（Assembled at Runtime, Never Hardcoded）”**。将 System Prompt 视为一个由不同策略（Policies）、工具（Tools）、技能（Skills）和当前运行时上下文（Runtime Context）共同拼装出来的“生成式产物”。引入 **Section Shelf（货架分区）** 架构，严格按照特定层级进行顺序组装，在最大化命中 Prompt Cache 的同时，保证逻辑的彻底解耦。

---

## 2. 核心工作原理：货架分区与缓存锁定

系统将整个 System Prompt 划分为四个标准货架分区（Section），其拼装和对齐顺序不可颠倒：

```
┌────────────────────────────────────────┐
│  Section 1: Identity & Capabilities   │ ───► 完全静态 (绝对命中 Cache)
├────────────────────────────────────────┤
│  Section 2: Tools Schemas             │ ───► 相对稳定 (高度命中 Cache)
├────────────────────────────────────────┤
│  Section 3: Long-term Memory Catalog  │ ───► 极少变动 (大部分命中 Cache)
├────────────────────────────────────────┤
│  Section 4: Runtime Environment (CWD) │ ───► 频繁变动 (卡在末尾，防缓存击穿)
└────────────────────────────────────────┘

```

* **缓存不变性（Cache Invariance）：** 将**绝对不会变**的设定放在最前面，将**变动最频繁**的运行时状态（如当前路径、时间）**硬编码锁死在整个 System Prompt 的最末尾**。这样，前三个货架可以完美拼装出连续的缓存切片（Cache Buckets），保证 90% 以上的底座 Token 永久命中缓存。

---

## 3. 核心功能代码实现

### ① 货架数据结构与注册器

引入 `PromptSection` 类，实现对各个提示词块的生命周期与缓存权重的标准化管理：

```python
from dataclass import dataclass
import time
from pathlib import Path

@dataclass
class PromptSection:
    id: str             # 分区唯一标识，如 "identity", "tools", "runtime"
    owner: str          # 归属模块，如 "core", "tool_registry", "context_loader"
    content_fn: callable # 动态生成内容的函数指针，保证运行时获取最新状态
    cache_weight: int   # 缓存权重（越低越靠前，越稳定）

```

### ② 四大分区内容的运行时动态生成

```python
WORKDIR = Path(".").resolve()

# 货架 1：身份设定 (绝对静态)
def get_identity_content() -> str:
    return "You are a professional, highly autonomous coding agent. Your goal is to solve tasks safely and efficiently."

# 货架 2：工具集描述 (跟随工具池动态更新，但相对稳定)
def get_tools_content() -> str:
    # 假设从工具池动态拉取当前注册的所有工具 Schema 的名称与描述
    # 生产级会在此处输出严格排序（字母序）的工具清单，对齐缓存哈希
    return "Available Tools:\n- bash: Run commands\n- read_file: View file contents\n- write_file: Modify files"

# 货架 3：记忆与技能目录 (低频更新)
def get_memory_skills_content() -> str:
    # 仅输出极轻量的 Markdown 链接和目录，完整细节按需借调
    return "Long-term Knowledge Catalog:\n- user-tabs: User preference for indentation.\n- code-review: General PR checklist."

# 货架 4：运行时上下文 (高频变动，强制锁死在最后)
def get_runtime_content() -> str:
    return (
        f"Current Workspace Context:\n"
        f"  - CWD: {WORKDIR}\n"
        f"  - System Time: {time.strftime('%Y-%m-%d %H:%M:%S')}"
    )

```

### ③ 动态货架装配算法 (`assemble_system_prompt`)

统一装配器。在每次 Agent 准备向大模型发送请求前实时调度，按照 `cache_weight` 字典序将所有分区无缝揉合：

```python
# 全局提示词货架列表
PROMPT_SHELF: list[PromptSection] = [
    PromptSection("identity", "core", get_identity_content, cache_weight=10),
    PromptSection("tools", "tool_registry", get_tools_content, cache_weight=20),
    PromptSection("memory_skills", "context_loader", get_memory_skills_content, cache_weight=30),
    PromptSection("runtime", "runtime", get_runtime_content, cache_weight=100), # 变动最大的放最后面
]

def assemble_system_prompt() -> str:
    """运行时动态提示词装配内核"""
    # 1. 严格按照缓存权重由低到高排序，锁定物理分布位置
    sorted_shelf = sorted(PROMPT_SHELF, key=lambda s: s.cache_weight)
    
    blocks = []
    for section in sorted_shelf:
        try:
            # 2. 运行时动态调用函数，捞取当前最新的内容状态
            content = section.content_fn()
            
            # 3. 标准化包裹 XML 标签，确保大模型能完美分离结构
            block_text = (
                f"<system-section id='{section.id}' owner='{section.owner}'>\n"
                f"{content}\n"
                f"</system-section>"
            )
            blocks.append(block_text)
        except Exception as e:
            # 容错降级：某一货架崩了不能导致整个智能体死锁，注入错误提示继续装配
            blocks.append(f"<system-section id='{section.id}'>Error loading section: {str(e)}</system-section>")
            
    # 4. 用统一的双换行拼接成最终的单条大 System Prompt 字符串
    return "\n\n".join(blocks)

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 **Claude Code** 工业级生产级源码（主要分布在 `services/prompt/` 目录下的 `promptAssembly.ts`、`createSystemPrompt.ts` 之中）中，其架构设计极具技术壁垒：

* **静态类型检查与常量断言锁 (`const as const`)：** 在 CC 源码中，每个货架分区的元数据（如 `id: "identity" as const`）全量使用了 TypeScript 的**字面量强类型断言**。这在工程编译期就彻底封死了开发者由于手误修改分区名称引发的崩溃隐患，确保所有拼装策略在全链路天然具备类型安全（Type-safe）。
* **Antrhopic 缓存切片对齐机制 (`cache_control`)：** 生产级装配器在组装 XML 字符串时，不是简单地返回文本。对于前三个极稳定的货架（`identity`、`tools`、`memory`），系统会在组装结果的数据结构里隐式附带极其关键的 **`"cache_control": {"type": "ephemeral"}`** 显式标记。这会直接告知 Anthropic 的 API 网关：“请在这里强行卡住并切分缓存”。而把最后一个高频变动的 `runtime` 货架排除在缓存控制之外，达成了精密的 Token 费用节约策略。
* **按需裁剪降级门控 (`fitPromptToBudget`)：** 当项目中的子 Agent 或者是 MCP 工具数量突然暴增，导致装配出来的 System Prompt 总大小快要逼近大模型单次请求的 Token 限制上限时，生产级源码不会任由其直接报错击穿。系统内置了一个 `fitPromptToBudget()` 算法：它会**由后向前**依次降低货架的细节丰满度（例如将 `tools` 货架中的冗长例子删除，只保留纯参数定义；或者是截断 `memory_skills` 的行数），在运行时弹性确保总装配提示词绝对安全、不超标。
