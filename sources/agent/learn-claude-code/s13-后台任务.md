> _慢命令可以在旁边等，主循环不必陪着发呆。_

## 这一章要解决什么问题

前面几章里，工具调用基本都是：

```
模型发起 -> 立刻执行 -> 立刻返回结果
```

但遇到慢操作（`npm install`、`pytest`、`docker build`）就会卡住。

所以这一章要解决的是：

**把"慢执行"移到后台，让主循环继续推进别的事情。**

## 最小心智模型

**主循环仍然只有一条，并行的是等待，不是主循环本身。**

```
主循环
|
+-- background_run("pytest")
| -> 立刻返回 task_id
|
+-- 继续别的工作
|
+-- 下一轮模型调用前
    -> drain_notifications()
    -> 把摘要注入 messages

后台执行线
|
+-- 真正执行 pytest
+-- 完成后写入通知队列
```

## 关键数据结构

### 1. RuntimeTaskRecord

```python
task = {
    "id": "a1b2c3d4",
    "command": "pytest",
    "status": "running",
    "started_at": 1710000000.0,
    "result_preview": "",
    "output_file": "",
}
```

教学版建议落成两份文件：

```
.runtime-tasks/
  a1b2c3d4.json  # RuntimeTaskRecord
  a1b2c3d4.log   # 完整输出
```

### 2. Notification

```python
notification = {
    "type": "background_completed",
    "task_id": "a1b2c3d4",
    "status": "completed",
    "preview": "tests passed",
}
```

通知只负责做一件事：告诉主循环"有结果回来了"。

## 最小实现

### 第一步：登记后台任务

```python
class BackgroundManager:
    def __init__(self):
        self.tasks = {}
        self.notifications = []
        self.lock = threading.Lock()
```

### 第二步：启动后台执行线

```python
def run(self, command: str) -> str:
    task_id = new_id()
    self.tasks[task_id] = {
        "id": task_id,
        "command": command,
        "status": "running",
    }
    thread = threading.Thread(
        target=self._execute,
        args=(task_id, command),
        daemon=True,
    )
    thread.start()
    return task_id
```

**主循环拿到 `task_id` 后就可以先继续往前走。**

### 第三步：完成后写通知

```python
def _execute(self, task_id: str, command: str):
    try:
        result = subprocess.run(..., timeout=300)
        status = "completed"
        preview = (result.stdout + result.stderr)[:500]
    except subprocess.TimeoutExpired:
        status = "timeout"
        preview = "command timed out"
    with self.lock:
        self.tasks[task_id]["status"] = status
        self.notifications.append({
            "type": "background_completed",
            "task_id": task_id,
            "status": status,
            "preview": preview,
        })
```

### 第四步：下一轮前排空通知

```python
def before_model_call(messages: list):
    notifications = bg.drain_notifications()
    if not notifications:
        return
    text = "\n".join(
        f"[bg:{n['task_id']}] {n['status']} - {n['preview']}"
        for n in notifications
    )
    messages.append({"role": "user", "content": text})
```

## 为什么完整输出不要直接塞回 prompt

1. 完整输出写磁盘
2. 通知里只放简短摘要
3. 模型真的要看全文时，再调用 `read_file`

**通知负责提醒，文件负责存原文。**

# 新版 Background Tasks

根据 [Learn Claude Code](https://learn.shareai.run/zh/s13/) 课程第 **[s13 Background Tasks（异步后台线程）](https://learn.shareai.run/zh/s13/)** 章节的正文，其核心概念、工作原理与教学版代码实现提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 智能体在执行软件工程任务时，经常会遇到极度耗时的**长时阻塞操作**（如 `npm install` 跑 2 分钟、跑完整个流水线的集成测试、或者编译大型 C++ 源码）。如果让 Agent Loop 处于同步等待状态，不仅会造成严重的“前端卡死”假象，极大地败坏用户交互体验，更会白白中断智能体当前的思考心流。
* **解决思路：** **“慢操作进后台，主线程继续想（Slow Operations Go to the Background）”**。引入类似于操作系统的守护后台线程（Daemon Background Threads）**机制。主线程在遭遇长时任务时，仅负责“创建并踢入后台”这一瞬间动作，随后立刻恢复自由身，继续分析下一个文件或与人类对话；而慢操作则在后台的**独立异步管道（Background Lanes）中静默高能运转。

---

## 2. 三轨并行与通知队列机制

系统在底层运行时被拆分为三条并行的核心轨道：

| 轨道 / 机制 | 物理角色 | 核心职责 |
| --- | --- | --- |
| **1. Main Thread** | 主线程（前台） | 保持 CLI 交互响应，持续推进 Agent 逻辑思考，不被任何 IO 拖垮。 |
| **2. Background Lanes** | 后台异步执行车道 | 并行物理执行耗时较长的 Bash 脚本、编译或自动化测试。 |
| **3. Notification Queue** | 缓冲通知队列 | 后台任务完成或崩溃时，不粗暴地弹窗打断前台，而是向队列投递一个 `Notification` 信号，静静等待主线程在下一轮循环的安全节点主动“收件”。 |

---

## 3. 核心功能代码实现（379 LOC 教学版内核）

### ① 异步任务管理器与全局状态

利用 Python 的 `threading` 模块构建轻量级的异步任务托管中心：

```python
import threading
import subprocess
import queue
import time
from dataclasses import dataclass

# 全局异步通知缓冲队列
NOTIFICATION_QUEUE = queue.Queue()

@dataclass
class BackgroundJob:
    id: str
    command: str
    status: str  # running, success, failed
    output: str = ""

# 内存全局任务注册表
ACTIVE_JOBS: dict[str, BackgroundJob] = {}

def _async_worker(job_id: str, command: str):
    """在独立的后台线程中物理拉起子进程，不阻塞主 TTY"""
    job = ACTIVE_JOBS[job_id]
    try:
        # 物理挂起长时进程
        process = subprocess.Popen(
            command, shell=True, stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True
        )
        stdout, _ = process.communicate() # 此时在此线程内部阻塞等待结果
        
        job.output = stdout
        if process.returncode == 0:
            job.status = "success"
        else:
            job.status = "failed"
    except Exception as e:
        job.status = "failed"
        job.output = str(e)
    finally:
        # 核心：执行完毕或遭遇崩溃后，向主线程唯一的通知队列投递结项红利
        NOTIFICATION_QUEUE.put({"event": "job_finished", "job_id": job_id})

```

### ② 踢入后台工具 (`dispatch_background_task`)

包装为标准的大模型 Schema 工具。大模型调用它后，工具瞬间返回一个“任务已建”的回执，绝不逗留：

```python
JOB_COUNTER = 0

TOOLS = [
    {
        "name": "dispatch_background_task",
        "description": "Spawn a long-running bash command in the detached daemon background lane.",
        "input_schema": {
            "type": "object",
            "properties": {
                "command": {"type": "string", "description": "The slow command to run, e.g., 'npm install'"}
            },
            "required": ["command"]
        }
    }
]

def run_dispatch_background_task(command: str) -> str:
    global JOB_COUNTER
    JOB_COUNTER += 1
    job_id = f"JOB-{JOB_COUNTER}"
    
    # 1. 登记入库
    ACTIVE_JOBS[job_id] = BackgroundJob(id=job_id, command=command, status="running")
    
    # 2. 瞬间派生守护线程，脱离主控制流
    t = threading.Thread(target=_async_worker, args=(job_id, command), daemon=True)
    t.start()
    
    # 3. 瞬间向大模型复命，耗时接近 0ms
    return f"Success: Command dispatched to background. Track ID: {job_id}. Do not wait for it; proceed with other reasoning."

TOOL_HANDLERS = {"dispatch_background_task": run_dispatch_background_task}

```

### ③ 安全节点收件箱消费与 Agent Loop 闭环

主循环绝对不能在任意位置被子线程随机弹窗打断（避免破坏 LLM 会话状态）。必须采用 **“主动拉取（Polling at Safe Node）”** 策略：在每一轮 LLM 决策前，看一眼收件箱，把已完结的后台成果作为外部事实喂给模型：

```python
def check_and_inject_notifications(messages: list):
    """在每一轮调用大模型前的黄金安全节点，统一消费通知队列"""
    injected_notifs = []
    
    while True:
        try:
            # 非阻塞尝试捞取队列消息
            notif = NOTIFICATION_QUEUE.get_nowait()
            job_id = notif["job_id"]
            job = ACTIVE_JOBS[job_id]
            
            # 将后台跑出来的真实数据组装为一则外部紧急动态通知
            report = (
                f"\n[BACKGROUND NOTIFICATION] Background task {job_id} ('{job.command}') "
                f"has finished with status: {job.status.upper()}.\n"
                f"Output summary:\n{job.output[-1000:]}" # 截取后1000字，防撑爆
            )
            injected_notifs.append(report)
            NOTIFICATION_QUEUE.task_done()
        except queue.Empty:
            break # 队列全掏空了，体面退出
            
    if injected_notifs:
        # 核心：将所有完成的后台异步结果，作为最新的 user 消息动态补丁追加进历史，推给大模型自纠
        combined_report = "\n\n".join(injected_notifs)
        print(f"\033[93m[POLLING] Injecting finished async jobs: {list(ACTIVE_JOBS.keys())}\033[0m")
        messages.append({"role": "user", "content": combined_report})

def agent_loop_with_async_lanes(messages):
    while True:
        # --- 【核心新增：安全节点收件箱提取】 ---
        check_and_inject_notifications(messages)
        
        # 呼叫大模型
        response = client.messages.create(model=MODEL, messages=messages, tools=TOOLS)
        messages.append({"role": "assistant", "content": response.content})
        
        if response.stop_reason != "tool_use":
            # 如果模型想退出，但后台还有没跑完的任务，进行安全节流锁拦截
            running_jobs = [j.id for j in ACTIVE_JOBS.values() if j.status == "running"]
            if running_jobs:
                print(f"[AWAIT] System cannot exit yet. Tasks still running in background: {running_jobs}")
                time.sleep(5) # 强行挂起前台，直到后台清空或有通知进来触发下一轮
                continue
            break # 物理安全退出
            
        # 正常的同步/异步工具分发执行
        # (若是同步工具则原地卡住执行；若是 dispatch_background_task 则瞬间返回，代码省略...)

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 **Claude Code** 生产级工业代码（主要分布在 `src/services/background/` 目录下的 `TaskProcessLane.ts`、`NotificationCenter.ts`）中，其并发模型的工程考量极其深邃：

* **完全隔离的伪终端影子空间 (PTY Shaded Isolation)：** 教学版代码直接粗暴使用 `subprocess.Popen(shell=True)`，这会导致后台任务的彩色高亮格式日志、交互式中断信号直接缺失。真实源码在底层调用了高度复杂的 **`node-pty`（物理伪终端库）**。它会为每一个被踢入后台的长时任务强行向操作系统申请开辟一个拥有完整独立 TTY 特性的进程影子。这保证了即便是后台默默跑的测试，也能完美吐出带有带颜色的断言矩阵，保留最纯正的日志环境。
* **主动心跳侦测与僵死拦截锁 (`Zombie Process Gatekeeper`)：** 如果大模型派发了一个包含死循环的后台任务（如误触了不带 `-y` 的交互式无限等待弹窗，或写错了死循环脚本），后台车道会被永久霸占。真实生产代码设计了“主从心跳护栏（Heartbeat Grim Reaper）”：后台 Lane 在拉起 PTY 时，会向内核挂载一个特定时间步长的守护时钟（Watcher）。一旦侦测到该后台 PTY 连续 5 分钟没有产生任何一行 `stdout` 吐字更新，或者 CPU 占用率持续异常归零，主控中心的 `NotificationCenter` 会无情地判定其死锁，越权发送 `SIGKILL` 强行击杀僵尸卡片，并向大模型抛出结构化的超时错误，实现了长时并发的容错刚性。
* **高精度的并行底座锁控制 (Concurrency Lockstep)：** 在真实源码里，如果有多个后台任务并行结束，它们同时往主线程投递数据时，为了绝对不击穿大模型的单次 Prompt Cache 哈希结构，系统设计了名为 `getAggregateNotificationAttachment` 的压缩算法。它不会让消息在消息链条（Messages Array）中散乱平铺，而是会把同一时间段完结的所有 Job Output 合并归拢，放入到一个结构极其紧凑的统一 XML 标签包裹内。这样能促使模型在面对多任务并发归口时，依然能最大限度维持上下文长文本哈希的不变性，极力保全企业的资费预算。
