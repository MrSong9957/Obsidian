> _上下文不是越多越好，而是要把"仍然有用的部分"留在活跃工作面里。_

## 这一章要解决什么问题

到了 `s05`，agent 已经会：

* 读写文件
* 规划步骤
* 派子 agent
* 按需加载 skill

也正因为它会做的事情更多了，上下文会越来越快膨胀：

* 读一个大文件，会塞进很多文本
* 跑一条长命令，会得到大段输出
* 多轮任务推进后，旧结果会越来越多

如果没有压缩机制，很快就会出现这些问题：

1. 模型注意力被旧结果淹没
2. API 请求越来越重，越来越贵
3. 最终直接撞上上下文上限，任务中断

所以这一章真正要解决的是：

**怎样在不丢掉主线连续性的前提下，把活跃上下文重新腾出空间。**

## 先解释几个名词

### 什么是上下文窗口

> 模型这一轮真正能一起看到的输入容量。它不是无限的。

### 什么是活跃上下文

> 当前这几轮继续工作时，最值得模型马上看到的那一部分。

### 什么是压缩

> 用更短的表示方式，保留继续工作真正需要的信息。

例如：

* 大输出只保留预览，全文写到磁盘
* 很久以前的工具结果改成占位提示
* 整段长历史总结成一份摘要

## 最小心智模型

```
第 1 层：大结果不直接塞进上下文
  -> 写到磁盘，只留预览

第 2 层：旧结果不一直原样保留
  -> 替换成简短占位

第 3 层：整体历史太长时
  -> 生成一份连续性摘要
```

手动触发 `/compact` 或 `compact` 工具，本质上也是走第 3 层。

## 关键数据结构

### 1. Persisted Output Marker

当工具输出太大时，不要把全文强塞进当前对话：

```
Full output saved to: .task_outputs/tool-results/abc123.txt
Preview:
...
```

### 2. CompactState

```python
{
    "has_compacted": False,
    "last_summary": "",
    "recent_files": [],
}
```

### 3. Micro-Compact Boundary

教学版可以先设一条简单规则：**只保留最近 3 个工具结果的完整内容，更旧的改成占位提示。**

## 最小实现

### 第一步：大工具结果先写磁盘

```python
def persist_large_output(tool_use_id: str, output: str) -> str:
    if len(output) <= PERSIST_THRESHOLD:
        return output
    stored_path = save_to_disk(tool_use_id, output)
    preview = output[:2000]
    return (
        "\n"
        f"Full output saved to: {stored_path}\n"
        f"Preview:\n{preview}\n"
    )
```

### 第二步：旧工具结果做微压缩

```python
def micro_compact(messages: list) -> list:
    tool_results = collect_tool_results(messages)
    for result in tool_results[:-3]:
        result["content"] = "[Earlier tool result omitted for brevity]"
    return messages
```

### 第三步：整体历史过长时，做一次完整压缩

```python
def compact_history(messages: list) -> list:
    summary = summarize_conversation(messages)
    return [{
        "role": "user",
        "content": (
            "This conversation was compacted for continuity.\n\n"
            + summary
        ),
    }]
```

压缩结果至少要保住：当前任务目标、已完成的关键动作、已修改的文件、关键决定与约束、下一步应该做什么。

### 第四步：在主循环里接入压缩

```python
def agent_loop(state):
    while True:
        state["messages"] = micro_compact(state["messages"])
        if estimate_context_size(state["messages"]) > CONTEXT_LIMIT:
            state["messages"] = compact_history(state["messages"])
            state["has_compacted"] = True
        response = call_model(...)
        ...
```

## 它如何接到主循环里

从这一章开始，agent loop 同时维护两件事：

```
任务推进
上下文预算
```

## 初学者最容易犯的错

1. 以为压缩等于删除（不是，是换一种表示）
2. 只在撞到上限后才临时乱补（应该从一开始就有三层）
3. 摘要只写成一句空话（要保住文件、决定、下一步）
4. 把压缩和 memory 混成一类（压缩=当前会话太长，memory=跨会话保留）

## 一句话记住

**上下文压缩的核心，不是尽量少字，而是让模型在更短的活跃上下文里，仍然保住继续工作的连续性。**

# 新版上下文压缩

在 Claude Code 的架构设计中，**三层上下文压缩策略（Context Compaction）** 是为了解决 Agent 在面对长会话或大型项目时，上下文窗口（Context Window）爆满导致 API 报错（`prompt_too_long`）的核心机制。

它的核心设计原则是：**“便宜的先跑，贵的后跑”**——先通过无 API 消耗的纯文本/结构操作进行裁剪，最后逼不得已才调用 LLM 进行摘要。

---

## 核心工作原理

在每轮 LLM 调用前，系统会自动按顺序执行以下三层预处理程序（均为 0 API 调用）：

### 1. L3: 大结果落盘 (`tool_result_budget`)

* **解决痛点：** Agent 一次性读取了几个大文件，单条消息中的工具返回结果（`tool_result`）可能就高达数百 KB，直接挤爆上下文。
* **处理逻辑：** 检查最后一条 user 消息中所有工具返回内容的总大小。如果超过 **200KB** 的预算，系统会按大小排序，把最大的内容直接写入本地磁盘（`.task_outputs/tool-results/`），在上下文中仅保留一个 `<persisted-output>` 标记和前 2000 字符的预览。
* **效果：** 模型看到标记知道完整内容在磁盘上，需要时可以重新读取，瞬间释放了巨大的空间。

### 2. L1: 裁掉无关的旧对话 (`snip_compact`)

* **解决痛点：** 随着对话轮数增加（比如跑了 80 轮），最早期的对话（如“帮我创建个环境”）早已与当前工作无关，却仍白白占用 Token。
* **处理逻辑：** 当消息数超过一定阈值（如 50 条）时，系统会**保留最头部的 3 条**（初始上下文）和**最尾部的 47 条**（当前工作），直接将中间的旧对话“剪掉”，并替换为一个占位符 `[snipped X messages...]`。
* **注意点：** 裁剪时有严格的边界保护，绝对不会把 `assistant(tool_use)` 和它对应的 `user(tool_result)` 强行拆开。

### 3. L2: 旧工具结果占位 (`micro_compact`)

* **解决痛点：** 即使中间的对话被剪了，留在尾部工作区的消息里可能还躺着之前几次 `cat` 某个文件输出的完整文本，这些旧的工具输出依然很重。
* **处理逻辑：** 系统**仅保留最近 3 条**工具返回结果（`tool_result`）的完整内容。对于更早的工具结果，只要内容长度大于 120 字符，直接将其内容清空，替换为轻量占位符 `[Earlier tool result compacted. Re-run if needed.]`。
* **效果：** 极大地对当前活跃的上下文进行了“抽脂”。

---

## 为什么执行顺序是 L3 → L1 → L2？

在实际源码中，执行顺序至关重要，绝对不能换：

1. **必须先跑 L3（大结果落盘）：** 因为如果先跑了 L2（旧结果占位），大文件的内容直接就被替换成占位符抹去了，L3 就没办法把完整的工具输出保存到磁盘供后续使用了。

---

## 进阶：如果三层压缩后还是超标怎么办？

如果经历了这三层纯文本裁剪后，Token 数量依然超过了安全阈值，系统就会启动兜底的 **L4: LLM 全量摘要 (`compact_history`)**：

1. **保存完整记录：** 先把至今为止的完整对话保存到本地（`.transcripts/`）。
2. **LLM 总结：** 调用一次 LLM（产生 1 次 API 消耗），让它把复杂的历史对话压缩成一份包含 *当前目标、重要发现、已改文件、剩余工作* 的精简摘要。
3. **彻底替换：** 用这份摘要把所有的旧消息全部替换掉，实现无限续航。
