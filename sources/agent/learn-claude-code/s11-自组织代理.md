> _"队友自己看看板, 有活就认领"_ -- 不需要领导逐个分配, 自组织。

## 问题

s09-s10 中, 队友只在被明确指派时才动。领导得给每个队友写 prompt, 任务看板上 10 个未认领的任务得手动分配。这扩展不了。

真正的自治: 队友自己扫描任务看板, 认领没人做的任务, 做完再找下一个。

一个细节: 上下文压缩 (s06) 后智能体可能忘了自己是谁。身份重注入解决这个问题。

## 解决方案

```
Teammate lifecycle with idle cycle:

  +-------+
  | spawn |
  +---+---+
      |
      v
  +-------+   tool_use     +-------+
  | WORK  | <------------- |  LLM  |
  +---+---+                +-------+
      |
      | stop_reason != tool_use (or idle tool called)
      v
  +--------+
  |  IDLE  |  poll every 5s for up to 60s
  +---+----+
      |
      +---> check inbox --> message? ----------> WORK
      |
      +---> scan .tasks/ --> unclaimed? -------> claim -> WORK
      |
      +---> 60s timeout ----------------------> SHUTDOWN
```

## 工作原理

1. 队友循环分两个阶段: WORK 和 IDLE。

```python
def _loop(self, name, role, prompt):
    while True:
        # -- WORK PHASE --
        messages = [{"role": "user", "content": prompt}]
        for _ in range(50):
            response = client.messages.create(...)
            if response.stop_reason != "tool_use":
                break
            # execute tools...
            if idle_requested:
                break

        # -- IDLE PHASE --
        self._set_status(name, "idle")
        resume = self._idle_poll(name, messages)
        if not resume:
            self._set_status(name, "shutdown")
            return
        self._set_status(name, "working")
```

2. 空闲阶段循环轮询收件箱和任务看板。

3. 任务看板扫描: 找 pending 状态、无 owner、未被阻塞的任务。

4. 身份重注入: 上下文过短 (说明发生了压缩) 时, 在开头插入身份块。

# 新版 Error Recovery

根据 [Learn Claude Code](https://learn.shareai.run/zh/s11/) 课程第 **s11 Error Recovery（错误恢复与自愈）** 章节的正文，其核心概念、工作原理与教学版代码实现提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 在复杂的智能体长时运行（Long-running Agent Loop）中，错误是不可避免的。传统的系统一旦遇到大模型输出阶段性被截断（Max Tokens 溢出）、上下文过长导致溢出（Prompt Too Long）、或者底层服务频次超限（Rate Limit 429），通常会采取直接报错并崩溃退出的方式。这不仅导致之前的多步执行成果付诸东流，更极大伤害了自动化流水线的稳定性。
* **解决思路：** **“错误不是终点，而是重试与自愈的起点（Errors are the start of a retry）”**。构建一套智能的 **Failure Inbox（故障收件箱）**，在框架底层拦截所有异常。系统不盲目重试，而是将错误进行分类分级（Classification），并结合当前的 **RecoveryState（恢复状态机）** 动态调整系统参数（如动态扩大 Max Tokens 预算、强行触发上下文压缩、或无缝降级模型底座），在用户完全无感知的情况下实现静默自愈。

---

## 2. 三大错误恢复路径图 (Error Recovery Paths)

系统将最常见的生产级故障分为三大防御路径：

| 故障现象 (Failure Inbox) | 核心诱因 | 自愈动作 (Recovery Action) |
| --- | --- | --- |
| **`max_tokens` 溢出** | 模型在回答复杂问题或输出大量代码时中途被强行截断 | 将 `max_tokens` 从默认的 `8K` 动态暴力提升至 `64K`（甚至更高），使用原请求重新发起续写或重试。 |
| **`prompt_too_long` 溢出** | 会话轮数过多，导致上下文总长超限（Context Too Large） | 强行立即调用 [Context Compact](https://learn.shareai.run/zh/s08/) 压缩模块对历史进行脱水，重置计数器并重试。 |
| **`429 Rate Limited`** | 触发了云端 API 的并发或每分钟 Token（TPM）频率限制 | 自动将当前的 `current_model` 从主力高配模型（Primary）降级切换到轻量平替模型（Fallback），保持业务连续性。 |

---

## 3. 核心功能代码实现（287 LOC 教学版内核）

### ① 恢复状态机与故障收件箱定义

引入 `RecoveryState` 来精确跟踪当前的异常重试频次与运行参数：

```python
from dataclass import dataclass
import time

@dataclass
class RecoveryState:
    max_tokens: int = 8000          # 默认输出预算
    current_model: str = "claude-3-5-sonnet" # 默认主力模型
    retry_attempt: int = 0          # 当前重试次数
    reactive_compact_used: bool = False # 是否已触发过应急上下文压缩

```

### ② 故障诊断器与自愈策略分发 (`handle_error`)

这是核心的策略中枢，负责解析错误类型，修改状态机，决定是“继续重试”还是“彻底放弃”：

```python
MAX_RETRY_LIMIT = 3

def handle_error(error_type: str, state: RecoveryState, messages: list) -> bool:
    """
    分析故障并动态自愈状态。
    返回 True 代表成功制定了修复策略，允许重试；返回 False 代表无法自愈，必须报错。
    """
    if state.retry_attempt >= MAX_RETRY_LIMIT:
        print(f"\n⛔ [ERROR] Recovery failed: Exceeded max retry limit ({MAX_RETRY_LIMIT})")
        return False
        
    state.retry_attempt += 1
    print(f"\n[⚠️ RECOVERY] Attempt {state.retry_attempt} for error: {error_type}")
    
    # 路径 1：处理 max_tokens 截断错误
    if error_type == "max_tokens_exceeded":
        # 动态扩大 8 倍输出上限，给模型提供充足的施展空间
        state.max_tokens = 64000 
        print(f"   -> Scaling up max_tokens to {state.max_tokens}")
        return True
        
    # 路径 2：处理上下文超长错误
    elif error_type == "prompt_too_long":
        if state.reactive_compact_used:
            return False # 如果已经压缩过一次还是超长，说明任务规模过大，放弃自愈
        print("   -> Context window full. Triggering emergency reactive compaction...")
        # 强行调用 s08 的压缩机制，对历史消息做有损脱水
        messages[:] = reactive_compact(messages) 
        state.reactive_compact_used = True
        return True
        
    # 路径 3：处理 429 频次限制错误
    elif error_type == "rate_limited_429":
        # 降级切换到备用轻量模型（如 Haiku），绕开主力模型的额度限制
        state.current_model = "claude-3-5-haiku"
        print(f"   -> Rate limited. Degrading model to {state.current_model}")
        time.sleep(2 ** state.retry_attempt) # 指数退避延迟
        return True
        
    return False # 未知错误，无法自愈

```

### ③ 具备异常自愈能力的智能体主循环 (`agent_loop_with_recovery`)

将异常拦截与状态机回滚无缝嵌入到模型调用最外层，实现业务的抗脆弱性：

```python
def agent_loop_with_recovery(messages):
    # 初始化局部自愈状态机
    state = RecoveryState()
    
    while True:
        try:
            # 使用当前状态机中指定的动态模型和动态 max_tokens 参数发起调用
            response = client.messages.create(
                model=state.current_model,
                max_tokens=state.max_tokens,
                messages=messages,
                tools=TOOLS
            )
            
            # 显式检查模型自身的退出原因是否是被中途截断 (Mid-answer cutoff)
            if response.stop_reason == "max_tokens":
                raise Exception("max_tokens_exceeded")
                
            # 执行成功，重置重试计数器（证明当前参数工作良好）
            state.retry_attempt = 0 
            
            # ... 正常的工具分发与执行逻辑 (s02) ...
            messages.append({"role": "assistant", "content": response.content})
            if response.stop_reason != "tool_use":
                break # 任务体面收尾
                
        except Exception as e:
            # 捕获异常，将其送入 Failure Inbox
            err_msg = str(e)
            error_type = "unknown"
            if "max_tokens_exceeded" in err_msg: error_type = "max_tokens_exceeded"
            elif "context_length_exceeded" in err_msg: error_type = "prompt_too_long"
            elif "429" in err_msg or "rate_limit" in err_msg: error_type = "rate_limited_429"
            
            # 调度自愈策略
            should_retry = handle_error(error_type, state, messages)
            if should_retry:
                continue # 命中自愈策略，带上改写后的参数直接重新发起这一轮循环
            else:
                raise e # 无法修复，抛出崩溃

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 **Claude Code** 工业级生产级源码（如 `src/services/recovery/` 下的 `FailureInbox.ts`、`BackoffStrategy.ts`）中，错误恢复机制是一套防御极其严密的工程防线：

* **自适应滑动窗口退避 (Adaptive Jitter Backoff)：** 教学版只使用了死板的 `time.sleep(2  attempt)`。生产级源码采用的是带随机抖动的自适应指数退避算法（Full Jitter Backoff）。它不仅计算当前的失败次数，还会实时观测当前系统 TTY 的网络吞吐延迟、排队积压情况（Queue Congestion），防止成百上千个并发的子 Agent 在同一时间抱团发起重试，从而彻底避免引发对企业网关的二次瞬间“尖峰踩踏”击穿。
* **增量追加续写机制 (`stop_reason: "max_tokens"` 的高级处理)：** 教学版在遇到模型因 `max_tokens` 被截断时，采用的方法是简单的抹掉上一轮并用大参数完全“重跑一次”。但这在长对话中会带来极其昂贵的 Token 浪费。真实源码采用的是“断点续接（Append Continuation）”技术：当大模型输出到一半断掉时，系统会默默在 messages 历史里追加一条带有特殊指示的空 `user` 占位消息（如 `"Continue exactly from where you left off"`），强行让模型在下一轮以增量形式拼合输出，节省了巨大的算力成本。
* **原子级别的文件回滚沙箱 (Transactional Worktree Recovery)：** 生产级源码在执行复杂的重构任务时，如果遇到崩溃或硬故障（即使自愈失败），为了不破坏用户的本地代码库，系统底层会联动 `git` 等版本控制钩子，触发 **Worktree Isolation**。当判定自愈宣告失败准备退出前，系统会自动启动 `abortAndRollback()`，一键抹除过去所有脏写入的文件碎片，确保给人类开发者留下的始终是一个干净、无污染的物理工作区。
