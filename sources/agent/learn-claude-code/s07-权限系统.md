> _模型可以提出行动建议，但真正执行之前，必须先过安全关。_

## 这一章的核心目标

到了 `s06`，agent 已经能读文件、改文件、跑命令、做规划、压缩上下文。问题也随之出现了：

* 模型可能会写错文件
* 模型可能会执行危险命令
* 模型可能会在不该动手的时候动手

所以从这一章开始，系统需要一条新的管道：

**"意图"不能直接变成"执行"，中间必须经过权限检查。**

## 先解释几个名词

### 什么是权限系统

权限系统不是"有没有权限"这样一个布尔值。它更像一条管道，用来回答：

1. 这次调用要不要直接拒绝？
2. 能不能自动放行？
3. 剩下的要不要问用户？

### 什么是权限模式

权限模式是系统当前的总体风格。例如：

* 谨慎一点：大多数操作都问用户
* 保守一点：只允许读，不允许写
* 流畅一点：简单安全的操作自动放行

### 什么是规则

```
{
  "tool": "bash",
  "content": "sudo *",
  "behavior": "deny",
}
```

## 最小权限系统应该长什么样

```
tool_call
|
v
1. deny rules -> 命中了就拒绝
|
v
2. mode check -> 根据当前模式决定
|
v
3. allow rules -> 命中了就放行
|
v
4. ask user -> 剩下的交给用户确认
```

### 为什么顺序是这样

1. **deny 先看**：有些东西不应该交给"模式"去决定（明显危险的命令、越界的路径）
2. **mode 第二**：模式决定当前会话大方向（如 `plan` 模式更保守）
3. **allow 第三**：安全、重复、常见的操作可以直接过
4. **ask 最后**：灰区交给用户

## 推荐先实现的 3 种模式

| 模式 | 含义 | 适合什么场景 |
| --- | --- | --- |
| `default` | 未命中规则时问用户 | 日常交互 |
| `plan` | 只允许读，不允许写 | 计划、审查、分析 |
| `auto` | 简单安全操作自动过，危险操作再问 | 高流畅度探索 |

## 关键数据结构

### 1. 权限规则

```
PermissionRule = {
    "tool": str,
    "behavior": "allow" | "deny" | "ask",
    "path": str | None,
    "content": str | None,
}
```

### 2. 权限模式

```
mode = "default" | "plan" | "auto"
```

### 3. 权限决策结果

```
{
    "behavior": "allow" | "deny" | "ask",
    "reason": "why this decision was made"
}
```

## 最小实现

```python
def check_permission(tool_name: str, tool_input: dict) -> dict:
    # 1. deny rules
    for rule in deny_rules:
        if matches(rule, tool_name, tool_input):
            return {"behavior": "deny", "reason": "matched deny rule"}
    # 2. mode
    if mode == "plan" and tool_name in WRITE_TOOLS:
        return {"behavior": "deny", "reason": "plan mode blocks writes"}
    if mode == "auto" and tool_name in READ_ONLY_TOOLS:
        return {"behavior": "allow", "reason": "auto mode allows reads"}
    # 3. allow rules
    for rule in allow_rules:
        if matches(rule, tool_name, tool_input):
            return {"behavior": "allow", "reason": "matched allow rule"}
    # 4. fallback
    return {"behavior": "ask", "reason": "needs confirmation"}
```

然后在执行工具前接进去：

```python
decision = perms.check(tool_name, tool_input)
if decision["behavior"] == "deny":
    return f"Permission denied: {decision['reason']}"
if decision["behavior"] == "ask":
    ok = ask_user(...)
    if not ok:
        return "Permission denied by user"
return handler(**tool_input)
```

## Bash 为什么值得单独讲

所有工具里，`bash` 通常最危险。因为 `read_file` 只能读文件，`write_file` 只能写文件，但 `bash` 几乎能做任何事。

建议至少先挡住这些明显危险点：`sudo`、`rm -rf`、命令替换、可疑重定向、shell 元字符拼接。

核心思想：**bash 不是普通文本，而是可执行动作描述。**

## 一句话记住

**权限系统不是为了让 agent 更笨，而是为了让 agent 的行动先经过一道可靠的安全判断。**

# 新版 Permission

根据 [Learn Claude Code](https://learn.shareai.run/zh/) 课程第 **[s03 Permission（权限门控）](https://learn.shareai.run/zh/s03/)** 章节的正文，其核心概念、工作原理与教学版代码实现提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 在此前的架构（s02）中，智能体虽然拥有了读写文件和 Bash 工具，但它在执行时处于“完全不设防”的状态。如果用户对模型说“帮我清理一下项目”，模型可能会在内部调用 `bash` 并执行高危命令如 `rm -rf /`。安全不能寄希望于模型的自觉（Trusting the model），而必须依赖运行时的代码框架。
* **解决方案：** **“工具执行前先做权限判断”**。在整个 Agent Loop 的工具执行层前插入一个权限路由管线 `check_permission()`。大模型只负责“提议（Propose）”要使用的工具，而由 Harness 运行时系统来决定这个请求是**直接放行（Allow）、软询问用户（Ask）还是硬拒绝（Deny）**。

---

## 2. 三道权限闸门工作原理

系统通过三道层层递进的闸门对工具请求进行过滤，顺序固定（硬拒绝优先，软询问次之，均未命中则放行）：

```
模型提议工具请求 (Tool Request)
       │
       ▼ [闸门 1: 拒绝列表] ─── 命中 ───► ⛔ 直接硬拒绝 (Deny)
       │ 未命中
       ▼ [闸门 2: 规则匹配] ─── 命中 ───► [闸门 3: 用户审批] ─── 拒绝 ───► ⛔ 拦截
       │ 未命中                                       └─── 允许 ───┐
       ▼                                                           ▼
🔓 自动直接放行 (Allow) ──────────────────────────────────────────► 执行工具

```

---

## 3. 核心功能代码实现（180 LOC 教学版内核）

### ① 闸门 1：硬拒绝黑名单 (`check_deny_list`)

用于拦截永远禁止执行的高危系统命令（如根目录删除、提权等）：

```python
# 教学版硬拒绝模式串
DENY_LIST = [
    "rm -rf /", "sudo", "shutdown", "reboot", "mkfs", "dd if=", "> /dev/sda"
]

def check_deny_list(command: str) -> str | None:
    for pattern in DENY_LIST:
        if pattern in command:
            return f"Blocked: '{pattern}' is on the deny list"
    return None

```

### ② 闸门 2：条件规则匹配 (`check_rules`)

根据工具类型和运行时参数动态评估风险。例如：禁止写工作区（WORKDIR）外部的文件、拦截潜在的破坏性 Bash 命令：

```python
from pathlib import Path
WORKDIR = Path(".").resolve()

PERMISSION_RULES = [
    {
        "tools": ["write_file", "edit_file"],
        # 拦截路径穿越（..），防止写到项目工作区外面
        "check": lambda args: not (WORKDIR / args.get("path", "")).resolve().is_relative_to(WORKDIR),
        "message": "Writing outside workspace"
    },
    {
        "tools": ["bash"],
        # 拦截带有破坏性倾向的本地命令
        "check": lambda args: any(kw in args.get("command", "") for kw in ["rm ", "> /etc/", "chmod 777"]),
        "message": "Potentially destructive command"
    }
]

def check_rules(tool_name: str, args: dict) -> str | None:
    for rule in PERMISSION_RULES:
        if tool_name in rule["tools"] and rule["check"](args):
            return rule["message"]
    return None

```

### ③ 闸门 3：交互式用户审批 (`ask_user`)

当闸门 2 命中风险时，暂停智能体循环，将选择权交还给终端人类用户：

```python
def ask_user(tool_name: str, args: dict, reason: str) -> str:
    print(f"\n⚠ {reason}")
    print(f"   Tool: {tool_name} ({args})")
    choice = input("   Allow? [y/N] ").strip().lower()
    return "allow" if choice in ("y", "yes") else "deny"

```

### ④ 三闸串联与 Agent Loop 嵌入 (`check_permission`)

将权限验证作为中间件拦截器，嵌入到原有的工具分发执行循环中：

```python
def check_permission(block) -> bool:
    # 1. 闸门 1: 拦截硬拒绝
    if block.name == "bash":
        reason = check_deny_list(block.input.get("command", ""))
        if reason:
            print(f"\n⛔ {reason}")
            return False  # 直接拦截
            
    # 2. 闸门 2 + 3: 规则匹配与用户交互审批
    reason = check_rules(block.name, block.input)
    if reason:
        decision = ask_user(block.name, block.input, reason)
        if decision == "deny":
            return False  # 用户说不，拦截
            
    return True  # 统统没命中，安全放行

# 嵌入到 s02 原有的智能体循环体内
def execute_tools_with_gate(response_content):
    results = []
    for block in response_content:
        if block.type == "tool_use":
            
            # --- 【核心新增：执行前拦截】 ---
            if not check_permission(block):
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": "Permission denied by user or system policy."
                })
                continue  # 跳过执行，直接报错喂回给大模型
                
            # --- 【原有执行逻辑】 ---
            handler = TOOL_HANDLERS[block.name]
            output = handler(**block.input)
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
    return results

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 [Claude Code 生产级源码](https://learn.shareai.run/zh/s03/) 中，权限门控被设计为一套极其精密的安全护栏体系：

* **PermissionResult 的四种行为：** 教学版只有 Allow/Ask/Deny 三种状态。而 CC 源码（`types/permissions.ts`）包含第四种状态 **`passthrough`**（透传）。它意味着当前特定的工具或局部检查不表态，交由系统的全局底层安全管线做最终裁决。
* **严密的 6 阶段验证管线：** 在源码的 `checkPermissionsAndCallTool()` 中，一个工具请求在被最终执行前需要经过 6 道防线：
1. **Zod Schema 验证**（严格检查参数类型是否合法，防注入）。
2. **`validateInput()`**（工具级语义验证）。
3. **参数字段补全**。
4. **[PreToolUse Hooks](https://learn.shareai.run/zh/s04/) 拦截**（外部钩子拥有最高裁决权）。
5. **协调钩子与管线决策**。
6. **`hasPermissionsToUseToolInner()`**（多层级规则合并检查、运行安全检查分级，若违规则强制变更为 `ask` 且不可被配置绕过）。


* **配置权重的 8 大来源合并：** 生产级没有单一的硬编码 `DENY_LIST`。它的权限规则来自 8 个不同的通道（如用户全局配置 `~/.claude/settings.json`、项目本地配置、企业合规 Policy 策略、CLI 命令行参数 `--deniedTools`、当前会话临时授权等）。多个来源通过特定的优先级权重（从低到高：user < project < local < flag < policy）进行原子合并与覆盖。
* **YoloClassifier（大模型自动安全审批）：** 在 CLI 的 `auto` 自动模式下，系统不会愚蠢地频繁弹窗打扰人类。CC 引入了 `classifyYoloAction` 机制。它会把当前的工具调用连同近几轮的会话上下文，悄悄发送给一个低成本的轻量分类器 LLM 来判断当前意图是否安全。只有当分类器评估有风险，或分类器连续拒绝次数超限时，才会降级回退到人工弹窗审批。
* **[权限冒泡 (Permission Bubbling)](https://learn.shareai.run/zh/s15/)：** 当使用 `AgentTool` 派生出后台并行工作的子 Agent 时，子智能体的 `permissionMode` 会被硬编码强制设为 `'bubble'`。子 Agent 无法直接与人类交互，一旦它的工具触发了 `ask` 规则，该弹窗请求会顺着调用链一路“冒泡”到人类正在凝视的主终端 CLI 上，由人类统一审批后，再将允许/拒绝信号反向注入回深层子 Agent 空间中。
