> _"大任务拆小, 每个小任务干净的上下文"_ -- 子智能体用独立 messages[], 不污染主对话。

## 问题

智能体工作越久, messages 数组越胖。每次读文件、跑命令的输出都永久留在上下文里。

"这个项目用什么测试框架?" 可能要读 5 个文件, 但父智能体只需要一个词: "pytest。"

## 解决方案

```
Parent agent                     Subagent
+------------------+         +------------------+
| messages=[...]   |         | messages=[]      | <-- fresh
|                  | dispatch|                  |
| tool: task       | ------->| while tool_use:  |
| prompt="..."     |         |   call tools     |
|                  | summary |   append results |
| result = "..."   | <-------| return last text |
+------------------+         +------------------+
Parent context stays clean. Subagent context is discarded.
```

## 工作原理

1. 父智能体有一个 `task` 工具。子智能体拥有除 `task` 外的所有基础工具 (禁止递归生成)。

```python
PARENT_TOOLS = CHILD_TOOLS + [
    {
        "name": "task",
        "description": "Spawn a subagent with fresh context.",
        "input_schema": {
            "type": "object",
            "properties": {"prompt": {"type": "string"}},
            "required": ["prompt"],
        },
    },
]
```

2. 子智能体以 `messages=[]` 启动, 运行自己的循环。只有最终文本返回给父智能体。

```python
def run_subagent(prompt: str) -> str:
    sub_messages = [{"role": "user", "content": prompt}]
    for _ in range(30):  # safety limit
        response = client.messages.create(
            model=MODEL, system=SUBAGENT_SYSTEM,
            messages=sub_messages,
            tools=CHILD_TOOLS, max_tokens=8000,
        )
        sub_messages.append({
            "role": "assistant",
            "content": response.content})
        if response.stop_reason != "tool_use":
            break
        results = []
        for block in response.content:
            if block.type == "tool_use":
                handler = TOOL_HANDLERS.get(block.name)
                output = handler(**block.input)
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": str(output)[:50000]})
        sub_messages.append({
            "role": "user", "content": results})
    return "".join(
        b.text for b in response.content if hasattr(b, "text")
    ) or "(no summary)"
```

子智能体可能跑了 30+ 次工具调用, 但整个消息历史直接丢弃。父智能体收到的只是一段摘要文本, 作为普通 `tool_result` 返回。

| --- | --- | --- |

# 新版 SubAgent

根据 [Learn Claude Code](https://learn.shareai.run/zh/) 课程第 **s06 Subagent（子智能体与上下文隔离）** 章节的正文，其核心概念、工作原理与教学版代码实现提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 智能体在处理复杂的 debug、重构或长链路分析时，为了追踪调用链需要读取大量的文件，并伴随数十轮的对话。这会导致当前的 `messages` 历史极速膨胀（例如超过 100 条）。这些繁杂的“中间过程文本”会大量占据上下文窗口，严重稀释系统提示词（System Prompt）的约束力，导致 Agent 变得“健忘”，甚至忘记了最初的核心目标。
* **解决思路：** **“大任务拆小，开新终端干活”**。类似于人类程序员在排查复杂问题时，会“开一个新的终端窗口”专门去跑命令和追踪代码，追踪完后关闭该窗口，只把核心结论记入笔记中。通过引入 `task` 工具，系统在面临复杂子任务时会动态 spawn（衍生）一个全新的**子智能体（Subagent）**，赋予它一个**完全干净、独立的 `messages[]**`。子任务执行完后，主会话只接收其文本摘要结论，中间过程垃圾全部被丢弃，确保主对话上下文的绝对纯净。

---

## 2. 核心工作原理

```
[Parent Agent] messages[] (主对话：保持轻量)
       │
       ▼ 调用 task 工具
[Spawn Subagent] ───► 分配全新 messages[] ───► 独立运行最多 30 轮 Loop
                                                     │
                                                     ▼ 任务完成/退出
[Parent Agent] ◄─── 仅接收最后的文本结论摘要 ◄────────┘

```

1. **上下文彻底隔离：** 子智能体拥有全新的消息历史，它的所有漫游、报错和试错过程都不会进入主 Agent 历史。
2. **工具降级（禁止递归防护）：** 为防止系统由于逻辑陷入无休止的“套娃”死循环，子智能体虽然拥有基础读写工具（`bash`, `read_file` 等），但其工具列表中**不包含 `task` 工具**，从而在底层绝育了递归衍生。
3. **权限不隔离（Permission Bubbling）：** 上下文的隔离不代表安全性的跳过。子智能体在调用高危写工具时，其底层的 `PreToolUse` Hook 依然生效，并将权限审批请求向上“冒泡”到人类交互的主终端。

---

## 3. 核心功能代码实现

### ① 主 Agent 工具 Schema 定义（注册 `task`）

主 Agent 的工具池中新增 `task` 委派工具，用来接收子任务的描述：

```python
TOOLS = [
    # ... 基础文件读写与规划工具 (bash, read_file, write_file, edit_file, glob, todo_write) ...
    {
        "name": "task",
        "description": "Launch a subagent to handle a complex subtask. Returns only the final conclusion.",
        "input_schema": {
            "type": "object",
            "properties": {
                "description": {"type": "string", "description": "Detailed prompt for the subagent to execute."}
            },
            "required": ["description"]
        }
    },
]

```

### ② 子智能体生命周期内核实现 (`spawn_subagent`)

该函数作为 `task` 工具的处理器，核心在于开辟独立历史，并在退出前精炼提取最后一轮的文本：

```python
# 子智能体专用的精简工具池：绝对禁止包含 "task" 本身，防止无限递归
SUB_TOOLS = [
    {"name": "bash", "description": "Run shell commands.", "input_schema": {...}},
    {"name": "read_file", "description": "Read file contents.", "input_schema": {...}},
    {"name": "write_file", "description": "Write to file.", "input_schema": {...}},
    {"name": "edit_file", "description": "Edit file chunks.", "input_schema": {...}},
    {"name": "glob", "description": "Find files.", "input_schema": {...}},
]

SUB_SYSTEM = "You are a subagent. Focus on the assigned subtask. Complete it directly and do not attempt to delegate."

def spawn_subagent(description: str) -> str:
    print(f"\n[Subagent spawned] Task: {description}")
    
    # 核心逻辑 ①：开辟完全干净、隔离的全新的消息数组，不污染主线程
    sub_messages = [{"role": "user", "content": description}]
    
    # 核心逻辑 ②：严格的 30 轮安全硬限制，防止子进程死循环耗尽 Token
    for _ in range(30):
        response = client.messages.create(
            model=MODEL,
            system=SUB_SYSTEM,
            messages=sub_messages,
            tools=SUB_TOOLS,
            max_tokens=4000
        )
        sub_messages.append({"role": "assistant", "content": response.content})
        
        if response.stop_reason != "tool_use":
            break # 任务阶段性搞定，跳出工具循环
            
        # 执行子 Agent 的工具流分发
        results = []
        for block in response.content:
            if block.type == "tool_use":
                # 安全策略不跳过：子 Agent 调用写工具仍通过外部钩子进行审计/拦截
                blocked = trigger_hooks("PreToolUse", block)
                if blocked:
                    results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(blocked)})
                    continue
                    
                # 查子工具表并执行（SUB_HANDLERS 映射不含 task）
                handler = SUB_HANDLERS.get(block.name)
                output = handler(**block.input) if handler else "Unknown tool"
                
                trigger_hooks("PostToolUse", block, output)
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
                
        sub_messages.append({"role": "user", "content": results})
        
    print("[Subagent done]")
    
    # 核心逻辑 ③：只回传最后的纯文本结论。中间繁杂的工具返回结果和消息历史在这里随着函数生命周期结束直接被 GC 销毁
    return extract_text(sub_messages[-1]["content"])

# 绑定分发到主工具映射表
TOOL_HANDLERS["task"] = spawn_subagent

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 [Claude Code 工业级源码](https://learn.shareai.run/zh/s06/)（如 `AgentTool.tsx`, `forkSubagent.ts`, `forkedAgent.ts`）中，Subagent 的设计并不是一种单一的清空历史，而是三种复杂的生产级执行路径并存：

* **Fork 模式与 Prompt 缓存共享 (`buildForkedMessages`)**：教学版只讲了全新 `messages[]` 的清空模式（对应源码中的 Normal 路径）。但 CC 为了极致地降低 API 延迟和成本，设计了 **Fork 模式**（`forkSubagent.ts`）。它不会将上下文完全抹去，而是通过 `buildForkedMessages()` 构造一个对大模型极度友好的“缓存友好前缀（Cache-Friendly Prefix）”，将父会话的 system prompt、tools、thinking 机制字节级一致地同步过去。这能**完美触发 Anthropic API 的 Prompt Cache 命中**，无需为子 Agent 重新计算高达数万 Token 的基础底座。
* **精确的上下文克隆粒度 (`createSubagentContext`)**：真实的子进程与父进程并不是绝对冷血隔离。在 `forkedAgent.ts` 中，子智能体会**全量克隆父智能体的文件读取状态（`readFileState`）**。这意味着父 Agent 如果已经在大文件里找到了 Bug 所在的行数，子 Agent 启动时直接就能感知到这个状态，避免了子 Agent 重新去调用 `glob` 或 `read_file` 导致性能二次损耗。
* **异步后台路径支持 (`run_in_background`)**：教学版属于同步阻塞模型（父 Agent 一直在 await 等待子 Agent 返回）。在实际 CC 源码中，若传入 `run_in_background: true`（或触发系统的自动后台升级机制），子 Agent 会在后台的一个独立 Daemon 管道中被异步唤醒。系统会先向父 Agent 立即返回一条 `{ status: 'async_launched' }` 结构，父 Agent 此时可以继续去干别的活，子 Agent 跑完后再通过系统通知（Notification Event）将结果插队喂给主会话。
