> _"加一个工具, 只加一个 handler"_ -- 循环不用动, 新工具注册进 dispatch map 就行。

## 问题

只有 `bash` 时, 所有操作都走 shell。`cat` 截断不可预测, `sed` 遇到特殊字符就崩, 每次 bash 调用都是不受约束的安全面。专用工具 (`read_file`, `write_file`) 可以在工具层面做路径沙箱。

关键洞察: 加工具不需要改循环。

## 解决方案

```
+--------+     +-------+     +------------------+
| User   | --> | LLM   | --> | Tool Dispatch    |
| prompt |     |       |     | {                |
+--------+     +---+---+     |   bash: run_bash |
   ^               |         |   read: run_read |
   |               |         |   write: run_wr  |
   +-----------+   |         |   edit: run_edit |
   tool_result |   |         | }                |
               +---+         +------------------+
```

The dispatch map is a dict: `{tool_name: handler_function}`. One lookup replaces any if/elif chain.

## 工作原理

1. 每个工具有一个处理函数。路径沙箱防止逃逸工作区。

```python
def safe_path(p: str) -> Path:
    path = (WORKDIR / p).resolve()
    if not path.is_relative_to(WORKDIR):
        raise ValueError(f"Path escapes workspace: {p}")
    return path

def run_read(path: str, limit: int = None) -> str:
    text = safe_path(path).read_text()
    lines = text.splitlines()
    if limit and limit < len(lines):
        lines = lines[:limit]
    return "\n".join(lines)[:50000]
```

2. dispatch map 将工具名映射到处理函数。

```python
TOOL_HANDLERS = {
    "bash": lambda **kw: run_bash(kw["command"]),
    "read_file": lambda **kw: run_read(kw["path"], kw.get("limit")),
    "write_file": lambda **kw: run_write(kw["path"], kw["content"]),
    "edit_file": lambda **kw: run_edit(kw["path"], kw["old_text"], kw["new_text"]),
}
```

3. 循环中按名称查找处理函数。循环体本身与 s01 完全一致。

```python
for block in response.content:
    if block.type == "tool_use":
        handler = TOOL_HANDLERS.get(block.name)
        output = handler(**block.input) if handler \
            else f"Unknown tool: {block.name}"
        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": output,
        })
```

加工具 = 加 handler + 加 schema。循环永远不变。

# 新版 TOOL USE

根据 [Learn Claude Code](https://learn.shareai.run/zh/s02/) 课程正文，**Tool Use（工具与执行）** 的核心概念、设计架构与教学版核心代码提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 在最基础的智能体循环（如 s01 阶段）中，系统往往只硬编码了一个万能的 `bash` 工具。模型为了满足“读取文件”或“修改文件”的需求，必须在内部将意图“翻译”为 `cat`、`sed` 或 `echo "..." > file` 等 Linux 命令。这不仅极大地**浪费 Token**，还容易因为 shell 转义或语法拼错导致循环崩溃。
* **解决思路：** **加工具，不加代码行数**。通过引入 **Tool Dispatch Map（工具分发表）** 架构，将工具的“定义（Schema）”与“具体实现（Handler）”彻底解耦。整个 Agent Loop 的底层 `while True` 架构一行都不需要改动，新工具只需注册进分发表即可无限扩展。

---

## 2. 核心架构：工具分发表 (Tool Dispatch Map)

整个框架的升级主要体现在工具执行层，核心逻辑从硬编码调用 `run_bash()` 变为了**查表分发**：

```
LLM 返回 tool_use 块 (例如 name: "read_file")
       │
       ▼
查表定位：handler = TOOL_HANDLERS["read_file"]
       │
       ▼
动态执行：handler(**block.input)

```

---

### ② 工具的具体实现函数 (Handlers)

```python
import glob as g
from pathlib import Path

# 路径安全检查伪函数（防止越界越权）
def safe_path(path):
    p = Path(path).resolve()
    # 实际生产中会校验 p 是否在 WORKDIR 内
    return p

def run_bash(command):
    # 执行 shell 命令的具体逻辑
    import subprocess
    res = subprocess.run(command, shell=True, capture_output=True, text=True)
    return res.stdout or res.stderr

def run_read(path, limit=None):
    lines = safe_path(path).read_text().splitlines()
    if limit:
        lines = lines[:limit]
    return "\n".join(lines)

def run_write(path, content):
    safe_path(path).write_text(content)
    return f"Wrote {len(content)} bytes to {path}"

def run_edit(path, old_text, new_text):
    text = safe_path(path).read_text()
    if old_text not in text:
        return "Error: text not found"
    safe_path(path).write_text(text.replace(old_text, new_text, 1))
    return f"Edited {path}"

def run_glob(pattern):
    return "\n".join(g.glob(pattern, recursive=True))

```

### ③ 工具注册表与分发循环（Loop）

```python
# 核心分发映射表：工具名 -> 函数指针
TOOL_HANDLERS = {
    "bash":       run_bash,
    "read_file":  run_read,
    "write_file": run_write,
    "edit_file":  run_edit,
    "glob":       run_glob,
}

# 智能体循环体内执行工具的部分
def execute_tools(response_content):
    results = []
    for block in response_content:
        if block.type == "tool_use":
            # 1. 查表分发（核心变化就在这一行！）
            handler = TOOL_HANDLERS.get(block.name)
            if not handler:
                output = f"Error: Tool {block.name} not found"
            else:
                try:
                    # 2. 解包模型输入的参数并动态调用
                    output = handler(**block.input)
                except Exception as e:
                    output = f"Execution Error: {str(e)}"
            
            # 3. 组装结果以便喂回给模型
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            })
    return results

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 Claude Code（CC）工业级工程实现中，机制要严密得多：

* **并发分区算法 (`partitionToolCalls`)**：教学版是遍历 `response.content` **逐个串行**执行工具。而 CC 会在底层评估工具的并发安全性（`isConcurrencySafe`）。它会将一连串工具切分成连续的 Batch：**只读工具（如 `read_file`, `glob`, `ls`）会被归入同一个 Batch 进行并行异步并发执行**，一旦遇到写工具（如 `bash rm`），则切出新 Batch 进行串行阻塞，在性能与安全之间取得了完美平衡。
* **流式执行 (`StreamingToolExecutor`)**：CC 的工具执行不需要等待大模型把整句话全部说完。当模型流式输出（Streaming）到一段完整的 `tool_use` JSON 块时，后台的执行器就已经悄悄启动去读写文件了，大幅降低了用户的体感延迟。
* **大结果防死循环落盘**：CC 规定了工具返回结果的最大字符数（`maxResultSizeChars`），超限就自动写成本地临时文件，只给模型看预览。但为了防止死循环，**`read_file` 工具的落盘阈值被硬编码设为了 `Infinity**`。否则，一旦读大文件触发落盘，模型下次去读落盘的临时文件又会触发二次落盘，导致逻辑死循环。
