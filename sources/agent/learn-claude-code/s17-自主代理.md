> _一个团队真正开始"自己运转"，不是因为 agent 数量变多，而是因为空闲的队友会自己去找下一份工作。_

## 这一章要解决什么问题

到了 `s16`，团队已经有持久队友、邮箱、协议、任务板。但还有一个明显瓶颈：

**很多事情仍然要靠 lead 手动分配。**

所以这一章要解决的核心问题是：

**让空闲队友自己扫描任务板，找到可做的任务并认领。**

## 最小心智模型

```
WORK
|
| 当前轮工作做完，或者主动进入 idle
v
IDLE
|
+-- 看邮箱，有新消息 -> 回到 WORK
|
+-- 看任务板，有 ready task -> 认领 -> 回到 WORK
|
+-- 长时间什么都没有 -> shutdown
```

**空闲时，按规则检查两类新输入：邮箱和任务板。**

# 新版自主代理

根据 [Learn Claude Code](https://learn.shareai.run/zh/s17/) 课程第 **s17 Autonomous Agents（自治智能体）** 章节的正文，其核心概念、工作原理与教学版代码实现提炼如下：

---

## 1. 核心痛点与解决思路

* **痛点：** 在此前的 [Team Protocols](https://learn.shareai.run/zh/s16/) 阶段，队友已经具备了通信与体面关机的能力。然而，所有的任务都需要主导者（Lead）手动进行 `assign` 分配。如果看板上有 10 个任务，Lead 就必须手动分配 10 次，这在大型工程中完全无法扩展。
* **解决思路：** **“自己看板，自己认领”**。不再依赖中央调度员（Central Dispatcher），而是建立一个共享的任务看板机制。队友在空闲时（Idle）会自发、定期地去轮询扫描任务看板，发现满足依赖条件且无人认领的任务后，自行调用工具进行 `claim`（认领）并切换到工作状态。

---

## 2. 核心工作原理

引入自治后，队友的生命周期从“工作-退出”的传统两阶段，演进为 **WORK → IDLE → SHUTDOWN** 三阶段循环：

| 阶段 | 行为 | 退出条件 |
| --- | --- | --- |
| **WORK** | 消费收件箱 $\rightarrow$ 投喂 LLM $\rightarrow$ 执行工具循环 | 模型返回 `stop_reason != "tool_use"` |
| **IDLE** | 挂起，每 5 秒轮询一次收件箱 + 扫描共享任务板 | 累计 60 秒无新任务则触发超时 |
| **SHUTDOWN** | 发送工作总结（Summary）给 Lead，然后优雅退出线程 | — |

---

## 3. 核心功能代码实现

### ① 队友外层生命周期管理循环

之前的队友执行完 10 轮工作就直接退出，现在使用外层 `while True` 维系 WORK 与 IDLE 的交替流转：

```python
# 队友外层核心状态机循环
while True:
    # --- 【WORK 阶段】 ---
    # 内层循环：处理当前认领的任务（最多 10 轮 LLM 调用防止死循环）
    for _ in range(10):
        # 检查收件箱、处理协议消息、调用 LLM、执行工具
        ...
        if response.stop_reason != "tool_use":
            break  # 任务阶段性做完，跳出内层循环
            
    # --- 【IDLE 阶段】 ---
    # 进入空闲轮询状态，等待新消息或主动找活
    idle_result = idle_poll(name, messages, name, role)
    
    if idle_result == "shutdown":
        break  # 收到 Lead 的强行关机指令，退出
    if idle_result == "timeout":
        break  # 60秒内看板没活、也没人理我，超时自动关机

# --- 【SHUTDOWN 阶段】 ---
# 退出前向 Lead 统一汇报最终工作总结
BUS.send(name, "lead", summary, "result")

```

### ② 空闲双源轮询器 (`idle_poll`)

在空闲期间，队友优先检查**收件箱（指令优先级最高）**，其次扫描**任务看板（主动找活）**：

```python
import time

IDLE_POLL_INTERVAL = 5  # 每 5 秒轮询一次
IDLE_TIMEOUT = 60       # 累计 60 秒超时

def idle_poll(agent_name, messages, name, role) -> str:
    """返回 'work'、'shutdown' 或 'timeout'"""
    
    # 60秒内一共轮询 12 次
    for _ in range(IDLE_TIMEOUT // IDLE_POLL_INTERVAL):
        time.sleep(IDLE_POLL_INTERVAL)
        
        # 核心逻辑 ①：优先检查收件箱（防止关机等紧急协议消息被饿死）
        inbox = BUS.read_inbox(agent_name)
        if inbox:
            for msg in inbox:
                if msg.get("type") == "shutdown_request":
                    # 收到关机指令立刻回复并指示外层退出
                    return "shutdown"
            
            # 如果是人类/Lead发来的普通文本任务，注入上下文并立刻激活进入 WORK 阶段
            messages.append({"role": "user", "content": "[New Message from Lead]..."})
            return "work"
            
        # 核心逻辑 ②：如果没有紧急消息，扫描任务看板主动找活
        unclaimed = scan_unclaimed_tasks()
        if unclaimed:
            task = unclaimed[0]  # 教学版默认取排序后的第一个任务
            result = claim_task(task["id"], agent_name)
            
            # 只有认领成功才接活，防止并发冲突
            if "Claimed" in result:
                messages.append({
                    "role": "user", 
                    "content": f"<task>You claimed task {task['id']}: {task['subject']}. Start working.</task>"
                })
                return "work"  # 成功抢到活，回到 WORK 阶段
                
    return "timeout"  # 60秒到了都没活干，通知外层体面收尾

```

### ③ 看板扫描与前置依赖检查 (`scan_unclaimed_tasks`)

智能体不能瞎接活，认领必须满足三个条件：任务处于 `pending`、没有 `owner`、且它所依赖的前置任务（`blockedBy`）已经全部处于完成状态：

```python
import json
from pathlib import Path

TASKS_DIR = Path(".tasks")

def scan_unclaimed_tasks() -> list[dict]:
    unclaimed = []
    # 遍历本地任务 JSON 文件
    for f in sorted(TASKS_DIR.glob("task_*.json")):
        task = json.loads(f.read_text())
        
        # 校验：状态为 pending + 没有主客 + 依赖树已经解锁 (can_start)
        if (task.get("status") == "pending" and 
            not task.get("owner") and 
            can_start(task["id"])):
            unclaimed.append(task)
            
    return unclaimed

def can_start(task_id: str) -> bool:
    task = load_task(task_id)
    # 检查所有被 blockedBy 的前置任务是否均已完成
    for dep_id in task.get("blockedBy", []):
        dep_task = load_task(dep_id)
        if dep_task.get("status") != "completed":
            return False  # 任一依赖未完成，该任务即被阻塞
    return True

```

### ④ 原子性状态防御 (`claim_task`)

由于多个智能体并行运行，认领时必须在底层做校验防冲突，避免多个 Agent 同时做同一个任务：

```python
def claim_task(task_id: str, owner: str) -> str:
    task = load_task(task_id)
    if task.status != "pending":
        return f"Task {task_id} is {task.status}, cannot claim"
    if task.owner:
        return f"Task {task_id} already owned by {task.owner}"
    if not can_start(task_id):
        return f"Task {task_id} is blocked by dependencies."
        
    # 双重检查通过，原子性锁定状态
    task.owner = owner
    task.status = "in_progress"
    save_task(task)
    return f"Claimed {task.id} successfully."

```

### ⑤ 上下文重组时的身份保持（重注入）

因为系统带有 `autoCompact`（上下文自动压缩）机制，对话过长时历史会被 LLM 压成一段摘要。为了防止 Agent 被压缩后“忘掉自己是谁”，在每次进入新工作轮次时要进行长度检测：

```python
# 如果上下文被干洗/压缩到只剩头部，重新注入身份标签
if len(messages) <= 3:
    messages.insert(0, {
        "role": "user", 
        "content": f"<identity>You are '{name}', role: {role}. Continue your assigned or claimed task.</identity>"
    })

```

## 4. 教学版 vs. 生产级 Claude Code 源码的差异

在真实的 Claude Code 工业级分布式协作中，为了追求高性能与高并发安全，机制设计更为精精密：

* **文件级排他锁 (`proper-lockfile`)**：教学版在 `claim_task` 时没有加物理文件锁，如果多线程同时读写会发生 TOCTOU 并发冲突。Claude Code（在 `utils/tasks.ts:541-612` 中）使用了 `proper-lockfile` 包，在执行 `claimTaskWithBusyCheck` 时，会通过强原子性的**文件锁**将读-检查-改-写完全锁死，绝对杜绝两个 Agent 抢同一个任务文件的可能。
* **文件监听系统代替主动轮询 (`useTaskListWatcher`)**：教学版是每 5 秒用 `glob` 扫描一次磁盘，比较浪费性能。Claude Code 底层则是通过 `fs.watch()` 监听 `.claude/tasks/` 文件夹的变化并设置 1 秒的防抖（Debounce）。一旦有新任务发布或某个前置依赖被解锁，系统会**被动唤醒并触发通知**。
* **无缝空闲唤醒与更短轮询**：生产级队友在等待区不是 5 秒一跳，而是跑在一个 `500ms` 的极速轮询循环中（`waitForNextPromptOrShutdown`），并且一完成工作就会立刻调用 `sendIdleNotification()` 向 Lead 发送通知，确保多 Agent 之间的协同延迟降低到毫秒级。
