# Auto-Optimize：四角色迭代验证优化

## 为什么需要这个技能

模糊需求的核心问题是**无法客观判断做得好不好**。旧方法让模型看代码打分——但这不是真正的验证，只是"AI 觉得好"。

本技能的解决方案：**用真实工具验证真实结果**。像真实的 QA 团队一样工作——需求拆解为可测试的验收标准，代码被真实运行和操作，截图和测试输出作为证据。

核心原则：
- **验证而非评分**：PASS/FAIL 二元判定，不是 1-10 主观打分
- **四角色分离**：研究者定义标准、实现者写代码、测试者真实验证、评估者审查证据
- **真实工具验证**：Playwright 打开页面截图、pytest 运行测试、console 检查错误
- **迭代直到通过**：不合格打回修复，最多 3 轮

## 角色分工

| 角色 | 子代理类型 | 职责 | 关键约束 |
|------|-----------|------|---------|
| 研究者 | `Explore` | 分析需求、产出验收标准 | 只读，不写代码 |
| 实现者 | `general-purpose` | 生成实现代码 | 可编辑，各自独立 |
| 测试者 | `general-purpose` | 真实工具验证 + 截图 | 只读 + 运行，盲验 |
| 评估者 | `general-purpose` | 审查报告+截图，裁决 | 只读，必须独立验证 |

## 工作流程

### 协调器监控协议

协调器（主代理）是工作流的 Leader，全程负责质量保障。在**每个阶段完成后、进入下一阶段之前**，协调器必须执行监控检查。

#### 监控检查（每个阶段完成后必做）

1. **产出存在性**：该阶段的预期输出文件是否存在且非空
2. **产出合理性**：内容是否符合该阶段的格式要求（不是乱码、截断、或空白）
3. **产出可操作性**：下游阶段能否基于此产出继续工作

#### 处置手段（发现问题后，按优先级使用）

| 手段 | 适用场景 | 示例 |
|------|---------|------|
| 补充指令 | 产出不完整但基本可用 | 测试者漏了 2 条 AC 的验证 → 追加 prompt 补测 |
| 重新启动 | 产出格式错误或质量太差 | 评估者没做独立验证 → 重启评估者，强调独立验证 |
| 内联接管 | 子代理反复失败（2 次以上） | 实现者两次 429 → 协调器自己写代码 |
| 降级运行 | 多个子代理连续失败 | 2 个实现者 + 测试者都失败 → 切换到内联模式 |

#### 全局兜底规则

- **不跳过**：任何阶段的产出不达标，禁止跳过继续。宁可重做，不可带病推进
- **不猜测**：子代理没返回的信息，协调器不自己编造。缺失就回去补
- **不放弃**：子代理失败不等于任务失败。总有处置手段可用（最后手段是协调器内联完成所有角色）

### Phase 1：研究者 — 需求拆解 + 验收标准

收到模糊需求后，先启动研究者子代理（`subagent_type: "Explore"`）做需求分析。

研究者的任务是：
1. **提取隐含期望**：从用户模糊描述推断真正在意什么
   - "好看的界面" → 在意视觉美感、交互流畅、第一印象
   - "自动化处理" → 在意省力程度、可靠性、边界情况
   - "差不多的工具" → 在意能用就行、快速出结果
2. **产出可验证的验收标准**（不是评分维度）

每条验收标准必须满足三个条件：
- **明确的 PASS/FAIL 定义**：什么算通过、什么算不通过，无灰色地带
- **对应的验证方法**：用哪个工具怎么验证（Playwright 截图、pytest 断言、手动检查）
- **不可笼统**：
  - ❌ "代码质量好"
  - ✅ "pytest 运行 5 个测试全部通过"
  - ❌ "界面好看"
  - ✅ "首屏截图显示完整的文件列表，每行包含文件名和大小"
  - ❌ "功能完整"
  - ✅ "点击上传按钮能选择文件，上传后文件列表更新"

对于常见场景，参考 `references/acceptance-criteria-templates.md` 中的预定义验收标准集。

**UI 任务附加 AC**：如果用户需求涉及 UI/前端界面，验收标准中应包含 AC-UI-8（两种风格视觉可区分）——确保两个变体不只是内容不同，视觉风格也能明确区分。

产出格式：

```markdown
# 验收标准：{需求标题}

## 需求分析
- **原始需求**：{用户描述}
- **隐含期望**：{推断的 2-3 个核心期望}

## 验收标准

### AC-1：{标准名称}
- **验证方法**：{Playwright 截图 / pytest / 手动检查 / console 检查}
- **PASS 条件**：{具体的通过条件}
- **FAIL 条件**：{具体的失败条件}

### AC-2：{标准名称}
...
```

**用户确认后进入 Phase 2。** 将验收标准呈现给用户，等确认或微调。用户说"就这样"或"继续"视为确认。

**协调器检查**：AC 文件非空、至少 3 条标准、每条有 PASS/FAIL 定义。不满足则重启研究者并指明缺失。

### Phase 2：实现者 — 生成 2 个变体

启动 2 个独立的实现者子代理（`subagent_type: "general-purpose"`），**并行**执行。

两个变体的策略不同：

**变体 X**：确保所有验收标准都能通过。功能完整、稳定可靠，不留 placeholder。视觉风格偏保守专业。优先正确性。

**变体 Y**：满足基本验收标准 + 尝试更优方案。可以探索更好的交互设计、视觉方案、架构选择。视觉风格偏大胆创新。优先体验突破。

每个实现者拿到的信息：
- 完整的验收标准文档
- 自己的策略指引（但只知道自己的变体编号，不知道对方的策略）
- **不看到其他变体的任何信息**

实现者子代理的 prompt 模板：

```
你是一个实现者。请根据以下验收标准实现 {需求描述}。

## 策略
{变体 X：确保每一条验收标准都能通过。功能完整、稳定可靠，不留 placeholder。视觉风格偏保守专业。优先正确性。}
{变体 Y：满足基本验收标准的同时，尝试更优的交互/视觉/架构方案。视觉风格偏大胆创新。可以大胆创新。}

## 风格分离要求（硬性）
如果你的任务涉及 UI/前端实现，必须遵守以下风格分离规则：
- 使用完全不同的 CSS 类名体系（类名不能与另一变体共享超过 50%）
- 使用不同的配色方案（主色色相差 ≥ 30°）和不同的字体大小比例、间距节奏
- 使用不同的 HTML 结构方式（如 grid vs flex、section vs article、不同的嵌套层级）
- 不复制通用 CSS reset/base 样式——即使需要 reset 也用自己的写法

## 验收标准
{完整粘贴 acceptance_criteria.md 的内容}

## 输出要求
- 实现文件保存到：{输出目录}/variant_X.{扩展名}（或 variant_X.html）
- 测试文件保存到：{输出目录}/test_variant_X.py — 为你的实现编写 pytest 测试，覆盖所有验收标准
- 不要留 TODO、placeholder、"待实现"等未完成标记
- 每个功能都要完整可用

## 技术上下文
{用户的项目环境、技术栈、已有代码结构}
```

注意：两个实现者分别收到 variant_X 和 variant_Y 的标记。实现者不知道自己是"稳扎稳打"还是"创新"——只看到自己的策略指引。

所有实现和测试文件输出到同一扁平目录：
```
outputs/
  variant_X.py（或 .html）
  variant_Y.py（或 .html）
  test_variant_X.py
  test_variant_Y.py
  acceptance_criteria.md
  test_report.md
  ...
```

**协调器检查**：variant_X/Y 文件和 test_variant_X/Y.py 都存在。缺 1 个 → 进入单变体模式；缺 2 个 → 重试一次，仍失败则内联接管。

**单变体模式**：只有 1 个变体可用时，测试者和评估者只处理该变体。PASS 则直接交付，CONTINUE 则正常迭代修复。最终报告中记录"第二变体生成失败"。

### Phase 3a：测试者 — 真实工具验证

启动测试者子代理（`subagent_type: "general-purpose"`），对两个变体做**盲验**。

**关键**：测试者不知道哪个是稳扎稳打版、哪个是创新版。变体标记为 X 和 Y。

**测试归属**：测试者运行实现者编写的测试文件（`pytest test_variant_X.py test_variant_Y.py`），并补充边界测试。测试者不负责编写主要测试——那是实现者的职责。

**验证流程**：测试者读取 `references/qa-verification-guide.md` 获取完整的验证操作指南（前端 Playwright 步骤、后端 pytest 步骤、截图命名规范、报告格式模板）。

**硬性要求**：
- 每条验收标准必须有 PASS/FAIL 判定 + 截图/pytest 输出作为证据
- 证据必须可追溯到原始输出文件（截图文件名或 pytest 输出行号）
- 原始输出必须保存：前端截图全部保存到 outputs/，后端保存 `pytest_output_X.txt` / `pytest_output_Y.txt`
- 产出 `test_report.md`，必须包含截图路径清单（评估者需要这些路径来查看截图）

**协调器检查**：
1. test_report.md 存在且包含逐条 AC 结果。
2. **截图路径校验**（前端场景）：读取 test_report.md，检查截图路径是否指向 outputs/ 目录。如果路径包含 `.playwright-mcp/`，说明截图保存位置错误。
3. **截图文件存在性**：用 Glob 检查 outputs/ 目录下是否有 PNG 文件。如果截图在 `.playwright-mcp/` 而不在 outputs/，执行搬迁（见下方）。
4. 后端：pytest_output_*.txt 存在。
不满足则重启测试者并指明缺失项。截图在错误目录也算不合格。

**截图兜底搬迁**：如果协调器发现截图在 `.playwright-mcp/` 而非 `outputs/` 目录：
1. 将 `.playwright-mcp/` 中的截图复制到 `outputs/` 目录（`cp .playwright-mcp/*.png outputs/`）
2. 更新 `test_report.md` 中所有截图路径（将 `.playwright-mcp/` 替换为 `outputs/` 绝对路径）
3. 在 `workflow-state.md` 异常记录中标注"截图路径已搬迁"

### Phase 3b：评估者 — 独立验证 + 裁决

启动评估者子代理（`subagent_type: "general-purpose"`），审查测试者产出的所有证据。

**评估者必须多模态**：使用 Read 工具查看截图（PNG 文件），不只看文字报告。这是硬性要求——跳过截图直接裁决是违规的。

**独立验证（不可跳过）**：

评估者不能仅凭测试者的报告裁决。必须独立执行以下验证：

- **前端**：用 Read 工具查看每张截图，逐条确认测试者的 PASS/FAIL 判定。不一致时以自己的判断为准
- **后端**：运行 `pytest test_variant_X.py -v` 和 `test_variant_Y.py -v`，对比实际通过数与测试者报告
- **抽查**：随机选取 2-3 条验收标准，自己执行验证方法
- 如果独立验证与测试者报告不一致，以评估者的独立验证为准

**裁决规则（最严格原则）**：任何一条 AC FAIL → CONTINUE；Console error → CONTINUE；只有零问题才 PASS。详细裁决标准和评估报告格式见 `references/qa-verification-guide.md`。

**CONTINUE 时必须说明问题类型**，决定循环回哪个角色：
- **代码 Bug**（验收标准 FAIL、console 错误）→ 循环回实现者修复
- **需求理解错误**（实现方向与用户意图不符）→ 循环回研究者重新定义

**协调器检查**：评估报告中每个变体有明确裁决（PASS/CONTINUE）。CONTINUE 必须有问题类型和具体 AC 编号。裁决矛盾或格式不对 → 重启评估者，附上格式要求。

### Phase 4：验收门控 & 迭代

这是协调器（主代理）的工作。根据评估者的裁决决定下一步：

**情况 1：两个变体都 PASS**
→ 呈现评估者推荐 + 两个变体的关键截图给用户
→ 用户选择最终方案

**情况 2：任一变体 CONTINUE**

迭代执行协议（**不可跳过**）：

当评估者对任一变体裁决 CONTINUE 时，协调器必须：

1. **提取修复清单**：从评估者报告中提取所有 CONTINUE 变体的具体问题
2. **提取证据路径**：从 test_report.md 的截图清单中提取所有截图文件路径，传递给下一轮评估者子代理
3. **启动修复实现者**子代理（只修 CONTINUE 的变体，不动已 PASS 的变体）：

   ```
   Agent({
     subagent_type: "general-purpose",
     description: "修复变体 {X/Y}",
     prompt: "你是修复实现者。变体 {X/Y} 有以下问题需要修复：\n\n## 需要修复的问题\n{从评估者报告逐条提取}\n\n## 原始实现\n路径：{variant_X.py 路径}\n\n## 要求\n- 只修复上述问题，不做其他改动\n- 修复后运行 pytest {输出目录}/test_variant_{X/Y}.py -v 确认通过\n- 覆盖保存到同一文件\n- 保存 pytest 输出到 {输出目录}/pytest_output_{X/Y}_fix.txt"
   })
   ```

4. **重测范围**：重新走 Phase 3a + 3b，测试者重新运行完整测试套件（`pytest test_variant_X.py -v`），这同时覆盖 CONTINUE 项和回归检查。前端场景对已 PASS 的 AC 做快速截图抽查。
5. **记录迭代次数**：Phase 2 是第 1 轮，每次 3a→3b→修复 算一轮

**情况 3：3 轮迭代后仍有 CONTINUE**
→ 输出当前最优变体 + 未通过项说明
→ 告知用户哪些验收标准未能通过

**迭代上限**：最多 3 轮。3 轮后仍有 CONTINUE，输出当前最优变体 + 未通过项说明。

**协调器硬性约束**：
- 禁止直接修改实现代码——必须通过子代理
- 禁止跳过测试者直接让评估者判断
- 禁止在 CONTINUE 后直接向用户展示结果——必须先修复
- 禁止跳过重测——修复后必须重新走 Phase 3a
- 必须基于评估者报告和截图决定下一步
- 每轮修复只针对具体问题，不全面重写
- 每轮只修 CONTINUE 的变体，不动已 PASS 的变体

### 工作流状态追踪

协调器在 outputs/ 目录维护 `workflow-state.md`，每个阶段完成后更新：

```markdown
# 工作流状态
## 当前阶段：{Phase 1/2/3a/3b/4}
## 迭代轮次：{1/2/3}
## 变体状态
| 变体 | 实现 | 测试 | 评估 | 裁决 |
|------|------|------|------|------|
| X | ✅ | ✅ R1 | ✅ R1 | CONTINUE |
| Y | ✅ | ✅ R1 | ✅ R1 | PASS |
## 待修复问题
- [ ] 变体 X AC-5：移动端按钮 36px → 44px
## 异常记录
- Phase 2 变体 Y 实现者超时，重试后成功
```

协调器上下文丢失时，读此文件恢复状态。

## 子代理调用模板

### 测试者调用
```
Agent({
  subagent_type: "general-purpose",
  description: "盲验测试 - Playwright/pytest 验证",
  prompt: "你是一个测试者。请对以下两个变体进行盲验。\n\n## 截图路径（硬性要求）\n所有 Playwright 截图必须使用完整路径：{实际输出目录绝对路径}/{variant}-xxx.png。\n不要使用裸文件名，否则截图会保存到 .playwright-mcp/ 默认目录。\n正确示例：filename: \"{实际输出目录绝对路径}/X-fullpage.png\"\n错误示例：filename: \"X-fullpage.png\" ← 这会保存到 .playwright-mcp/\n每次截图后，用 Bash 执行 ls {实际输出目录绝对路径}/*.png 确认文件在正确位置。\n\n## 验收标准\n{完整标准}\n\n## 变体 X\n路径：{path-X}\n\n## 变体 Y\n路径：{path-Y}\n\n## 验证指南\n请读取 references/qa-verification-guide.md 获取完整的验证流程和模板。\n\n## 输出\n保存 test_report.md 到 {输出目录}，包含截图路径清单和逐条验收结果。"
})
```

### 评估者调用
```
Agent({
  subagent_type: "general-purpose",
  description: "评估裁决 - 独立验证并审查",
  prompt: "你是一个评估者。你必须独立验证测试者的结论。\n\n## 独立验证（不可跳过）\n1. 前端：用 Read 工具查看每张截图，与测试者判定逐条对比\n2. 后端：运行 pytest test_variant_X.py -v 和 test_variant_Y.py -v，对比实际通过数与测试者报告\n3. 通用：抽查 2-3 条验收标准，自己执行验证方法\n4. 如果你的独立验证与测试者报告不一致，以你的验证为准\n\n## 测试报告\n{test_report.md 内容}\n\n## 原始证据文件\n{列出 pytest_output_*.txt 文件路径（后端）}\n{列出截图文件路径（前端，从 test_report.md 截图清单提取）}\n\n## 要求\n1. 必须执行独立验证，不能只抄测试者报告\n2. 最严格原则：任何问题都标 CONTINUE\n3. 每个变体独立裁决\n4. 在报告中记录你的独立验证过程\n\n## 验收标准\n{完整标准}"
})
```

## 适配说明

本技能针对智谱 GLM-5.1 模型优化：
- GLM-5.1 对长指令遵循度高，子代理 prompt 可以包含完整的验证流程
- 评估者看截图时使用 Read 工具读取 PNG 文件，GLM-5.1 的多模态能力支持图像理解
- 前端验证依赖 Playwright MCP 工具，需要环境中有 Playwright 可用

## 降级模式：部分降级与内联执行

**触发条件**：遇到以下情况时，按角色逐个判断是否需要降级：
- 子代理返回 429 rate limit 错误
- 子代理超时（超过 10 分钟无响应）
- 网络不可用导致子代理无法启动
- 其他子代理启动失败错误

### 部分降级（优先）

降级不是全有或全无——某个角色的子代理失败时，只内联该角色，其他角色仍用子代理：

1. **研究者失败** → 内联研究者，子代理实现者/测试者/评估者照常
2. **实现者失败** → 内联实现者（遵守下方规则），其他角色照常
3. **测试者失败** → 内联测试者，评估者仍用子代理
4. **评估者失败** → 内联评估者，其他角色不受影响

只有当多个角色连续失败（≥2 个角色）时，才进入全内联模式。

### 实现者内联规则

实现者内联时，两个变体必须**顺序**生成以确保风格分离：
1. 先完成变体 X（保存到文件）→ 清除上下文中的实现细节
2. 再开始变体 Y → Y 的 CSS 类名、配色、HTML 结构必须与 X 不同
3. 生成变体 Y 前重新读取验收标准，避免被 X 的实现思路锚定

### Playwright 不可用时的结构化代码审查

当 Playwright 不可用时，测试者验证降级为**结构化代码审查**（不是笼统的"代码看起来没问题"）：

1. **逐条 AC 检查清单**：对每条验收标准，写明"在代码中的什么位置实现了什么功能"
2. **grep 确认**：用 Grep 工具搜索关键实现元素（CSS 类名、事件处理函数、API 端点等）
3. **手动构造测试用例**：对核心逻辑，手动构造输入→预期输出对照表
4. **产出格式**：与正常 test_report.md 相同，但每条判定标注"代码审查（无 Playwright 验证）"

### 迭代保护（内联模式）

内联模式下协调器直接修改代码时，必须遵守：
- **先列后改**：修改前先列出所有待修改项，确认后再逐项修改
- **改后必测**：每项修改后立即运行对应测试（pytest 或 Playwright 截图验证）
- **增量修改**：每项修改单独保存，不要一次性改多处再测试

### 降级模式标注（硬性要求）

降级模式下，评估报告**必须**在顶部标注降级状态：

```markdown
⚠️ **降级评估** — {列出降级的角色和原因}
- 内联执行：{如"实现者（429 rate limit）+ 测试者（Playwright 不可用）"}
- 无法执行：{列出无法执行的操作，如"独立截图审查"、"Playwright 前端验证"}
- 替代方案：{列出替代验证方式，如"结构化代码审查 + grep 确认"}
- 以下判定置信度受限
```

对每个受影响的判定降低一级置信度：PASS → "可能 PASS（未独立验证）"；CONTINUE 保持不变。

降级模式下仍然遵守：验收标准必须可验证、测试结果必须基于真实运行（非猜测）、评估者必须看截图（如可用）、原始输出必须保存。

最终报告中注明："本报告基于 {完全/部分} 降级评估，建议有条件时使用独立子代理重新验证降级的角色。"

## 错误处理

协调器按照"监控协议"中的处置手段处理异常。以下是常见场景的具体处理方式：

- **子代理执行失败**：记录失败 → 用剩余产出继续。全部失败 → 按处置手段升级（重试→内联接管→降级运行）
- **单实现者失败**：进入单变体模式（Phase 2 检查清单中有说明）
- **测试者中途崩溃**：删除部分产出 → 重新启动测试者从头验证
- **评估者跳过独立验证**：重启评估者，prompt 中强调独立验证步骤
- **评估者裁决矛盾**：重启评估者，附上格式要求和上次的问题
- **修复引入回归**：下一轮重测会通过完整 pytest 套件捕获（见 Phase 4 重测范围）
- **Playwright 不可用**：前端验证降级为结构化代码审查（逐条 AC 检查清单 + grep 确认 + 手动构造测试用例，见降级模式章节）
- **用户中途修改需求**：终止当前迭代，回到 Phase 1 重新拆解
