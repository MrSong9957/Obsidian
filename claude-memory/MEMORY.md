## 用户偏好

### 沟通语言

**使用中文**进行所有交流和解释。

### 代码学习偏好

用户只关心**基本原理和实现逻辑**，大多数情况下**无需关心具体代码实现**。

**实践方式：**
- 直接修改代码，事后简洁说明原理
- 重点解释"为什么"和"整体逻辑"
- **默认不逐行讲解代码**

**例外情况：需要人工干预时**
- 当 AI 无法自动解决问题，用户主动要求查看代码
- 此时才需要**逐行讲解代码细节**

### 解释风格偏好

**嵌入术语的形象比喻** — 用比喻建立直觉，同时在比喻中嵌入真实专业术语。

**为什么不用纯比喻：** 纯比喻只能解释基本逻辑，无法与现实一一对应。

**为什么不用纯术语：** 专业说法晦涩，不利于教学。

**示例：** 用"作家、图书馆、机器人管理员"的比喻解释虚拟内存，同时在比喻中自然嵌入 MMU、页表、物理地址、磁盘交换空间等术语，让比喻和现实一一对应。

### 项目推进方式

面向零基础用户，小步推进，边干边学。

**核心原则：**
- **小步推进** — 每次只做一个小改进
- **可验证** — 每个阶段都有可验证的结果

### 核心工作流原则

**自主闭环：** 遇到问题自动验证、测试、迭代修复；完成代码后直接启动测试验证。多次尝试失败才请求用户介入。

### 调试原则

**永远先观察，再假设。** 详见 [debugging-lessons.md](./debugging-lessons.md)

遇到 Bug 时的第一件事：加日志，打印相关变量，观察实际值。

### obsidian-vault 同步规则

obsidian-vault 仓库**只保存全局记忆**，不保存项目记忆。

### Obsidian 管理方法

**文件夹结构：**
```
obsidian-vault/
├── README.md           # 管理方法说明（根目录）
├── Attachments/        # 图片、PDF 等附件
├── Templates/          # 笔记模板
├── References/         # 长期参考材料（方法、原则、最佳实践）
├── Projects/           # 项目相关笔记
├── Learning/           # 学习笔记、知识整理
├── claude-memory/      # Claude Code 全局记忆
└── Inbox/              # 待整理笔记
```

**分类原则：**
- 新笔记先放 Inbox/，定期整理
- 根目录只放 README.md，保持简洁
- References/ 存放长期可复用的知识

### 技术选型原则

优先复用成熟方案，能直接用就用，不能则在此基础上修改，避免重复造轮子。

### 避免过度工程化

只进行直接要求的或明显必要的更改。保持解决方案简单和专注：

- **范围**：不要添加功能、重构代码或进行超出要求的"改进"
- **文档**：只在逻辑不自明的地方添加注释
- **防御性编码**：只在系统边界验证
- **抽象**：不要为一次性操作或假设的未来需求设计

### 子代理使用原则

**使用子代理：** 任务可以并行运行、需要隔离的上下文、涉及不需要共享状态的独立工作流。

**直接工作：** 简单任务、顺序操作、单文件编辑、需要跨步骤维护上下文的任务。

### 前端美学原则

避免"AI 泛滥"美学，制作有创意、独特的前端。

**详细：** [frontend-aesthetics.md](./frontend-aesthetics.md)

### 代码解决方案原则

使用标准工具编写高质量的通用解决方案：

- **不要创建变通方法**：不创建辅助脚本或仅针对特定测试输入的硬编码方案
- **通用逻辑**：实现对所有有效输入都能正确工作的方案
- **正确理解问题**：测试用于验证正确性，不是用来定义解决方案
- **有原则的实现**：遵循最佳实践和软件设计原则
- **诚实反馈**：如果任务不合理或测试不正确，告知用户而非绕过
