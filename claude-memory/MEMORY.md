# Memory

## 用户偏好

### 沟通语言

**使用中文**进行所有交流和解释。

### 代码讲解风格

用户要求**行级粒度**的代码讲解，而非块级/功能级讲解。

**讲解模板：**

```markdown
## 行级讲解：[函数名/模块名]

```typescript
// 完整代码块
```

### 第 X 行
```typescript
    具体那一行代码
```

| 部分 | 含义 |
|------|------|
| `关键字` | 解释 |
| `关键字` | 解释 |

**为什么这样写？**
- 解释设计原因
- 说明可能的问题或注意事项

---

## 执行流程图

(用 ASCII 图展示执行流程)
```

**关键原则：**
1. 每行代码单独讲解，不要跳过
2. 解释语法细节（`const`、`=>`、`:` 等）
3. 说明"为什么"而不仅是"是什么"
4. 用表格 + ASCII 流程图辅助理解
5. 对比相关概念（如 `console.log` vs `process.stdout.write`）

### 项目推进方式

面向**零基础用户**，以**小步推进**的方式，实现**边干边学**。

**核心原则：**
1. **小步推进** — 每次只做一个小改进，不要一次改太多
2. **先跑起来** — 代码能运行再完善
3. **边干边学** — 理解了就改代码，学习和动手相结合
4. **可验证** — 每个阶段都要有可验证的结果
5. **二八定律** — 只关心最关键的 20%

### 代码学习偏好

用户只关心**基本原理和实现逻辑**，大多数情况下**无需关心具体代码实现**。

**实践方式：**
- 直接修改代码，事后简洁说明原理
- 重点解释"为什么"和"整体逻辑"
- **默认不逐行讲解代码**

**例外情况：需要人工干预时**
- 当 AI 无法自动解决问题，用户主动要求查看代码
- 此时才需要**逐行讲解代码细节**
- 这是"最后的手段"，不是常态

### UI 设计原则

**Ctrl+P 是唯一主菜单入口**，遵循以下原则：

1. **一个功能一个位置** — 不能重复占用菜单选项
2. **功能整合** — 相关功能必须合并为一个菜单项
   - 例如：选择会话 + 删除会话 → 整合为"会话管理"
3. **慎重添加** — 主菜单选项必须精简，不能随意扩展

```
主菜单结构（示例）:
├── 会话管理     ← 整合：选择/新建/删除/重命名
├── 模型选择     ← 未来
└── 设置        ← 未来
```

### 核心工作流原则

**1% 规则：** 只要有 1% 可能性某 SKILL 技能适用 → 必须调用该 SKILL 技能。

**自主解决原则：** 遇到问题 → 自动验证、自动测试、迭代修复 → 多次尝试后仍失败才请求用户介入。

**不用问，直接测：** 完成代码修改后，优先自主启动测试验证效果，迭代修复问题，无需询问用户是否需要测试。

### 调试原则

**永远先观察，再假设。** 详见 [debugging-lessons.md](./debugging-lessons.md)

遇到 Bug 时的第一件事：加日志，打印相关变量，观察实际值。
