# Memory

## 用户偏好

### 沟通语言

**使用中文**进行所有交流和解释。

### 代码学习偏好

用户只关心**基本原理和实现逻辑**，大多数情况下**无需关心具体代码实现**。

**实践方式：**
- 直接修改代码，事后简洁说明原理
- 重点解释"为什么"和"整体逻辑"
- **默认不逐行讲解代码**

**例外情况：需要人工干预时**
- 当 AI 无法自动解决问题，用户主动要求查看代码
- 此时才需要**逐行讲解代码细节**

### 项目推进方式

面向零基础用户，小步推进，边干边学。

**核心原则：**
- **小步推进** — 每次只做一个小改进
- **可验证** — 每个阶段都有可验证的结果

### 核心工作流原则

**自主闭环：** 遇到问题自动验证、测试、迭代修复；完成代码后直接启动测试验证。多次尝试失败才请求用户介入。

### 调试原则

**永远先观察，再假设。** 详见 [debugging-lessons.md](./debugging-lessons.md)

遇到 Bug 时的第一件事：加日志，打印相关变量，观察实际值。

### obsidian-vault 同步规则

obsidian-vault 仓库**只保存全局记忆**，不保存项目记忆。

### Obsidian 管理方法

**文件夹结构：**
```
obsidian-vault/
├── README.md           # 管理方法说明（根目录）
├── Attachments/        # 图片、PDF 等附件
├── Templates/          # 笔记模板
├── References/         # 长期参考材料（方法、原则、最佳实践）
├── Projects/           # 项目相关笔记
├── Learning/           # 学习笔记、知识整理
├── claude-memory/      # Claude Code 全局记忆
└── Inbox/              # 待整理笔记
```

**分类原则：**
- 新笔记先放 Inbox/，定期整理
- 根目录只放 README.md，保持简洁
- References/ 存放长期可复用的知识

### 技术选型原则

优先复用成熟方案，能直接用就用，不能则在此基础上修改，避免重复造轮子。

### 避免过度工程化

只进行直接要求的或明显必要的更改。保持解决方案简单和专注：

- **范围**：不要添加功能、重构代码或进行超出要求的"改进"。修复 bug 不需要清理周围的代码。简单的功能不需要额外的可配置性。
- **文档**：不要为没有更改的代码添加文档字符串、注释或类型注解。只在逻辑不自明的地方添加注释。
- **防御性编码**：不要为不可能发生的场景添加错误处理、回退或验证。信任内部代码和框架保证。只在系统边界（用户输入、外部 API）进行验证。
- **抽象**：不要为一次性操作创建辅助函数、工具或抽象。不要为假设的未来需求进行设计。正确的复杂度是当前任务所需的最小量。

### 子代理使用原则

**使用子代理：** 任务可以并行运行、需要隔离的上下文、涉及不需要共享状态的独立工作流。

**直接工作：** 简单任务、顺序操作、单文件编辑、需要跨步骤维护上下文的任务。

### 前端美学原则

避免"AI 泛滥"美学，制作有创意、独特的前端。

**重点关注：**
- **排版**：选择美观、独特且有趣的字体。避免 Arial、Inter 等通用字体。
- **颜色和主题**：坚持一致的美学，使用 CSS 变量。主色调配以鲜明的强调色。从 IDE 主题和文化美学中汲取灵感。
- **动效**：使用动画实现效果和微交互。HTML 优先用纯 CSS；React 用 Motion 库。专注于高影响力的时刻（如精心编排的页面加载配合交错显示）。
- **背景**：创造氛围和深度，而非纯色。叠加 CSS 渐变、几何图案或上下文效果。

**避免通用 AI 生成美学：**
- 过度使用的字体（Inter、Roboto、Arial、系统字体）
- 陈词滥调的配色（特别是白色背景上的紫色渐变）
- 可预测的布局和组件模式
- 缺乏上下文特定特征的千篇一律设计

**跳出框框思考**：创造性地解读，做出意想不到的选择。在浅色/深色主题、不同字体、不同美学之间变化。避免收敛到常见选择（如 Space Grotesk）。

### 代码解决方案原则

使用标准工具编写高质量的通用解决方案：

- **不要创建变通方法**：不创建辅助脚本或仅针对特定测试输入的硬编码方案
- **通用逻辑**：实现对所有有效输入都能正确工作的方案，而非仅通过测试用例
- **正确理解问题**：测试用于验证正确性，不是用来定义解决方案
- **有原则的实现**：遵循最佳实践和软件设计原则，方案应健壮、可维护、可扩展
- **诚实反馈**：如果任务不合理或测试不正确，告知用户而非绕过

### 代码质量约束（自动发现机制）

**核心原则：用户不需要知道"什么是好的"，AI 负责发现最佳实践。**

**实现前必须做的事：**
- **强制研究**：实现新功能前，AI 必须先研究成熟开源项目（至少 1 个），说明采用了什么模式
- **说明来源**：设计决策必须标注"参考自 [项目名] 的 [模块]"
- **列出备选**：写代码前，列出 2-3 个实现方案及取舍理由

**类型安全要求：**
- **禁止 `any` 类型**：必须使用具体类型
- **参数验证用 Zod**：定义 schema 一次，自动推导类型 + 运行时验证，避免手写 JSON Schema
- **类型从定义推导**：不要重复定义（改一处参数要改两处代码是错误的）

**模块设计要求：**
- **高内聚**：相关逻辑放在一起，不要散落在多个文件
- **低耦合**：模块间通过明确接口通信，不依赖内部实现
- **单一职责**：一个函数/模块只做一件事

**代码审查要求：**
- 新功能完成后，用 `code-reviewer` agent 审查
- 审查重点：安全漏洞、类型安全、是否遵循上述原则
