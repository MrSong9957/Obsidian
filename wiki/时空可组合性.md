# 核心认知

> **动态系统要安全变化，必须同时解决两件事：组件离开时能撤销自己造成的影响；依赖变化时能自动重新协调。**[^1]

对应两个概念：

```text
Temporal Composability  时间可组合性
→ 组件离开后，环境可以恢复

Spatial Composability   空间可组合性
→ 依赖变化后，组件可以重新接线
```

**人话翻译：** 像可随时换人的团队：旧人走了要把自己的东西收干净，新人来了其他人还能自动重新配合。

---

# 为什么需要这套设计

动态系统中的组件可能随时：

```text
加入
移除
替换
重新加载
```

但组件运行时又会：

```text
注册 Tool
监听事件
创建定时器
挂载服务
修改共享状态
依赖 filesystem / database / llm
```

因此真正困难的不是“怎么加载一个插件”，而是：

```text
它走了，留下的东西怎么办？
它依赖的人换了，怎么办？
```

**人话翻译：** 开门营业很容易，难的是员工离职后没人留下烂摊子，供应商换了以后业务还能继续跑。

# 1. 时间可组合性：副作用必须能撤销

传统方式通常把生命周期拆成：

```text
setup()
cleanup()
```

问题是 cleanup 完全依赖开发者记得做，而且很容易漏掉某个事件监听、定时器或服务。

Cordis 使用 **Revertible Effects（可撤销副作用）**：

```text
执行操作
↓
同时记录如何撤销
↓
Runtime 保存
↓
组件卸载
↓
自动反向撤销
```

核心入口类似：

```text
ctx.effect(...)
```

也就是把：

```text
做什么
+
怎么恢复
```

绑在一起。

**人话翻译：** 每借走一样东西时就顺便留下“怎么归还”的记录，而不是半年后再靠记忆清点。

---

# 2. 空间可组合性：依赖必须显式声明

假设：

```text
Tool
↓ 需要
Filesystem
↓ 当前由
LocalFilesystem 提供
```

如果以后换成：

```text
SandboxFilesystem
```

组件不应该自己到处：

```text
查服务
判空
监听 Provider
重新连接
```

Cordis 使用 **Reactive Coeffects（响应式环境依赖）**。

组件只声明：

```text
我需要 filesystem
我需要 database
我需要 llm
```

Runtime 根据当前环境处理：

```text
Provider 出现
→ 依赖满足
→ 激活组件

Provider 消失
→ 依赖不足
→ 停用组件

Provider 替换
→ 重新解析依赖
```

**人话翻译：** 员工只需要说“我需要一台打印机”，不用自己负责采购、维修和以后换哪台机器。

---

# 3. Effect + Coeffect：组件与环境的两个方向

组件与外部环境的关系可以压成两个方向：

```text
Component ───→ Environment
       Effect
       我改变了什么

Component ←─── Environment
      Coeffect
      我需要什么
```

Cordis 用 **Context** 统一管理这两种关系。

所以 `ctx` 不只是一个放服务的全局对象，更像：

> **组件与运行环境之间的受控接口。**

**人话翻译：** Context 像公司的前台：员工要资源通过它申请，对公司做了什么修改也通过它登记。

---

# 4. Component：不是执行一次，而是持续被 Runtime 管理

一个 Component 可以理解成：

```text
Component
=
需要哪些能力
+
运行时会造成哪些影响
```

其运行时实例叫 **Fiber**。

典型生命周期：

```text
依赖不足
↓
INACTIVE

依赖满足
↓
LOADING
↓
ACTIVE

依赖消失
↓
UNLOADING
↓
撤销 Effect
↓
INACTIVE
```

如果加载过程中依赖再次改变，Runtime 不会同时乱跑 load 和 unload，而是先完成当前状态转换，再按照最新情况继续调整。

**人话翻译：** 像电梯正在从 1 楼去 5 楼时又有人按 3 楼，不是同时往两个方向跑，而是有序处理新的目标。

---

# 5. Cordis Core：只解决动态组合问题

整体结构：

```text
Application
Koishi / Agent Harness
        ↓
Component Loader
配置 / reconciliation / HMR
        ↓
Cordis Core
Effect Tracking
+
Coeffect Resolution
```

Cordis Core 不关心上层到底是：

```text
聊天机器人
Coding Agent
IDE
其他应用
```

它主要回答三个问题：

```text
副作用怎么撤销？
依赖怎么重新满足？
组件什么时候加载或卸载？
```

因此 Cordis 更接近 **meta-framework**：提供组件动态组合的底层规则，而不是规定具体业务怎么写。

**人话翻译：** 它更像交通规则，而不是某一辆具体汽车。

# 6. HMR 为什么自然出现

**HMR（Hot Module Replacement，热模块替换）**解决的是：程序不停机的情况下替换组件代码。

只要系统已经保证：

```text
Effect 可撤销
+
Coeffect 可重新解析
```

替换就可以变成：

```text
旧 Component
↓
dispose
↓
撤销旧 Effect
↓
加载新 Component
↓
重新建立 Effect 和依赖
```

因此 HMR 不是一个孤立功能，而是时空可组合性成熟后的自然结果。

**人话翻译：** 如果旧店员能完整交接，新店员又能自动接上工作，那么换人就不需要整家公司停业。

# 7. 对 Agent Harness 的意义

传统修改 Harness：

```text
修改代码
↓
restart
```

可能导致：

```text
正在执行的任务被打断
进程内状态丢失
连接和缓存重新建立
```

论文指向的未来形态则是：

```text
Agent
↓
生成 Tool / Component
↓
动态安装
↓
Runtime 协调依赖
↓
发现有问题
↓
撤销 / 替换
↓
Harness 继续运行
```

这就是 **Self-Evolving Agent Harness** 所需要的基础能力。

**人话翻译：** Agent 不只是使用工具，还可能在系统运行过程中自己安装、替换工具，而系统不能因为换一个零件就整台机器重启。

# 最重要的工程原则

## 1. 副作用与清理绑定

```text
执行操作
+
同时定义撤销方式
```

不要长期把 `setup` 和 `cleanup` 分散管理。

**人话翻译：** 谁弄乱的，系统当场记下以后怎么恢复。

## 2. 依赖显式声明

```text
Component：
我需要 filesystem / database / llm
```

不要让组件偷偷寻找全局服务。

**人话翻译：** 把需求写进采购单，不要让员工自己满公司找设备。

## 3. 生命周期由 Runtime 保证

正确性不能主要建立在：

```text
开发者记得 cleanup
```

而应尽量由框架保证组件：

```text
正确加载
正确卸载
正确恢复
正确重新连接依赖
```

**人话翻译：** 重要流程应该靠制度自动执行，而不是靠每个人记性好。

## 4. Plugin 只是形式，Composition 才是目标

真正重要的不是：

```text
Everything is a Plugin
```

而是：

```text
Everything should be composable
```

也就是：

```text
             Component
             /       \
          Effect    Coeffect
          可撤销     可重解析
             \       /
              ↓
   Spatiotemporal Composability
              ↓
      加入 / 移除 / 替换 / 重组
```

**人话翻译：** 重点不是“东西都做成插件”，而是这些插件能不能随时安全地插上、拔掉和换掉。

| 实体                  | 作用                                  | 与主题的关系                  |

| **Cordis**          | 管理 Effect、Coeffect 和 Component 生命周期 | 时空可组合性的主要实现载体           |

| **HMR**             | 运行中替换组件                             | 时空可组合性带来的直接能力           |

# 最终心智模型

只记这一张关系就够：

```text
动态系统为什么难？
↓
组件会不断变化
↓
变化带来两个问题

① 旧组件留下什么？
② 新环境还能不能满足依赖？

        ↓                 ↓

     Effect            Coeffect
     可撤销             可重解析
        ↓                 ↓

Temporal             Spatial
Composability        Composability

        \               /
         \             /
          ↓           ↓

     Component 可以安全
     加入 / 移除 / 替换 / 重组

              ↓

      Self-Evolving System
```

**认知升级：** 判断一个动态插件或 Agent Harness 架构是否真正成熟，不要只看“能不能加载插件”，而要看它能否**安全撤销变化，并在环境变化后自动重新组合**。
