**当记忆需要统计、检查冲突或触发提醒时，可以把用户信息整理成程序能直接处理的数据，再用函数执行规则，减少模型临时计算和判断的负担。**[^1]

**User as Code 的做法，是“用对象保存状态，用函数处理状态”。**

对象有明确的字段和类型，例如：护照有效期是日期，是否国际旅行是布尔值，也就是“是或否”。函数则负责统计次数、比较日期和检查冲突。这样，明确的计算过程可以运行、测试和核对。[User as Code 论文](https://arxiv.org/abs/2606.16707)

它借用了“预写日志＋检查点”的思路：

1. **先记日志**：会话结束后，把提取的事实追加到日志末尾，保留历史记录。
2. **再整理状态**：定期读取完整日志，重建带类型的用户状态。这个整理好的状态快照就是“检查点”。
3. **运行规则**：查询时用函数计算；状态更新后，调用检查函数，主动发现需要提醒的问题。

日志保留过去记录过什么，状态表示当前整理出的信息。**函数需要接入更新流程，写出函数本身不会让它自动执行。**

下面是根据原文简化的**说明示例，采用 Python 风格伪代码**；类型定义和提醒函数省略，只保留一次旅行：

```python
state = {
    "passport": PassportInfo(
        expiry_date=date(2025, 2, 18)
    ),
    "trips": [
        Trip(
            destination="Tokyo",
            departure_date=date(2025, 1, 15),
            is_international=True
        )
    ]
}

# 遍历旅行记录，统计 2025 年的国际旅行次数
trip_count = sum(
    1 for trip in state["trips"]
    if trip.is_international
    and trip.departure_date.year == 2025
)

# 检查每次国际旅行出发时，护照还剩多少天有效期
def check(state):
    for trip in state["trips"]:
        if trip.is_international:
            days = (
                state["passport"].expiry_date
                - trip.departure_date
            ).days

            if days < 180:  # 仅用于演示的阈值
                alert("护照剩余有效期不足", trip, days)

# 系统在状态更新后调用检查
check(state)
```

按这组示例数据，国际旅行次数是 **1 次**，出发时护照还剩 **34 天**，因此会触发示例规则。**180 天只是演示条件，实际检查应使用对应行程的有效规则。**

原文还演示了冲突检测：遍历当前用药 `current_medications` 和过敏记录 `allergies`，比较双方的 `drug_class`（药物类别），匹配时报告冲突。这只是列表比对的简化示例，真实用药判断需要更完整、经过验证的医学规则。

**计算稳定，不等于事实一定正确。** 相同数据和规则可以得到相同结果，但事实提取错误、记录遗漏或规则写错，仍会产生错误结果。JSON 数据也可以接上计算函数；真正起作用的是明确的数据结构、规则和执行流程。

**认知类型回答另一个问题：应该记住什么内容？**

可以把 Agent 当前的上下文类比为**工作记忆**：临时放置当前任务要用的信息，包括近期对话、工具结果，以及从长期记忆中取回的内容。完整历史可以另外保存，不必全部塞进当前上下文。

原文借用三类认知科学概念，帮助设计长期记忆：

| 类型                          | 记住什么                 | Agent 中的例子                   |
| --------------------------- | -------------------- | ---------------------------- |
| **情景记忆（Episodic Memory）**   | 某次具体事件：何时发生、涉及谁、做了什么 | 用户预订了下周五去东京的 ANA 航班          |
| **语义记忆（Semantic Memory）**   | 可以反复使用的知识和用户特征       | 用户是素食者，偏好靠窗座位                |
| **程序记忆（Procedural Memory）** | 完成某类任务的方法和流程         | 先搜直飞航班 → 确认座位 → 使用常旅客号码 → 订餐 |

语义记忆可以来自用户直接说明，也可以从多次交互中提炼。保存一次订票经历，与保存长期座位偏好，表达的是不同内容。

这里是借用人类记忆概念做工程设计。例如，保存订票步骤与人类学会骑自行车，在实现机制上并不相同。

**记忆设计的三套分类，可以组合使用。**

| 分类维度     | 回答的问题          | 本章涉及的类别                                 |
| -------- | -------------- | --------------------------------------- |
| **记忆层次** | 信息归哪一层、承担什么职责？ | 轨迹、用户长期记忆，以及记录任务阶段的业务状态                 |
| **存储格式** | 用什么形式表示？       | 简单笔记、完整段落、JSON 卡片、增强 JSON 卡片，以及可执行对象与函数 |
| **认知类型** | 内容表达的是什么？      | 具体事件、一般知识、行为流程                          |

例如，“用户偏好靠窗座位”属于**语义记忆**，可以用 **Simple Notes** 保存到**用户长期记忆**中。

存储形式也不会直接决定认知类型：代码对象里的旅行记录仍然描述具体事件；用自然语言写下的订票步骤，也可以作为程序记忆。
