# KV Cache 友好的上下文设计与注意力机制

**KV Cache 保存已经算过的 Key 和 Value，避免模型生成新 token 时反复重算历史。** 要充分复用缓存，上下文中已经处理过的前缀应尽量保持稳定。

以下以常见的、逐 token 生成文本的 Transformer 模型为例。

**注意力机制通过 Q、K、V，决定当前应该参考哪些信息。**

以“北京的天气怎么样”为例：

| 向量         | 大白话解释        | 示例中的作用               |
| ---------- | ------------ | -------------------- |
| Query，Q，查询 | 我现在要找什么信息？   | “怎么样”发出查询            |
| Key，K，键    | 我有哪些可供匹配的特征？ | “北京”和“天气”分别提供自己的匹配特征 |
| Value，V，值  | 我能提供什么具体信息？  | 提供地点、天气等信息，供当前查询汇总   |

每个位置都有自己的 Q、K、V，它们都是模型计算出的数字向量。“查询”“标签”“内容”只是帮助理解其分工。

注意力计算分三步：

1. **匹配打分**：当前 Q 与各位置的 K 做点积，再进行缩放。点积就是两串数字逐位相乘，然后相加。
2. **转换成权重**：用 `softmax` 将分数转换成总和为 1 的权重。
3. **汇总信息**：按权重对各位置的 V 加权求和。权重越大，该位置的信息在这次汇总中占比越高。

下面按词演示，**分词方式和权重均为示意，不是真实模型测量结果**：

| 当前查询 Q ↓ / 被参考的位置 K → |   北京 |    的 |   天气 |  怎么样 |
| --------------------- | ---: | ---: | ---: | ---: |
| 北京                    | 1.00 |    — |    — |    — |
| 的                     | 0.30 | 0.70 |    — |    — |
| 天气                    | 0.20 | 0.10 | 0.70 |    — |
| 怎么样                   | 0.35 | 0.05 | 0.55 | 0.05 |

每行权重之和为 1；`—` 表示不允许关注，权重为 0。

处理“怎么样”时，这次注意力汇总为：

$$
0.35V_{\text{北京}}
+0.05V_{\text{的}}
+0.55V_{\text{天气}}
+0.05V_{\text{怎么样}}
$$

这里主要参考“天气”，同时结合“北京”等信息。得到的是当前层汇总的信息，还需经过后续计算才能预测下一个 token。

**热力图的三角形，来自“只能看自己和前文”的限制。**

这个限制叫**因果遮罩（Causal Mask）**：当前位置不能读取后面位置的信息。即使模型一次处理整段输入，也要遵守这一限制。

因此，在相同模型和配置下，末尾新增 token 不会改变前面位置已经计算出的 K、V，这正是缓存能够复用的基础。

**使用 KV Cache 后，每一步只为新增位置计算新的 Q、K、V。**

处理过程是：

1. 首次处理输入时，计算并保存各注意力层的 K、V。
2. 处理新增 token 时，计算它的 Q、K、V，把新 K、V 追加到缓存。
3. 用新 Q 匹配缓存中的 K，再按权重汇总 V，继续预测下一个 token。

后续计算需要新的 Q；旧 Q 对应旧位置的查询，无需像 K、V 一样长期保留。[Hugging Face 缓存原理](https://huggingface.co/docs/transformers/cache_explanation)

缓存省掉了旧 K、V 的重复计算，**新 Q 仍然需要读取和匹配可见的历史 K、V**。所以长上下文仍有计算成本，保存更多 K、V 也会占用更多内存或显存。

**KV Cache 和 Prompt Cache 属于不同层次。**

| 概念                | 作用                                        |
| ----------------- | ----------------------------------------- |
| KV Cache          | 推理引擎保存历史位置的 K、V，供后续生成复用                   |
| Prompt Cache／前缀缓存 | 在不同请求之间，复用相同输入前缀对应的计算结果，通常建立在 KV Cache 之上 |

跨请求缓存主要减少输入处理阶段的工作，帮助缩短**首 token 延迟**，也就是从发出请求到收到第一个输出 token 的时间。费用是否降低、降低多少，取决于服务的计费规则。

**前缀中一处变化，会影响该位置及后续部分的缓存复用。**

用字母代表 token：

* 上次请求：`A B C D E`
* 本次请求：`A B X D E`

从计算原理上看，`A B` 可以复用，`X D E` 需要重新计算。后面的 `D E` 虽然相同，但它们依赖的前文已经改变。

实际能复用多少，还取决于缓存是否保留、服务是否支持，以及引擎的缓存块粒度。改动越靠前，通常影响越大；增加一个空格也可能改变 token 序列。

一个客服 Agent 教学案例展示了这种影响：每天处理 **10 万次对话**，在系统提示词中加入实时变化的 `Current time: {{now}}` 后，首 token 延迟从 **0.5 秒**升至 **3–5 秒**，月度推理账单接近翻倍。这些数字用于说明案例中的影响幅度，不能直接套用到其他部署。

原因是时间戳靠近输入前部，每次变化都让后面的大量内容失去复用机会。

**上下文设计可以遵循三条原则。**

1. **稳定内容放前面。** 系统提示词和核心工具定义尽量保持内容、顺序和格式一致；业务规则确实变化时正常更新。
2. **动态数据放后面。** 时间、用户状态、当前进度等变化内容，尽量作为新消息放在末尾，避免反复改写已有前缀。
3. **使用匹配模型的消息格式。** 通过 API 的结构化消息和工具字段传入内容，由服务套用模型对应的 Chat Template。

Chat Template，即**聊天模板**，负责把 `role`、`content` 等结构转换成模型熟悉的角色标记和 token 序列。直接手拼 `"USER: ... ASSISTANT: ..."`，可能偏离模型训练时使用的格式，影响角色识别和回答质量。[Hugging Face 聊天模板文档](https://huggingface.co/docs/transformers/chat_templating)

布局伪代码如下，其中各消息都应包含协议要求的角色和内容：

```python
# 固定规则放前，历史按顺序保留，最新状态放最后
request.messages = [system_message] + history + [status_message]

# 工具说明保持稳定，通过专门字段传入
request.tools = core_tool_schemas
```

消息格式是否正确与缓存是否命中，需要分别考虑：**模型需要熟悉的格式，缓存需要连续一致的 token 前缀。**

**注意力可视化可以帮助观察信息流，但需要结合模型和任务解释。**

`attention_visualization` 实验通过热力图观察每个位置关注了哪里。行表示当前查询，列表示被参考的位置，颜色越深表示权重越高。不同层、不同注意力头——并行计算注意力的分支——可能呈现不同分布。

常见观察包括：

* **注意力储存池（Attention Sink）**：开头少数 token 可能吸收很高的权重，即使其语义并不重要。实验描述中的部分观察超过 70%，具体比例随模型和观察位置变化。
* **思考内容之间的关注**：生成 `<think>` 中的新内容时，可以参考此前的思考文本和工具定义。
* **输出对思考内容的关注**：生成回答时，可以利用前面已经生成、且仍在上下文中的思考文本。分段的注意力分布可能形成多个三角形区域。

对注意力储存池的一种解释是：`softmax` 要求权重总和为 1；开头位置对几乎所有后续 token 都可见，因此容易在训练中成为接收部分权重的稳定位置。集中到哪里、集中多少，由模型学到的模式决定。[StreamingLLM：注意力储存池研究](https://arxiv.org/abs/2309.17453)

因此，**高注意力权重不能直接当作信息重要性的评分，三角形形状也不能单独证明推理质量。**

**信息放在哪里，也可能影响模型能否有效使用它。**

Nelson F. Liu 等人在 *Lost in the Middle: How Language Models Use Long Contexts*（TACL，2024）中，通过多文档问答和键值检索发现：相关信息位于长上下文开头或结尾时，模型表现往往更好；位于中间时，表现可能明显下降。这种位置影响通常称为 **Position Bias，位置偏好**。[论文](https://aclanthology.org/2024.tacl-1.9/)

据此，实践中可以把稳定的关键约束放在前部，把当前目标、最新状态和必要提醒放在末尾，再用具体任务验证效果。

模型根据当次输入中的指令、示例、工具定义和过程信息来完成任务，属于**上下文学习（In-Context Learning）**：通过提供上下文适应任务，过程中无需重新训练或修改模型参数。
