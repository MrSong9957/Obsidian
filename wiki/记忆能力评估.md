**好的记忆系统，要能记准事实、找全相关信息，并主动用这些信息帮上忙。** 先明确这些标准，才能判断一种记忆方案到底改善了什么。[^1]

**原文提出三个递进层级：**

| 层级              | 要做到什么                            | 原文示例                               |
| --------------- | -------------------------------- | ---------------------------------- |
| **基础回忆：记得准**    | 保存并准确找回用户明确提供的信息                 | 用户说“会员号是 12345”，以后询问时能准确返回         |
| **多会话检索：找全并判断** | 从不同时间、不同交流对象的多次对话中，找齐相关信息，判断哪些适用 | 用户有两辆车，说“预约保养”时，应找到两辆车的信息，再询问是哪辆   |
| **主动服务：想到相关需求** | 联系过去的信息，发现用户没有明确点出的需求或问题         | 用户预订国际航班时，主动检查几个月前留下的护照信息，发现快过期就提醒 |

第二层还要能分清**信息的状态和关联**：询问贷款进度时，要找到正在履行的合同，排除未生效的旧报价；取消洛杉矶之旅时，要关联这趟旅行的机票和酒店。

第三层的关键是**用户没有逐项提醒，系统也能想到**。例如手机坏了，主动汇总厂家保修、信用卡附加保修和运营商保险；报税时，主动找齐股票销售、自由职业收入和房产税等记录。

**检查这三层能力时，可以进一步看八个方面。** 下面八项是原文作者综合归纳的分类。

| 能力     | 大白话解释                   |
| ------ | ----------------------- |
| 个人信息保留 | 记住身份等长期个人信息             |
| 偏好追踪   | 记住用户长期喜欢什么、不喜欢什么        |
| 上下文切换  | 换话题后仍能接上相关背景            |
| 记忆更新   | 用户明确更改信息后，正确更新旧记录       |
| 多会话连续性 | 这次聊天结束，下次还能接着用以前的信息     |
| 复杂思考   | 把多条记忆放在一起，判断当前该怎么回答     |
| 时间感知   | 理解日期、“昨天”等相对时间，并能计算时间间隔 |
| 冲突解决   | 发现记录互相矛盾，并判断哪条信息适用      |

其中，**记忆更新关注“信息变了怎么办”，冲突解决关注“记录对不上怎么办”**，两者有交集。

原文参考的 **LoCoMo（长期对话记忆评测）**，使用平均约 300 轮、最多跨 35 个会话的长对话，测试问答、事件摘要，以及结合文字和图片的对话生成。上述八项能力和三层框架属于本书的归纳与设计。[LoCoMo 官方介绍](https://snap-research.github.io/locomo/)

**实验 3-1 通过“逐次更新记忆，最后回答新问题”来评估。原文仅提供实验设计，未提供实测结果。**

测试集每层 **20 个用例，共 60 个**，每个用例包含大量事实细节：

* 第一层通常只有一个会话。
* 第二、三层包含跨时间、跨对象的多个会话，**每个用例合计约 50 轮沟通**。

每个用例按以下流程处理：

1. **生成记忆**：读取第一个会话，提取需要记住的信息。
2. **更新记忆**：读取下一个会话，结合已有记忆进行修改。此时只能访问已有记忆和当前会话，**不能回看之前的原始对话**。
3. **回答问题**：所有会话处理完后，只根据最终记忆回答一个新的用户问题。
4. **比较评分**：让另一个大语言模型对照参考答案，评价回答质量。这叫 **LLM-as-a-judge，即“让模型当评委”**。

不能回看旧对话，是这项设计的关键：**早期信息如果没有记下来，后面就无法靠重读原文补回来。** 因此，它既检查能否提取重要信息，也检查多次更新后是否丢失或改错信息。

原文说明，测试用例和评估脚本收录在配套仓库的 `user-memory` 项目中。这段材料没有提供得分、评分细则或方案对比，因此无法据此判断哪种记忆系统更好。
