**压缩会损失一部分缓存复用机会，但能换来更短、更有用的上下文。** 关键是保留稳定的前缀，选择合适的时机压缩，而不是为了保住缓存，让上下文一直膨胀。[^1]

## 压缩会影响哪部分缓存

本节采用的做法是：**在两次模型请求之间，由框架整理消息列表，再发送下一次请求。**

1. **保持前面的系统指令和工具定义稳定。**
2. **用摘要替换体积较大的工具结果**，保留工具结果与原调用的对应关系。
3. **从最早发生变化的位置起，重新计算后面的内容**；此前不变的前缀仍有机会复用缓存。

例如，把对话中间的一篇长网页换成摘要，网页之前的缓存可以保留；摘要及其后面的消息需要重新计算。之后，这份新的上下文又可以成为可复用的前缀。

频繁改写历史会反复触发重算。因此，可以根据容量和信息质量，集中压缩一批记录。这里权衡的是：**这次重算的代价，能否换来后续多轮处理量的下降。**

## 六种策略怎样取舍

| 策略          | 怎样处理               | 主要取舍                       |
| ----------- | ------------------ | -------------------------- |
| **无压缩**     | 原始工具结果全部保留         | 细节完整，但容易占满上下文              |
| **个体摘要**    | 每个搜索结果分别总结，再拼接     | 页内信息较独立，但跨页面的重复内容可能保留下来    |
| **组合摘要**    | 合并多个结果，再生成一份摘要     | 便于去重、整理关系；摘要请求本身过长时也需要分批处理 |
| **上下文感知摘要** | 同时提供当前问题、已有信息和搜索结果 | 更容易保留后续任务真正需要的信息           |
| **感知摘要加引用** | 在针对性摘要中保留事实对应的来源链接 | 方便核查和追问，但链接不保证网页永远可访问或保持原样 |
| **自适应窗口**   | 初期保留原文，接近阈值时再批量压缩  | 保留早期探索空间，但前几轮需要携带较多原文      |

个体摘要和组合摘要也能理解文本，只是**没有充分利用当前任务和已知信息来决定保留什么**。

上下文感知摘要会把 `query`（当前问题）和 `context`（已有信息）交给摘要模型。例如，任务是查一位创始人目前在哪任职，就优先保留姓名、机构、职位、变更时间和来源；与此无关的生平介绍可以省略。

自适应窗口主要决定**什么时候压缩**，触发后仍需选择具体的摘要方法。

## 实验结果：先分清统计口径

实验 2-10 调研 OpenAI 联合创始人的职业状态，使用 Kimi K3，并人为设置 **128,000 token 的上下文预算**。这是实验预算，不是该模型真实窗口的上限。

下面是书中及配套项目报告的一次运行结果。**单次上下文预算与多轮累计 token 是两回事。**[实验说明](https://github.com/bojieli/ai-agent-book/tree/main/chapter2/context-compression)

| 策略    | 记录的累计 token |   字符比例 | 迭代次数 | 实验结果      |
| ----- | ----------: | -----: | ---: | --------- |
| 无压缩   |     166,043 | 102.1% |    5 | 预算保护触发，中断 |
| 个体摘要  |     276,608 |  10.9% |   12 | 成功        |
| 组合摘要  |      93,449 |   4.3% |   10 | 成功        |
| 上下文感知 |      40,157 |   3.0% |    7 | 成功        |
| 感知加引用 |     222,992 |   4.1% |   10 | 成功        |
| 自适应窗口 |     174,601 | 102.4% |    7 | 成功        |

这张表有三个容易混淆的地方：

* **累计 token 不等于完整费用。** 按当前代码，统计累计的是主 Agent 请求的输入和输出，生成摘要的独立模型调用没有并入。比较总成本，还需要计入摘要调用及缓存计费。[统计实现](https://github.com/bojieli/ai-agent-book/blob/main/chapter2/context-compression/experiment.py)、[摘要调用实现](https://github.com/bojieli/ai-agent-book/blob/main/chapter2/context-compression/compression_strategies.py)
* **字符比例不等于 token 节省比例。** 本实验按“处理后字符数 ÷ 原始字符数”统计。3% 表示该项字符量约剩原来的 3%，不表示整个任务只花原来 3% 的 token。
* **102.4% 不能当作窗口化后的最终压缩效果。** 无压缩结果加入标题、链接等内容后，长度可以略有增加；窗口化策略的这项统计又未计入后续对历史消息的批量压缩。[相关实现](https://github.com/bojieli/ai-agent-book/blob/main/chapter2/context-compression/agent.py)

本次记录中，**上下文感知策略的主 Agent 累计 token 最少，7 轮也与自适应窗口并列成功组最少**。无压缩的 5 轮则是提前中断，不能理解成效率更高。

原文的“减少约 76%”来自 40,157 与 166,043 的比较；由于基线没有完成任务，且统计未包含全部摘要开销，**不能把它直接解释为完成同一任务的总费用降低了 76%**。一次运行也不能确定所有任务下的策略排名。

## 自适应窗口怎样工作

原文采用三个机制：

1. **阈值触发**：上下文用量超过预算的 80% 时启动压缩。实验中，128,000 × 80% = **102,400 token**。
2. **批量处理**：集中压缩尚未处理的工具结果，减少反复改写历史。
3. **跳过已压缩内容**：给结果添加 `[COMPRESSED]` 标记，后续由代码检查并跳过，避免这套机制反复摘要同一内容。

实际实现时，应检查**即将发送的完整输入**，压缩后再次确认长度，并为模型回复预留空间。仅凭上一轮用量，可能漏掉刚返回的一大段工具结果。

80% 是这次实验的设置。触发时机还应考虑单次工具输出大小和信息质量；即使空间尚够，已经出现遗漏条件、重复劳动等问题，也可以提前整理上下文。
