**记忆框架要把对话变成以后能用的信息。主要取舍是：什么时候整理新旧信息、怎样保留历史，以及需要时怎样找回来。**[^1]

**Mem0 的演进，把处理新旧信息的重点从写入阶段移到了查询阶段。**

| 对比项    | 2025 年论文与 v2                               | 2026 年 v3 新算法        |
| ------ | ------------------------------------------ | -------------------- |
| 写入过程   | 模型提取事实，检索相近旧记忆，再让模型决定如何处理                  | 事实提取合为一次模型调用，去重后追加保存 |
| 自动处理方式 | `ADD` 新增、`UPDATE` 更新、`DELETE` 删除、`NOOP` 不变 | 只做 `ADD`，新旧事实可以并存    |
| 信息变化时  | 写入时修改或删除旧信息                                | 保留变化过程，查询时判断哪些信息适用   |
| 主要收益   | 记忆库较简洁，减少重复和矛盾                             | 减少提取阶段的模型调用，避免自动覆盖历史 |
| 主要代价   | 错误更新可能损失信息；恢复依赖是否另有原始记录或历史版本               | 记录持续增加，更依赖检索和时间判断    |

例如，用户先说“我住在北京”，后来又说“我搬到了上海”：

* **v2** 可以把居住地更新为上海。
* **v3** 保留两条带时间背景的记录。问“现在住哪里”时使用上海，问“以前住哪里”时仍能找到北京。

v3 的**混合检索**会综合多种线索：意思是否相近、关键词是否匹配，以及是否涉及同一人物或地点。**BM25** 就是一种按关键词匹配程度打分的方法，**Top-k** 表示取排名靠前的 k 条记录。

具体到当前开源版，官方说明：先由语义检索产生候选，BM25 和实体匹配帮助调整排名；这些附加能力还受依赖和配置影响。只追加指的是自动提取流程，系统仍可通过专门接口删除记忆。[开源版迁移指南](https://docs.mem0.ai/migration/oss-v2-to-v3)

新算法也会记录 Agent 提供的信息，例如“已完成预订”。但**记住这句话，只能证明它说过；确认预订成功仍需要工具结果或外部状态作为证据。**

图记忆也要区分版本：

* **2025 年的 Mem0-g** 用人物、地点等实体及其关系组成图，帮助关联多条记忆。[原始论文](https://arxiv.org/html/2504.19413v1)
* **当前开源版 OSS** 已移除外部图存储和搜索结果中的 `relations` 字段；托管平台另有内置图记忆。不能把历史论文方案直接当作当前开源版能力。[迁移说明](https://docs.mem0.ai/migration/oss-v2-to-v3)

**Mem0 官方报告了评测提升，但这些数字需要连同来源和条件一起看。**

| 评测集         | 旧算法得分 | 新算法得分 |     增加 |
| ----------- | ----: | ----: | -----: |
| LoCoMo      |  71.4 |  92.5 | 21.1 分 |
| LongMemEval |  67.8 |  94.4 | 26.6 分 |

上表来自官方算法文章：**每题一次检索、一次回答，不进行多轮 Agent 循环；结果来自托管平台，包含开源版没有的优化。** 这是官方报告，不能视为开源 SDK 的复测成绩。[算法文章](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)

官方迁移指南另列出 91.6 和 93.4，页面之间没有说明差异原因，因此引用成绩时应保留具体来源。[平台迁移指南](https://docs.mem0.ai/migration/platform-v2-to-v3)

**Memobase 把重点放在“整理用户画像，再配上事件时间线”。**

它主要保存两部分：

* **用户画像（Profile）**：姓名、兴趣、职位等相对稳定的信息，按“主题 → 子主题”组织，例如 `basic_info.name`、`work.title`。开发者可以配置需要收集哪些信息。
* **事件记忆（Event Memory）**：用户经历过什么、什么时候发生，用来回答“我们上次讨论预算是什么时候”等问题。

它采用**缓冲批处理**：对话先暂存，积累到一定规模或闲置一段时间后，再统一提取记忆；也可以手动触发。查询时读取已经整理好的画像和事件，减少临时处理工作。[Memobase 官方仓库](https://github.com/memodb-io/memobase)

这样可以摊薄处理成本，但也意味着**新消息进入缓冲区后，长期记忆不一定立即更新**。需要马上使用最新信息时，应触发并等待处理完成。一次批处理也可能包含多次模型调用。

**多类型记忆协同是一种参考设计，不代表这两个框架已经完整实现。**

| 组成       | 保存和处理什么                       |
| -------- | ----------------------------- |
| **工作记忆** | 当前任务需要的信息：任务状态、近期交互，以及取回的长期记忆 |
| **情景记忆** | 具体事件，并附带时间、主题、情感标记、任务标识等信息    |
| **语义记忆** | 可以反复使用的事实、偏好和一般知识             |
| **程序记忆** | 可复用的做事步骤和行为流程                 |

这里新增的重点，是给事件加上**元数据，也就是帮助查找和理解事件的标签**。例如，查“上次讨论预算是什么时候”，可以结合主题“预算”、所属任务和时间排序，找到对应事件。

工作记忆与长期记忆双向配合：当前交互中的重要信息被选出来长期保存；新任务开始时，再把相关长期记忆加载到当前上下文。

**轨迹保留发生过什么，工作记忆组织现在需要什么。** 轨迹按时间追加事件；工作记忆可以筛选、压缩轨迹内容，也可以加入从长期记忆中取回的信息。

这些分类取决于内容：用户画像通常接近语义记忆，事件时间线接近情景记忆，Mem0 的事实条目也可以描述具体事件。工程上按需求选择组件即可：长期偏好需要画像，追问历史需要事件记录，复用做事方法才需要程序记忆。
