## 一句话理解

**上下文工程解决的是：怎样把 Agent 此刻真正需要的信息，准确地送到模型面前。**

模型再聪明，看不到项目规则、代码结构和执行结果，也只能瞎猜。

## 为什么上下文这么重要

模型只有通用能力，不天然知道你的：

* 代码和架构；
* 业务规则；
* 团队开发流程；
* 当前环境状态；
* 前面已经做过什么。

所以：

> **模型能力决定“会不会思考”，上下文决定“有没有条件把事情想对”。**

Coding Agent 至少需要三类信息：

| 信息   | 缺失后的典型问题              |
| ---- | --------------------- |
| 代码信息 | 写出的代码能运行，但破坏现有架构或风格   |
| 流程规范 | 跳过测试、错误提交、违反 CI/CD 流程 |
| 环境信息 | 本地能跑，换环境立即失败          |

这里进入 Context 的只是**环境的描述、观察结果和配置**，不是 Environment 本身。

## Context Engineering 在 Harness 里的位置

Harness 负责在每次模型决策前，整理模型应该看到的信息。

典型 Context 包括：

```text
System Prompt
工具定义
历史 user / assistant 消息
工具调用与工具结果
当前任务需要的代码、文档、环境状态
↓
模型做下一步决策
```

所以 Context Engineering 不是：

> 往 Prompt 里尽可能多塞东西。

而是：

> **在正确的时候，把正确的信息，以正确结构提供给模型。**

信息太少 → 模型瞎猜。

信息太多、太乱 → 关键内容被噪声淹没，成本也更高。

## ReAct 怎么理解 Context

ReAct 可以简化成：

```text
观察 → 行动 → 新观察 → 新行动 → ...
```

例如：

```text
用户：北京今天天气怎么样？
      ↓
模型：调用天气工具
      ↓
工具：23°C，晴
      ↓
模型：北京今天晴，23°C
```

到了最后一步，模型做决定时看到的不是单独一句：

```text
23°C，晴
```

而是类似：

```text
用户问了什么
→ 自己调用了什么工具
→ 工具返回了什么
```

这些历史共同构成当前的 `cₜ`。

因此 ReAct 的核心关系可以理解成：

> **下一步 Action = 根据截至现在积累的 Context 做出的决定。**

## 技术上 Context 怎么送进大模型

本质上就是：

> **Harness 把各种信息整理成结构化 API 输入，最终编码成 token 序列交给 Transformer。**

例如 API 层可能类似：

```text
system:
  你是 Coding Agent，修改代码后必须运行测试。

tools:
  read_file(...)
  run_command(...)

user:
  帮我修复这个 bug。

assistant:
  [tool_call] read_file("src/main.rs")

tool:
  文件内容……

assistant:
  ← 模型从这里继续生成
```

底层最终都会变成一串 token：

```text
[token][token][token][token]...
```

Transformer 的注意力机制再从这些 token 中判断哪些信息与当前生成最相关。

一个重要细节是：

> **LLM API 通常本身不替 Agent 保存完整工作状态。**

所以每轮调用时，Harness 都需要重新构造足够的 Context：

```text
历史消息
+ 工具结果
+ 当前状态
+ 必要规则
→ 新一轮 API 请求
```

不能为了节省 token 随便删除历史。可以摘要、压缩，但**不能丢掉会影响下一步决策的信息**。

## 真正的工程问题

因此上下文工程后面所有技术，本质都在解决同一个问题：

> **怎样用尽量少的 token，让模型仍然掌握做出正确下一步决策所需的全部关键信息？**

这也是为什么会出现：

* Context 布局；
* 动态工具加载；
* 状态栏；
* 检索；
* 摘要；
* Context Compression。

它们不是为了单纯缩短 Prompt，而是在做**信息供给管理**。

## 组织层面的关键洞察

上下文工程不只是 Agent 技术问题。

如果公司的关键知识都存在：

* 老员工脑子里；
* 私聊里；
* 没有记录的口头决定里；

Agent 根本拿不到这些 Context。

Linux 内核这类长期远程协作项目值得借鉴的地方，就是大量知识通过公开讨论、文档和历史记录沉淀下来。

所以：

> **AI 原生团队首先要做的，往往不是部署 Agent，而是把隐性知识变成可检索、可传递的显性 Context。**

OpenAI 研究员翁家翌强调的也是这一点：人与人、人与 AI 协作中的很多问题，本质上来自 **Context 不一致**。

### 最值得记住

**Agent 像一个永远刚入职的新员工。**

Harness 的上下文工程，就是每次做决定前，把它现在需要知道的资料重新摆到桌面上。
