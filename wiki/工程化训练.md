## 测试需求文档

功能实现前，先让 AI 用自然语言回答：

1. **正常情况**：哪些核心行为必须成功？
2. **失败/边界情况**：最可能怎么坏？
3. **不变量**：哪些事情绝对不能发生？
4. **证明方式**：分别用什么层级的测试证明？

一个比较合适的结构：

```text
# CLI Test Spec

## 1. Session Reset

### 正常行为

T-001
执行 /clear 后：
- 当前 transcript 清空
- 回到启动界面
- 当前 model 保留

T-002
执行 /new 后：
- 行为与 /clear 等价

### 边界情况

T-003
空 session 执行 /clear：
- 不报错
- UI 保持正常

T-004
长 transcript 后执行 /clear：
- 所有旧消息消失

### 不变量

T-005
/clear 绝不能：
- 改变当前 model
- 恢复旧 session 内容
- 留下旧 composer/status 内容

### 真实环境要求

T-006
必须使用真实 PTY 验证：
- transcript wipe
- composer/status 清理
- Windows ConPTY 渲染

原因：
普通组件测试不能证明真实终端最终表现。
```

这已经够了。

我甚至不建议每次单独生成正式 Markdown 文件。

多数功能直接把这段作为 **Plan / Agent 指令的一部分**即可。

只有比较大的功能、重要协议、跨模块设计，才值得形成正式测试设计文档。
