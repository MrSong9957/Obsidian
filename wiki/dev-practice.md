# 开发实践

## TDD 原则

- 安全函数（路径校验、权限检查）：第一个测试就是"必须被拦住的那个 case"
- 工具函数：先写 pytest 覆盖正常/边界/错误三路，再写实现
- 有参考代码时，逐行对齐关键步骤，不是"差不多"就行

> 详细内容见 sources/dev/dev-practice.md

## 调试方法论

- **永远先观察，再假设**：打印实际值，不猜测；创建最小诊断脚本
- **三段式可观测性**：before/after/failed 事件日志，append-only JSONL，最轻量的调试手段
- **先确认操作上下文，再假设代码 bug**：用户描述的"操作现场"是最关键线索

> 详细内容见 sources/dev/dev-practice.md

## KV 缓存设计

- 固定内容（工具定义、角色描述、常量规则）放前缀最前
- 动态内容（对话上下文、用户输入、临时指令）放后面
- 固定前缀中不要插入时间戳、计数器等变化内容
- 工具描述文本稳定后不改措辞，改动导致缓存失效

> 详细内容见 sources/dev/dev-practice.md

## 提示词 7 条原则

- 用禁令代替指令（堵死漏洞比正向鼓励可靠）；每条禁令写明原因
- 设置唱反调角色：AI 解释而非行动时，立即停止解释并执行验证
- 不知道就说不知道，禁止猜测；先看再改，必须先读取文件才能编辑
- 不要画蛇添足（三行重复好过过早抽象）；信息按需提供，避免一次全给

> 详细内容见 sources/dev/dev-practice.md

## Claude 协作提示词技巧

10 条从协作角度优化 Claude 输出质量的方法：

| 技巧 | 核心要点 |
|------|----------|
| 情境简报 | 先给背景再抛问题，有效输出提升 41% |
| 要思维过程 | 要求一步步推理，标出假设，不要死板结论 |
| 诚实约束 | 明确要求指出缺陷，不要软化 |
| 角色具体化 | 给具体经验画像，跳过常规建议 |
| 魔鬼代言人 | 要求摧毁方案，找出所有错误假设和风险 |
| 范围锁定 | 划定边界，宁要空白回答不要自信的错误 |
| 格式指令 | 精确指定输出结构，避免冗余 |
| 假设审计 | 追问隐藏假设，验证逻辑底层风险 |
| 压缩循环 | 每 5-6 轮总结：问题、决定、未解决事项 |
| 前期验尸 | 假设 6 个月后失败，找出最可能原因 |

**核心逻辑**：输出质量取决于输入信息量，视为协作者而非搜索框。
