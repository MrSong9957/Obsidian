**Agent 状态栏，就是框架提前整理好“现在做到哪了、用了多少次、还剩什么”，在请求模型时一起交给它。** 这些描述当前情况的辅助信息，叫作元信息。这里的状态栏主要给模型阅读，也可以展示给用户。[^1]

## 为什么完整历史还不够

假设系统规定：给同一个商家最多打三次电话。

Agent 已经给 Xfinity 打了三次，中间穿插着大量搜索结果。用户又说：“再打一次催一下。”

虽然三次通话都保存在执行记录中，但模型仍要找出这些记录、确认对象、累计次数，再判断是否达到上限。记录一长，就可能漏数或数错。

**保存了事情的经过，不等于已经整理出当前的结果。** 状态栏补上的就是这一步。

## 框架怎样维护状态栏

框架是负责执行工具、保存记录的程序。它可以：

1. **记录变化**：每次实际拨打电话，就更新对应商家的次数。
2. **整理状态**：结合次数上限、工具结果和待办清单，算出当前进度。
3. **提供给模型**：下次请求模型前，把最新状态放在上下文末尾。

沿用原文场景，状态摘要可以写成下面这样，时间为示例：

```text
<agent_status>
任务：联系 Xfinity 降低月费
拨打次数：3 次，上限 3 次
约束检查：已达上限，不能继续拨打
已完成：联系商家；确认降价至每月 59 美元
待办：向用户汇报结果
当前时间：2025-09-14 10:30
</agent_status>
```

模型可以直接使用“已达上限”这个结果，减少重新翻记录的工作。

也可以在电话工具的返回结果里直接附上：“这是本次任务中第 3 次拨打 Xfinity。”`<agent_status>` 只是标记文本范围的写法；实际请求仍要使用接口支持的消息结构。

## 为什么有帮助

状态栏主要减少两类工作：

* **重复统计**：原来要从多条通话记录中算出“三次”，现在由程序维护计数，模型直接读取。
* **寻找重点**：任务目标、剩余步骤和限制集中放在一起，减少它们被大量工具结果淹没的机会。

模型仍然能够统计和归纳，但这些工作不必每轮都重做。KV Cache 保存的是模型计算的中间结果，不能把它当作一个可靠的业务计数器。

把摘要放在上下文末尾，有助于突出最新状态；但不能简单理解成“位置越靠后，模型就一定越重视”。

## 实验说明了什么

原文的**实验 2-8 报告了对照观察**：使用 `attention_visualization` 项目，让 Qwen3-0.6B 模型处理同一段通话历史，比较有无状态栏的表现。

| 对照条件  | 原文报告的观察                               |
| ----- | ------------------------------------- |
| 没有状态栏 | 注意力分散在通话记录中，生成的思考内容包含计数过程，更容易继续拨打     |
| 添加状态栏 | 注意力更多集中在摘要上，直接使用“三次、已达上限”的信息，更稳定地停止拨打 |

这些是作者报告的实验观察。热力图能展示注意力分布，但单靠它不能完整解释模型为什么作出某个决定。[原文章节](https://bojieli.github.io/ai-agent-book/book/chapter2/)

相关研究还报告：在其测试任务中，状态摘要能明显提高小模型准确率，并让部分大模型的推理量、延迟和费用降低约一个数量级，也就是约降至原来的十分之一。**这是特定测试条件下的结果，不能保证所有任务都有十倍改善。**[研究说明](https://01.me/research/context-distillation/)

实际使用时，计数和时间应由程序准确维护，进度应根据真实结果更新。摘要只保留了部分信息，需要查细节时仍可能用到原始记录。对于“最多拨打三次”这样的硬限制，还应由程序在执行工具前检查并拦截；状态栏负责帮助模型作出正确决定。
