**状态会不断变化。更新时，要权衡两笔开销：删除旧状态后重算部分消息，或者保留旧状态并在后续请求中反复携带。**[^1]

## 两种更新方式

前缀缓存只能复用从开头起连续相同的内容。中间某处变了，即使后面的文字没变，也通常需要重新计算后面的部分。

| 方式       | 怎样更新              | 主要代价                    | 更适合                      |
| -------- | ----------------- | ----------------------- | ------------------------ |
| **每轮替换** | 删除上一份状态，在末尾加入最新状态 | 从旧状态原位置开始，后面的消息失去缓存复用机会 | 状态较大、更新次数多，或两次更新之间的消息较少  |
| **持续追加** | 保留旧状态，每轮只在末尾加入新状态 | 旧状态不断累积，占用上下文，也产生缓存读取费用 | 状态很小、两次更新之间的消息很多，且会话长度受控 |

例如，旧状态写着“已打两次电话”，后面又新增了第三次通话记录。删除旧状态，就改变了第三次记录前面的内容，因此这条记录需要重新计算；**旧状态之前的稳定历史仍可复用**。

持续追加则保留“两次”那份旧状态，再加入“三次”的新状态。前缀保持不变，但需要明确让模型以最新状态为准。

Claude Code 的一个实际例子是：已读文件发生变化后，追加 `<system-reminder>` 提醒，而不回头修改先前的读取记录。这体现了追加思路；会话压缩、清理历史则是另外的操作。[官方说明](https://code.claude.com/docs/en/prompt-caching#editing-files-in-your-repository)

## 怎样粗略比较费用

**缓存命中也可能收费，所以“缓存更稳定”不一定等于“总费用更低”。**

可以沿用原文的简化估算。Token 是模型处理文本的计量单位，先定义：

* `S`：每份状态的 token 数。
* `R`：两次状态更新之间新增的消息 token 数。
* `N`：总共注入多少份状态，包含第一份。
* `a`：缓存输入价格占普通输入价格的比例，例如一折就是 `0.1`。

把普通输入每 token 的价格记为 1，只比较两种方案不同的那部分费用：

```text
替换的额外费用 ≈ (N - 1) × (1 - a) × R
追加的额外费用 ≈ a × S × N × (N - 1) ÷ 2
```

第一行计算：那些本来可以按缓存价读取、现在需要重新计算的消息，多花了多少钱。

第二行计算：旧状态在以后每轮都要再次携带。第二轮多带一份，第三轮多带两份，累计读取次数越来越多。

**自拟算例：** 每份状态 100 token，每轮新增消息 1,000 token，共注入 10 份状态，缓存价格为一折：

| 方案 | 额外费用，相当于多少普通输入 token 的费用 |
| -- | -----------------------: |
| 替换 |                    8,100 |
| 追加 |                      450 |

这个例子中追加更便宜；会话继续变长，旧状态的累计费用也会继续增长。

这只是粗算：假设状态和消息长度大致固定、缓存能命中，未计缓存写入费、上下文容量及旧状态造成的干扰。实际选择要结合服务商计费和运行数据。

## 五种实用的状态信息

| 技术          | 实现要点                                         | 帮助模型解决什么问题        |
| ----------- | -------------------------------------------- | ----------------- |
| **时间戳**     | 在用户消息、工具结果产生时附上时间；历史时间不反复改写，也可使用明确标注的模拟时间做演示 | 分清事情发生的先后、间隔和日期   |
| **工具计数器**   | 用代码维护字典，例如 `{"read_file": 3}`，把次数附在结果中       | 配合错误信息，识别反复尝试同一操作 |
| **TODO 清单** | 保存任务编号、内容、状态和时间戳                             | 记住已完成和未完成的步骤      |
| **详细错误**    | 提供错误类型与说明、参数 JSON、调用栈和修复建议；调用栈说明错误经过了哪些函数    | 根据失败原因调整做法，减少盲目重试 |
| **系统状态**    | 提供实际工作目录、操作系统、Shell 和 Python 版本等             | 选择适合当前环境的路径和命令    |

原文的 TODO 实现提供两个工具：

* `rewrite_todo_list`：重写任务清单。
* `update_todo_status`：更新某项任务的状态。

四种状态分别是：`pending` 待处理、`in_progress` 进行中、`completed` 已完成、`cancelled` 已取消。

这些信息需要配合使用。例如，读取文件失败后，模型可以结合错误中的路径、当前工作目录和尝试次数，决定先检查目录，再寻找正确文件。**次数本身不能保证模型自动改变策略。**

工作目录也必须与实际执行环境一致。一次 `cd` 是否影响下次工具调用，取决于是否复用 Shell，或者框架是否保存并应用了新目录。

## 实验结果怎样理解

配套项目位于 `chapter2/system-hint`，包含五项功能的独立开关和真实对照测试。[项目说明](https://github.com/bojieli/ai-agent-book/tree/main/chapter2/system-hint)

原文报告过“启用 TODO 后，平均迭代次数从 21 次降至 15 次”和“详细错误使恢复成功率从 60% 升至 95%”。**这两组数字属于原文的历史报告；仓库公开的后续复测没有复现这些幅度，也保留了无明显改善或表现下降的结果。** 因此，不能把这些数字当作通用效果保证。[实验记录](https://github.com/bojieli/ai-agent-book/blob/main/chapter2/EXPERIMENT_LEDGER.md)

状态栏无需修改模型参数，信息也便于人工检查；实际收益仍取决于模型、任务和状态质量。

## 维护时要守住两点

**第一，状态尽量由代码准确维护。** 次数、时间和状态变更都有明确记录，适合由程序统计。如果需要模型处理自然语言，可以让它逐条提取事实，再由代码校验、汇总。错误或被篡改的状态会误导后续决策。

**第二，摘要没有保留的细节，模型无法凭空恢复。** 例如，“已经打了三次电话”能回答次数问题，却不能回答“第二次报价是多少”。

只有确认摘要覆盖了后续任务需要的信息，才适合把对应原始记录移出当前上下文；仍可能需要的细节，应保留或能够重新取回。**状态栏用于替代较长的原始记录时，才会减少上下文长度；单纯追加状态仍会增加输入量。**
