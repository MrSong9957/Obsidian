模型能理解用户的任务，但“怎样收费、什么算成功、失败后怎么办”取决于具体业务。**系统提示词需要传达已经确定的业务规则，减少模型自行解释的空间。**[^1]

**业务规则要明确适用条件和处理结果。** 以帮用户打电话办事的 Agent 为例，只写“根据任务选择合适的计费类型”，容易让模型把退货、取消订阅和协商降价都归为“省钱”。

可以把分类边界写成下面这样。以下收费方式和比例均为案例设定：

| 用户任务           | 计费规则                                                      | 分类依据        |
| -------------- | --------------------------------------------------------- | ----------- |
| 通过谈判降低现有账单     | `percentage_based_one_time`：按约定范围内节省金额的一定比例，收取一次性佣金，如 20% | 通过谈判获得降价    |
| 退货退款           | `fixed_fee`：固定服务费                                         | 取回已支付的钱     |
| 取消 Netflix 等订阅 | `fixed_fee`：固定服务费                                         | 终止服务，停止后续付费 |
| 预订餐厅等代办任务      | 按复杂度收取固定服务费                                               | 提供代办服务      |

规则应直接写明：**退款和取消服务使用 `fixed_fee`，不得使用 `percentage_based_one_time`。** 这样，“以后不用付钱”就不会被模型自行解释为可抽佣的节省额。

**费用怎么算、是否接单、失败是否退款，需要分别规定。**

* **费用计算方式**：采用提成还是固定费用。
* **接单条件**：哪些任务可以承接，哪些应拒绝，信息不足时怎么办。
* **收款与退费条件**：何时收取 Agent 服务费，任务失败后是否退还。

案例中的“困难任务预收且不退”用于筛选请求。它与“办不成就退款”必须有明确的适用范围，不能同时作为无条件承诺。

成功率也需要统一评估依据和步骤。例如，若设定“高于 60% 使用可退款模式，低于 30% 拒绝”，还必须规定 **30%～60%（含两个端点）** 如何处理，以及无法估计时怎么办。模型随口给出的百分比，不能直接当成经过验证的成功率。

**金额规则必须固定计算口径。** 至少讲清基准金额、计算周期、费率，以及何时舍入。

自拟示例：按一个月核算，现有账单从 150 美元谈到 120 美元，节省 30 美元；按 20% 提成，佣金为 6 美元。如果账单仍是 150 美元，只是假设未来可能涨到 180 美元，就不能把这 30 美元算作实际节省。

通话费用也一样：若按每分钟 0.05 美元计费，应明确**全部通话汇总后，再四舍五入到整数美元**；不足一分钟如何计费，也要事先规定。逐通电话先舍入再相加，可能得到不同金额。

业务负责人确定收费边界和例外，工程师参与澄清并落实到提示词与程序。金额计算和收费条件应由程序校验，再根据实际任务结果、用户反馈持续修正规则。

**Few-shot 示例用具体答案展示期望模式。** Few-shot（少样本提示）是在提示词中提供少量“输入—预期输出”示例，让模型参考它们处理新输入。这属于**上下文学习**：模型利用当前看到的示例，不需要重新训练。[Google 提示设计指南](https://ai.google.dev/gemini-api/docs/prompting-strategies#zero-shot-vs-few-shot-prompts)

适合使用示例的情况包括：

* 文案风格、客服语气难以准确描述；
* 报告格式需要保持一致；
* 分类边界容易混淆，例如“协商降价”和“取消订阅”。

例如，可以把前面的业务规则写成两组演示：

```text
输入：帮我把现有网费谈低一些。
预期输出：percentage_based_one_time

输入：帮我取消 Netflix 订阅。
预期输出：fixed_fee
```

这组示例展示了容易混淆的边界。示例必须与规则一致，输出格式也应统一。

可以先用 **2～3 个有代表性的示例**，再根据实际效果增减。优先覆盖不同情况和边界，避免堆叠相似例子；如果规则已经足够清楚、结果也稳定，就不必增加示例。数量没有统一最优值，过多示例可能让模型过度套用示例中的模式。[Google 示例数量指南](https://ai.google.dev/gemini-api/docs/prompting-strategies#optimal-number-of-examples)

**示例可以放在系统提示词，也可以组成演示对话。**

| 位置     | 组织方式                                | 适用情况            |
| ------ | ----------------------------------- | --------------- |
| 系统提示词  | 明确标注“示例”，列出输入与预期输出                  | 多个请求共用同一套规则和示例  |
| 消息列表开头 | 用成对的 `user`、`assistant` 消息演示，再接真实请求 | 按任务或会话类型选择不同示例集 |

使用无状态 API 时，后续请求仍需携带示例或包含示例的消息历史；只在首轮发送，不代表模型以后自动记得。

**示例的稳定性会影响缓存，但动态选例并不必然让全部缓存失效。**

KV Cache 保存模型处理前文时的中间计算结果；这里讨论的跨请求复用称为 **Prompt Cache**。它复用的是请求开头连续相同的内容，也就是“共同前缀”。

前文变化会影响后续计算，因此变化位置及其之后不能继续沿用原前缀的缓存。**变化位置之前的稳定内容，如果已经缓存且满足服务商要求，仍有机会复用。** 含义相同但措辞、顺序或格式不同，也可能破坏精确匹配。[Anthropic 缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#best-practices-for-effective-caching)

例如：

| 请求 | 固定前缀      | 后面的动态内容       |
| -- | --------- | ------------- |
| A  | 固定规则＋固定示例 | 检索示例 A＋用户任务 A |
| B  | 固定规则＋固定示例 | 检索示例 B＋用户任务 B |

可以按任务类型复用固定示例集，提高同类请求的缓存机会；需要动态检索示例时，将其放在固定内容之后。是否采用动态选例，应比较回答质量的改善与增加的成本、延迟，实际命中还受缓存有效期、最低长度和相关配置影响。
