模型有通用能力，但不会自动知道你的业务规则、表达习惯和验收标准，需要把这些要求明确告诉它。[^1]

**系统提示词（System Prompt）是 Agent 的“工作手册”**：规定它负责什么、怎样回答、遵守哪些限制、按什么流程工作。调用模型的 API（程序接口）时，有些接口将它放在 `role: "system"` 的消息中，有些使用独立的 `system` 参数。[Anthropic 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#give-claude-a-role)

提示工程（Prompt Engineering）就是设计、测试和调整模型收到的指令、背景与示例，让结果更符合需求；系统提示词是其中一部分。[Google 说明](https://cloud.google.com/discover/what-is-prompt-engineering)

一个实用的检验方法是：**让不了解任务的人照着提示词做事，看他是否知道该做什么、按什么顺序做、怎样算完成。**

**表达要求要具体到能判断是否做到。** “简洁一点”“表现专业”解释空间很大，可以改成具体行为。例如：

```text
- 先给结论，再补充必要说明。
- 普通问答少于 4 行。
- 无法完成时，用 1–2 句话说明原因和需要补充的信息。
```

这些限制要适合任务：详细教程需要足够的解释，不能为了行数省略关键步骤；失败原因也应按需要简短说明，帮助用户继续操作。

`MUST`、`NEVER` 等大写词可以用于强调，但效果取决于模型和场景，不能保证比普通措辞更有效。优先把条件和要求写清楚，避免反复使用强硬措辞。[Anthropic 指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#tool-usage)

**结构化格式帮助区分“哪一块是什么”。** 当提示词混有规则、背景和示例时，清楚的分组能减少内容混淆。

| 格式           | 写法              | 主要作用              |
| ------------ | --------------- | ----------------- |
| Markdown     | `#`、`##` 标题和列表  | 展示章节层次，方便阅读与维护    |
| XML（可扩展标记语言） | `<标签名>内容</标签名>` | 标出内容边界，用标签名说明内容用途 |

下面是将两者组合的**提示词示例**：

```text
# 工具使用规范

## 文件操作
<file_operation>
- 读取前检查文件是否存在、是否可访问。
- 修改配置文件前先备份；备份失败则停止修改。
</file_operation>

## 网络请求
<network_request>
- 每次请求超时为 30 秒。
- 对允许重试的请求，失败后最多重试 3 次。
</network_request>
```

标题组织层级，标签圈定规则所属的内容块。标签名应直观、一致；只有内容本身有上下级关系时，才需要嵌套。[Anthropic XML 指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#structure-prompts-with-xml-tags)

XML 标签仍是模型读取的文本，不会自动让规则得到严格执行，也不保证比清楚的普通文字更准确。简单提示用 Markdown 即可，内容复杂时再增加标签。

**有先后依赖的任务，要把规则组织成流程。** 零散规则说明“要遵守什么”，流程进一步说明“什么时候做、先做什么、失败后怎么办”。

SOP（标准操作流程）就是把任务整理成可重复执行的步骤。下面是文件处理的**流程示例**：输入是文件路径与处理要求，输出是处理后的文件，以及成功或失败的结果。

| 步骤     | 动作                       | 继续或停止的条件       |
| ------ | ------------------------ | -------------- |
| 1. 检查  | 检查文件是否存在、能否访问            | 失败则记录原因并停止     |
| 2. 分类  | 根据扩展名和内容判断文件类型           | 确定采用哪种处理方式     |
| 3. 预处理 | 配置文件先备份；适合分块处理的大文件采用流式处理 | 必要准备失败则停止      |
| 4. 执行  | 按文件类型和任务要求处理内容           | 执行失败则报告错误      |
| 5. 验证  | 检查预期改动是否完成、应保留的内容是否完整    | 通过才报告成功，否则报告失败 |

**流式处理**是分批读取和处理文件，避免一次把整份文件放进内存。原例中的“大于 1 MB”只是示例阈值，实际要根据内存和处理任务确定。配置文件也可能很大，因此“先备份”和“分块处理”可以同时适用。

流程把依赖关系写清楚：备份完成才能修改，验证通过才能报告成功。全程适用的约束可以单独列出，具体规则放在对应步骤，避免到处重复。

写完后，用正常文件、路径不存在、备份失败等情况试运行，检查 Agent 是否按要求继续或停止。这样才能判断提示词是否有效。
