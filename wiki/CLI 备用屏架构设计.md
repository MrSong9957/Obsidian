# CLI 备用屏架构设计

**交互式 CLI 启动就进入备用屏。平时正常更新；窗口缩放时，清掉当前画面，按新尺寸完整画一遍；退出时回到原主屏。**

本文基于[[wiki/终端重复绘制：原因与备用屏方案|《终端重复绘制：原因与备用屏方案》]]重写，面向 DeepSeek Harness CLI。底层原理、交互行为和验收要求在这里说清，文件拆分、接口和代码由 Agent 按项目现状落实。

**本轮决定：交付后的交互入口默认使用备用屏，用户不需要设置开关。** 旧文档中“先保留主屏默认、再通过开关切换”的迁移安排不再是本稿的前提。历史浏览和完整验收仍须随交付完成。

## 1. 为什么会重复绘制

**旧画面没擦干净，新画面又画上去了。** 重画本来正常，问题在于程序判断错了旧画面的位置。

例如：

1. 程序记住：“上一帧占了 10 行，下次退回 10 行擦掉。”
2. 窗口变窄，文字折成 15 行，部分还被挤进上方滚动历史。
3. 程序仍按旧位置擦，留下几行旧内容，再画新界面。反复缩放，副本越积越多。

终端只认识字符格和光标，不知道哪些文字属于“同一个输入框”。所以这里通常是同一份聊天数据留下多份画面；如果业务消息本身重复，需要另外修复。

主屏也可以全量重画，但只清当前窗口，清不到滚动历史里的旧副本；连历史一起清，又可能丢掉启动前的命令和输出。那些内容由终端保存，CLI 通常没有完整副本。

## 2. 备用屏解决了什么，又没有代替什么

**备用屏是一块与主屏分开的画布，大小就是当前窗口，没有自己的原生滚动历史。** 清理它不需要改写主屏历史，退出后可以回到原主屏。[^1]

这让修复变得直接：所有旧 UI 都留在能清除的范围内，缩放后整块清除，再画一份。

但只打开备用屏开关还不够，必须同时做到：

- **界面不越界。** 长消息、卡片和输入都不能把整帧撑出窗口。
- **数据单独保存。** 屏幕只是显示结果，聊天记录和草稿不能跟着清屏消失。
- **绘制统一管理。** 不能一边由 Ink 画界面，一边由其他代码乱动光标。
- **缩放后重建画面。** 清掉终端上的文字，也要让 Ink 放弃旧帧记录。

主屏、备用屏决定“画在哪里”；增量、全量决定“怎么更新”。本方案全程使用备用屏，不在缩放时临时切屏，也不要求每输出一个字就清屏。

## 3. 启动后，谁负责什么

继续使用现有 React/Ink。Ink 7 已提供备用屏入口，项目需要在它之上接好布局、重画和退出管理，无须先更换语言或自研渲染框架。[^2]

| 部分 | 负责什么 | 缩放时怎么处理 |
|---|---|---|
| 现有会话与控制器 | 接收消息、运行工具、处理取消、保存会话 | 照常工作 |
| 前端状态 | 聊天正文、草稿、焦点、卡片选择、阅读位置 | 保留，不随组件重画重置 |
| 布局 | 按当前宽高决定换行、区域高度和可见内容 | 重新计算 |
| 绘制协调器 | 决定何时能写终端，统一处理尺寸变化和退出 | 暂停旧画面，安排新画面 |
| 一个 Ink 根 | 把当前布局画进备用屏 | 按要求放弃旧帧并完整重画 |

这些是职责，不要求每行都新建一个类。优先复用已有状态和协调器，不另建一套会话存储。

第一份交互画面出现前就进入备用屏，加载提示和连接错误也在这里显示。主界面只挂载一个 Ink 根，退出时统一恢复终端。

工具输出、错误、日志都不能绕过管理直接穿插写到画面里。用户需要看的内容进入现有展示流程，诊断进入日志通道；stdout 和 stderr 连到同一个终端时，都遵守这个规则。

管道、重定向、帮助和版本输出继续使用既有普通文本路径，不发切屏控制码。“启动即备用屏”指交互界面，不是把每种命令输出都改成全屏。

## 4. 窗口只有这么大，长内容怎么办

**先给必须操作的部分留位置，再决定能显示多少聊天。**

正常聊天画面从上到下分成四部分：

| 区域 | 内容 |
|---|---|
| 历史区 | 已完成的聊天，可翻页 |
| 留白 | 内容不足时补空白，把底部区域推到窗口下方 |
| 活动区 | 正在输出的正文、工具进度、工作状态 |
| 底部区 | 输入框、状态栏和当前交互卡 |

卡片实际属于哪一组，沿用现有组件关系，但只能计算一次高度。

历史区可用行数＝窗口行数－活动区实际高度－底部区实际高度－必要安全留白，最少为 0。所有高度都按本次宽度和内容计算，不能固定写成“永远预留十行”。

例如窗口有 30 行，活动区和底部区合计需要 10 行，历史最多占剩余 20 行；卡片多出 5 行，历史就少显示 5 行，不能把输入框挤出窗口。

具体遵守以下规则：

- 长输入和高卡片在自己的区域内滚动，当前光标或选项必须可见。
- 活动正文过长时显示可容纳的末尾，完整内容仍保留；回复完成后可以翻页阅读全文。
- 空间不足时先减少装饰和留白，再压缩可见正文；极小窗口显示紧凑界面或放大窗口提示，仍可退出，放大后恢复全部状态。
- 最终整帧填满窗口但不超出窗口；不能在底部多写一个换行，把画面再次顶走。
- 中文、emoji 和组合字符按实际显示宽度处理。窄时截断、宽时重新展开，不能留下旧的截断版本。

**先算好受限布局，再输出。** 如果组件需要测量，测量过程也必须受控；不能先向终端试画一个超高界面，再指望下一帧裁回来。

## 5. 聊天和阅读位置怎样保留

**聊天记录是原始内容，画面只是当前截取的一段。**

同一条消息从流式输出到完成，使用同一个稳定身份。完成时把它从活动正文移到历史展示中，同一帧不能两边各放一份。不能靠“文字相同”去重，因为用户可以合法地发两条一样的消息。

历史区按当前宽度换行，再取当前窗口能显示的行。单条消息有一千行，也只显示其中一段；不能因为它是一条消息，就把一千行全部写到终端。全屏路径不再使用 <Static> 向主屏追加聊天。

可以缓存“这条内容在这个宽度下占多少行”，但内容或宽度改变时必须重新计算。只绘制可见部分能减少绘制量，并不意味着全部聊天数据不占内存。

阅读位置记录为“哪条内容的哪一段”，不要只记旧窗口的第几行。窗口变窄后重新换行，仍能找回原来正在看的文字。布局缓存可以丢弃，消息、草稿和选择状态不能丢弃。

首版历史浏览随默认备用屏一起交付：

- 没有卡片或选择器接管输入时，PgUp 进入历史浏览；浏览期间 PgUp/PgDn 翻页，Home 到最早，End 回到最新、恢复底部跟随并返回编辑。
- Esc 返回编辑状态，保留阅读位置；正常编辑时 Home/End 仍归编辑器，不抢走已有键义。
- 用户停在旧消息时，新输出只更新数据，不把阅读位置拉回底部。滚回底部后再恢复跟随。
- 编辑器、卡片、选择器、历史区只允许一个接收当前按键，沿用现有输入归属规则，不能一次按键同时触发翻页和回答卡片。

/new、/clear、/resume 沿用既有会话行为，但前端的阅读位置和布局缓存必须随会话切换重置或重新绑定，不能混入上一会话的画面。

当前可见文字仍可用 Windows Terminal 原生选择复制。首版不启用鼠标滚轮捕获，全文搜索、跨屏选字和退出时打印整段聊天都不属于本次必需能力。退出后通过既有会话恢复查看聊天。

## 6. 普通更新与缩放，走两条明确流程

**普通更新不需要每次清屏。**

消息或输入改变后，先更新前端状态，按当前尺寸生成受限布局，再交给 Ink 正常绘制。文字缩短或组件消失后，旧位置也必须擦净。连续几个输出片段可以合成一次画面更新，但不能丢弃业务事件。

**缩放时，旧位置已经不可信，必须重新建立整帧。**

| 顺序 | 必须做的事 | 为什么 |
|---|---|---|
| 1 | 停止提交旧尺寸的画面，作废排队中的旧绘制 | 防止旧画面在清屏后又写回来 |
| 2 | 保留消息、草稿、焦点和阅读位置；尽快清除失效画面 | 可以短暂空白，不能把旧布局留在新尺寸里 |
| 3 | 合并连续尺寸通知，绘制前重新读取实际宽高 | 排队里的尺寸可能已经过时 |
| 4 | 用当前状态和新尺寸完成布局，恢复阅读位置 | 不复用旧宽度下的换行和坐标 |
| 5 | 在同一受控输出过程中清除可见区域、归位光标、让 Ink 放弃旧帧记录 | 终端清了，框架也必须知道旧画面没了 |
| 6 | 从已知起点完整重画，并放置当前输入光标 | 建立一份完整、可继续更新的新画面 |
| 7 | 只有尺寸仍有效时才把它作为下一次更新的基准 | 中途又缩放，就作废本批并重新处理 |

第 2 步用于尽早去掉旧画面，第 5 步保证最终绘制从干净起点开始。是否能合并清除、等待多久，由 Agent 用真实终端验证；清除在先、完整重画在后、中间不夹入旧输出，是固定要求。

已经写入输出通道的字节不能撤回。必须通过同一个写入队列，让清屏排在已发出的旧内容之后，并拒绝旧任务继续写入；不能另开一个输出入口抢先清屏。

每次尺寸变化标记一个新的绘制批次。旧任务即使晚完成，也不能继续往新画面写。绘制期间出现的新消息正常保留；尺寸没变时可以画在下一帧，不能因为持续来消息就一直不显示。

连续拖动可以合并刷新，但不能无限等待；最后一次尺寸变化后必须主动完成重画，不能等用户再按一个键才恢复。按键和粘贴继续被完整接收；若框架暂存输入，恢复后只能交付一次。光标位置查询的响应由输入层识别，不能当作用户文字。

### Ink 必须提供的最小能力

协调器需要一个明确的“使旧帧失效并完整重画”入口。**只清终端、不清 Ink 的旧帧记录不够：Ink 可能认为文字没变，于是什么也不补画。**

优先使用现有接口；若当前版本没有公开接口，就在终端适配处封装项目已经使用的完整重画机制。调用方只发请求，不到处修改 Ink 私有状态。这个入口不能靠卸载主界面、切换备用屏或反复开关输入模式来实现，否则会丢焦点或打断输入。

保留现有 Ink，不另造字符格渲染器。先保证正确，短暂闪白可以接受；减少闪烁是后续优化，不能重新依赖旧行数去猜擦除位置。

## 7. /trace 和退出怎样处理

**整个交互运行期间，备用屏只有一个管理者。**

/trace 只在同一个 Ink 根里切换显示内容。进入时保存草稿、焦点和阅读位置，退出时恢复并重画；Trace 自己不能发送进入或离开备用屏的指令。会话切换、缩放也不切屏。正常生命周期只有启动进入、退出恢复这一对操作。

普通工具继续通过现有捕获与展示流程输出。本方案不新增外部程序直接接管终端的能力；已有接管行为若存在，Agent 必须在接入前查明，不能让另一个输出者绕过屏幕管理。

正常退出、Ctrl+C、应用捕获到的异常和现有强制退出兜底，共用一条恢复路径：

1. 停止新绘制，取消排队画面，防止退出后又写回 UI。
2. 按既有规则结束会话工作、完成必要保存；沿用现有退出时限。
3. 解除输入捕获，恢复应用改动的终端模式，离开备用屏并显示光标。
4. 确认已发出恢复操作，再输出必要的退出信息并结束进程。

**“开始退出”不等于“已经恢复”。** 恢复状态由一个地方记录，正常路径和兜底据此避免重复处理；不能先标记恢复完成，再等待一个可能挂住的卸载过程。

现有 2 秒强制兜底保留。当正常退出没有完成时，它需要同步发出最小恢复操作，覆盖备用屏、光标和括号粘贴等实际启用的模式，不能依赖异步组件卸载。保留直接触发标记，如实记录强制退出。

终端恢复成功不等于消息已经保存，两项必须分别验证。操作系统直接强杀进程时，程序可能没有机会清理，不把这种情况算作可保证的恢复路径。

## 8. Agent 的改造范围与实施顺序

**只改 CLI 前端的显示与终端管理，沿用 Core、Session、Event 和工具协议。**

先确认当前 Ink 及项目内补丁、终端写入点、Trace 切屏点和退出路径，再依次接通：启动与退出 → 受限布局与历史浏览 → 缩放重画 → Trace 与其余交互 → 完整验收。历史浏览复用 Trace 的滚动模型；输入、卡片、诊断和测试继续使用现有接线。分步开发不等于把半成品设为默认交付。

全屏入口不再运行旧主屏的历史追加、尾部行数预算、静态块重发和旧光标锚点修补。替换完成后清理因此失去用途的代码，保留仍用于输入过滤、输出协调和非交互输出的部分。

最终启动无需全屏开关，本设计不要求长期保留两套交互界面。Agent 同步相关文档与测试中的旧默认约定，不把“关闭开关仍走旧主屏”当作新版的必需验收。

文件位置、缓存结构、接口名字和刷新间隔由 Agent 决定。上述行为不能靠删断言或裁掉消息来实现；遇到框架能力缺口，先给出具体失败证据和最小补齐办法。

## 9. 怎样证明做成了

**视觉问题看真实终端，数据与顺序看对应记录，不能用一种证据包办全部。**

先记录同一入口的原始故障，再在正式构建上跑以下场景。记录提交完整 SHA、启动命令、终端尺寸和实际 UI bundle 哈希，避免测了旧包却验收新代码。

| 场景 | 必须通过的结果 |
|---|---|
| 不设置全屏开关启动 | 首份交互画面就在备用屏，启动前主屏历史未被清除 |
| 一条提问收到确定性 401 错误 | 提问和错误各一条，反复缩放没有新增消息块或旧输入框副本 |
| 通过正常 CLI 消息流程产生 H001–H100 | 全部可翻阅、顺序正确；同一条记录不因重画变成多条，单条长消息的中段可到达 |
| 慢拖、快速往返、连续缩放 | 宽度、高度都覆盖；拖动中和落定后均无残留副本、无新旧混合帧 |
| 窄窗口与超过 120 列的宽窗口往返 | 路径和状态字段能截断、能恢复；中文、emoji 和输入光标不错位 |
| 流式正文、长草稿、高卡片不断增长 | 整帧不越界，输入区不被挤走；已完成正文只显示一份 |
| 阅读旧消息时收到新输出 | 阅读位置保持，回到底部才恢复跟随；缩放后仍能定位原内容 |
| 问题、审批和选择卡；Esc 取消后续聊 | 保留原交互语义，按键只处理一次，取消回执后同一会话可继续聊天 |
| /new、/clear、/resume、/trace 往返 | 会话画面不串，Trace 不额外切屏，草稿和焦点按约定恢复 |
| 缩放期间键入、粘贴 | 输入不丢、不重复，没有光标查询响应混入文字 |
| 正常退出、Ctrl+C、强制兜底、启动后异常 | 原主屏恢复，光标与输入正常；会话保存和退出路径有各自证据 |
| 当前画面选择复制；非交互输出 | 原生复制正常；非交互文本不夹带切屏控制码 |

H001–H100 不能用启动 CLI 前的 shell echo 代替。历史翻页可以让同一行在不同截图中再次出现，这不算副本；要检查内容身份和同一阅读位置的显示结果。PTY 原始字节也会因正常重画重复，不能直接按出现次数判错。

验证分三层：

- **单元与 PTY 测试**：区域高度、换行、阅读位置、旧任务作废、清屏顺序、切屏和输入恢复。PTY 是可记录输入输出的测试终端。
- **真实 Windows Terminal 画面**：拖动中与结束后的重影、底部位置、截断恢复、选择复制和退出恢复。UIA 文本抓取只辅助观察，不能替代像素裁决。
- **项目回归**：沿用 verify:full:cli、test:snapshot 和受影响文档检查；具体命令按仓库现状核实。偶发失败需与基线在同等条件下比较，不能靠重跑一次成功就忽略。

旧门禁中关于“开关关闭时保留主屏默认”的条款，按本轮要求改为“无开关启动备用屏，非交互输出不受影响”；其余视觉、输入、历史、退出及失败裁决要求继续保留。

现有项目文档记录了备用屏原型的真实 WT 验证，说明路线有实现基础，但不能代替本稿对应的正式构建验收。其他终端须另外验证，不沿用 Windows Terminal 的通过结论。
