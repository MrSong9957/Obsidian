# 核心原则

编排解决的是：

> **谁决定 Agent 下一步做什么？**

优先顺序应该是：

```text
单次 LLM 调用
    ↓ 不够
固定工作流
    ↓ 仍无法应对动态情况
自主 Agent
```

**能简单解决，就不要上复杂 Agent。**

因为自主性越高，通常意味着：

* 调用次数更多；
* 延迟更高；
* 成本更高；
* 行为更难预测。

Anthropic 与多个团队的实践经验也是：**成功方案往往来自简单、可组合的模式，而不是复杂框架。**

# 工作流：代码决定路线，LLM 处理节点

Workflow 的关键不是“用了多个 LLM”，而是：

> **执行路线提前由开发者写死。**

例如订机票：

```text
验证身份
  ↓
搜索航班
  ↓
付款
  ↓
确认预订
```

LLM 可以在某个节点里理解自然语言，但不能自己决定：

```text
跳过身份验证
先预订再付款
突然执行其他工具
```

因此工作流特别适合**业务规则明确、步骤固定**的任务。

## 为什么工作流更安全

关键规则直接写进代码：

```text
付款成功 → 才允许预订
```

而不是：

```text
让 LLM 自己判断现在该不该预订
```

好处：

1. **流程可控**：关键步骤不会被跳过或乱序。
2. **攻击面更小**：提示注入通常只能影响当前节点，很难改变整个流程。

代价也很明显：

> **流程之外的情况，它不会自己变通。**

例如用户付款时突然要求改签，就必须提前写异常分支，否则只能交给人类或更自主的 Agent。

# 一个典型的“适配层”

传统文生图工作流：

```text
用户自然语言
    ↓
LLM 改写提示词
    ↓
Stable Diffusion
    ↓
图片
```

为什么要多一个 LLM？

因为 Stable Diffusion 更习惯类似：

```text
english tags, quality tags, style tags, negative prompts...
```

用户说的却是：

> 帮我画 AGI 时代程序员的工作场景。

所以中间的 LLM 本质是在做：

> **把人听得懂的话，翻译成工具听得懂的话。**

这种为了弥补模型或工具能力短板而存在的 Harness 代码，可以理解为**适配层**。

# 模型越强，适配层越少

如果换成原生支持自然语言 + 图像生成的多模态模型，例如：

* Nano Banana 2
* GPT-Image 2

流程可能直接变成：

```text
用户自然语言
    ↓
多模态模型
    ↓
图片
```

中间的“提示词翻译器”就没有必要了。

这背后有一个很重要的趋势：

> **Harness 中很多“翻译、修复、脚手架”代码，只是在暂时弥补模型能力不足。模型变强后，这些能力会被模型本身吃掉。**

已经发生过类似演进：

| 以前 Harness 负责   | 后来被模型能力替代       |
| --------------- | --------------- |
| few-shot、一步一步思考 | 指令微调、推理模型       |
| JSON 修复、输出解析    | 结构化输出           |
| 手写工具调用格式        | 原生 Tool Calling |
| 文生图 Prompt 改写   | 原生多模态理解         |

# 真正值得记住的判断标准

不要先问：

> 我要用什么 Agent 框架？

先问：

```text
一次模型调用能解决吗？
  ├─ 能 → 不做 Agent
  └─ 不能
       ↓
任务步骤能提前确定吗？
  ├─ 能 → Workflow
  └─ 不能 → Autonomous Agent
```

核心思想：

> **复杂度应该来自任务本身，而不是因为“Agent 更高级”就主动增加复杂度。**
