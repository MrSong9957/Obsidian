## 构建 Agent 的三个核心原则

### 1. 保持简单

**先用最简单、能工作的方案，复杂度只在确实需要时增加。**

优先：

```text
直接 API 调用 > 复杂框架
清晰代码 > 聪明抽象
```

原因很简单：

> 每增加一层抽象，就增加一层以后排查问题时看不到的东西。

所以不要一开始就设计复杂的多 Agent、工作流和框架。

---

### 2. 保持透明

Agent 做了什么，应该尽量能够看到：

* 当前计划；
* 工具调用；
* 执行结果；
* 决策轨迹；
* 错误和重试。

原因是：

> **看不到执行过程，就很难知道 Agent 为什么失败，更不知道怎么修。**

透明不仅用于开发调试，也是生产环境里的可观察性基础。

---

### 3. 设计好 ACI

**ACI（Agent-Computer Interface）就是专门给 Agent 使用的工具接口。**

传统 API 主要考虑：

> 程序员好不好调用？

ACI 更关心：

> **模型能不能看懂，而且不容易调用错？**

例如工具：

```text
execute(a, b, c)
```

模型很难知道参数代表什么。

更好的设计：

```text
delete_file(path)
search_web(query)
read_file(path)
```

名字和参数本身就在告诉模型应该怎么使用。

### ACI 的核心：防呆

不仅要“告诉模型别犯错”，最好让接口本身**无法犯这种错误**。

这叫 **Poka-yoke（防呆设计）**。

例如：

```text
危险设计：
transfer(amount, account)

更安全：
transfer(
    destination_account,
    amount,
    currency
)
+ 金额限制
+ 权限验证
+ 二次确认
```

核心思想：

> **能通过接口设计消灭的错误，就不要依赖模型自己记住规则。**

再强的模型遇到模糊工具，也会系统性出错，因为工具接口就是模型理解外部世界的入口。

# 模型怎么选

## 第一原则：在自己的任务上测试

不要只看排行榜。

因为：

```text
Benchmark 很强
≠
你的 Agent 场景一定很强
```

真正应该拿自己的任务测试：

* 工具选得对不对；
* 参数填得对不对；
* 连续多轮是否稳定；
* 遇到错误能不能恢复；
* 最终任务成功率。

> **Agent 选型最终看任务成功率，而不是单次问答分数。**

---

## 闭源与开源怎么选

### 闭源模型

通常优势：

* 能力强；
* Agent / 工具调用能力成熟；
* 基础设施完善。

代价：

* API 成本；
* 受厂商策略限制；
* 无法完全控制部署。

### 开源模型

通常优势：

* 成本低；
* 可以私有部署；
* 可以微调；
* 数据控制能力更强。

适合：

* 成本敏感；
* 数据不能出内网；
* 任务对顶级模型能力要求不高。

原文提到的国内 Agent 模型包括：

* DeepSeek
* Kimi
* GLM

但不同模型的**工具调用能力可能差很多**，必须实测。

---

## 不只看“能力”，还要看“能不能用”

一个容易忽略的问题：

> 模型会做，不等于产品允许它做。

需要同时检查：

```text
模型有没有能力
↓
API 有没有暴露能力
↓
模型愿不愿执行
↓
厂商策略允不允许
↓
服务条款允不允许
```

例如某个模型理论上具备网络安全能力，但聊天产品、Coding Agent 和 API 的限制可能完全不同。

业务关键任务最好还准备：

* 人工接管；
* 备用模型；
* 合规替代路径。

---

## Agent 通常需要 Reasoning 模型

Agent 经常需要：

```text
分析当前状态
↓
选择工具
↓
决定参数
↓
观察结果
↓
调整计划
```

这本身就是多步决策。

所以大多数 Agent 应优先使用具备 **Reasoning（推理）能力**的模型。

例外通常是非常简单的任务，例如：

```text
固定输入
→
固定动作
```

或者简单 GUI 点击。

只要任务出现：

* 多步骤；
* 动态环境；
* 工具选择；
* 错误恢复；

Reasoning 基本就变成必要能力。

---

## 两个容易漏掉的指标

### 1. 输出速度

Agent 的延迟会被循环放大。

例如：

```text
20 轮模型调用
×
每轮多等待 2 秒
=
多等待 40 秒
```

所以不能只比较：

* 单价；
* 智力。

还要看：

> **每轮响应到底有多快。**

### 2. 多模态

如果 Agent 需要处理：

* 图片；
* GUI；
* PDF 截图；
* 音频；
* 视频；

多模态就不是加分项，而是硬性能力。

---

## 模型选型最实用的检查顺序

```text
1. 能不能完成我的真实任务？
        ↓
2. 工具调用稳定吗？
        ↓
3. 策略/API 是否允许？
        ↓
4. 推理能力够不够？
        ↓
5. 延迟能不能接受？
        ↓
6. 成本能不能接受？
        ↓
7. 是否需要多模态 / 私有部署？
```

不要反过来只看：

```text
排行榜第一是谁？
哪个参数最多？
哪个最便宜？
```

## 最值得记住的两句话

**Agent 设计：**

> 简单减少故障点，透明方便发现问题，好的 ACI 从源头减少模型犯错。

**模型选型：**

> 不要选“排行榜最强的模型”，要选“在你的真实 Agent 任务上成功率最高、速度和成本又能接受的模型”。
