# UI 设计原则

> 内容已迁移至 [[wiki/frontend.md|frontend]]。

> 相关文档：[[Everything-Claude-Code.md|ECC 技能集]]

### 一、动手之前

- 先问用途再写代码——这东西给谁用？什么场景？搞清楚再动手。
- 先定一个极端审美方向——要么极简到底，要么极繁到满，不准走中间路线。选一个词：brutalist、editorial、luxury、playful、industrial，选完就贯彻。
- 先想"记忆点"是什么——用户打开页面会记住什么？一个不寻常的布局？一个大胆的配色？一个动画？想清楚这个再写。

### 二、先画线框，后写代码

- 不准上来就写代码，先用 ASCII 或 SVG 画 5 种截然不同的线框方案供用户选择。
- 5 种方案必须风格差异足够大——比如：①极简左对称 ②杂志式不对称网格 ③全屏沉浸式 ④卡片瀑布流 ⑤分屏对比式。
- 每种线框标注：页面结构分区、信息层级、视觉焦点位置、大致留白比例。
- 用户选定方案后，再基于此展开配色、字体、动效，不准跳过这步直接编码。

### 三、字体

- 绝对禁止 Inter、Roboto、Arial、Space Grotesk、system-ui 作为主字体。
- 必须用 `<link>` 标签从 Google Fonts CDN 加载，不准只在 CSS 里声明。
- 必须配对：一个有性格的标题字体（如 Cormorant Garamond、Bebas Neue、Syne）+ 一个好读的正文字体（如 DM Mono、Lora、Source Serif 4）。
- 字重要有层级——标题/副标题/正文/辅助文字，字重和字号必须拉开差距，不准都用 16px。

### 四、颜色

- 所有颜色用 CSS 变量定义在 `:root`，不准硬编码。
- 一个主色 + 一个锐利强调色，不准搞均匀分布的彩虹配色。
- 禁止 紫色渐变白底、Tailwind 默认蓝（#6366f1）、安全色板。
- 大胆尝试：深林绿配暖沙色、炭灰配酸黄、纯黑配猩红。

### 五、布局

- 禁止 居中 hero + 三栏卡片 + CTA 页脚（AI 默认套路）。
- 尝试：不对称网格、左锚定编辑式排版、全出血分屏、元素重叠、对角线流动。
- 空间要么慷慨要么密集，不准在中间晃荡——大量留白（refined）或高密度堆叠（maximalist），选一个。

### 六、动效

- 优先 CSS 动画，用 `animation-delay` 做交错入场，不准每个元素各自随机动。
- 动效要有编排——页面加载时的交错淡入比散落的微交互更有冲击力。
- hover 状态要惊喜——比如按钮 hover 时 letter-spacing 拉开、背景色切换，不准只改个透明度。

### 七、质感与氛围

- 不准只用纯色背景——加噪点纹理、渐变网格、几何图案、层叠透明、戏剧性阴影中的至少一样。
- body::before 加噪点覆盖层是低成本高回报的做法。
- 考虑自定义光标、装饰性边框、裁切形状等非常规细节。

### 八、代码质量

- 所有代码 inline 输出，不准用 artifact 包裹。
- 不准有占位逻辑——每个函数、每个状态都要能跑。
- 间距值、字号、颜色必须精确，不准用"大概差不多"的值。
- CSS 变量贯穿全局，改一处能联动全站。

### 九、自动迭代闭环

- 写完必须截图——无头浏览器渲染后截图。
- 截图必须自动分析：对齐、间距一致性、颜色对比度、文字可读性，逐项打分。
- 发现问题自动改代码重截，不准只改一次就收工。
- 设定迭代上限（如 5 轮）和收敛标准——连续两轮截图无明显差异则停止。
- 每轮迭代记录改了什么、为什么改——输出简要 diff 日志，让用户知道它在做什么。
- 用户可随时介入——在任何一轮之间插入"方向偏了，往 XX 调"，迭代从该指令重新开始。
- 最终输出：成品代码 + 迭代过程日志 + 最终截图，三者一起交付。

### 十、最佳实践：无头 vs 有头模式

默认用无头，只在关键时刻切有头。

| 场景 | 模式 | 原因 |
|---|---|---|
| 间距/对齐/颜色等量化检查 | 无头 | 精确、快、可自动化 |
| 代码 lint、结构验证、性能测试 | 无头 | 纯数据判断，不需要人眼 |
| 自动迭代中的截图对比 | 无头 | 机器比对像素差异比人快 |
| 审美定稿、风格方向确认 | 有头 | "好不好看"只有人能判断 |
| 动效体验、交互手感验证 | 有头 | 动画流畅度和舒适感无法量化 |
| 最终交付前验收 | 有头 | 用户必须亲眼看到成品再签收 |

原则：无头做苦力，有头做裁判。 用无头模式批量跑完 80% 的检测和迭代，最后把结果丢到有头模式里，让用户用肉眼做最终决策。不准全程无头闭门造车，也不准全程有头浪费用户时间。
