## 为什么需要

模型的上下文窗口有限，而工具返回的结果（测试日志、搜索结果、文件内容）常常又长又多。如果不处理，几轮之后历史就塞满窗口，既贵又丢早期信息。

关键分工要先分清：

- **API 结构**只负责“谁说了什么、有哪些工具”，即消息和工具的定义。
- **何时压缩、怎样压缩、压缩后保存什么**，是 Agent 程序自己额外实现的上下文管理，API 不会自动做。

推荐的总思路是：**先用本地程序筛选和限长，确实需要理解的长文本再调用模型做摘要。摘要生成后保存复用，但不承诺永久常驻、永不更新。**

## 全局流程一览

```
工具结果
  ├─ 代码减量够短 ──────────→ 直接进上下文
  ├─ 代码减量不够、需理解 ──→ 单条摘要 + 路径进上下文（结果进入主模型之前）
  └─ 落盘 ─────────────────→ 预览 + 路径 + 截断标记进上下文
                                ↓
              后续证据不足时，模型按需重读原文（或程序强制补查）
                                ↓
              历史整体到阈值 → 一次性摘要压缩（合并旧摘要，删过时内容）
```

完整表述：**工具结果先代码减量，够短直接进上下文，原文同步落盘（前提是该 Agent 有落盘机制）；减量不够又需要理解的，进入上下文前先调模型做单条摘要；结果以片段/摘要形式进上下文后，证据不足时模型按需重读原文（或程序强制补查）；最后历史整体到阈值才做一次性摘要压缩。**

三个关键时序结论：

1. 进入上下文的是**“代码减量后的片段 / 单条摘要 / 落盘路径”三者之一**，第一道关是代码减量，不是裁剪。
2. **单条摘要发生在结果进入主模型之前**，作用是替主模型挡住原文；“模型重读原文”是之后证据不足时的另一条独立路径，两者不是先后串联。
3. **历史裁剪和整体摘要压缩都是后续触发的**：DeepSeek Harness 的“留头尾删中间”是上下文压力大时才发生，不是每条结果进入时就裁。

## 两层压缩要分清

| | 单条工具结果处理 | 整体历史压缩 |
|---|---|---|
| 触发对象 | 某一次工具返回过长 | 整个会话历史积累过长 |
| 触发时机 | 结果进入上下文之前 | 上下文压力大/接近窗口上限时 |
| 典型做法 | 代码减量、落盘 + 预览、单条摘要 | 裁剪历史中的长结果、把旧历史换成摘要（近期消息留原文） |

顺序上：平时靠第一层挡住大块结果、只追加新消息（保住缓存前缀）；挡不住、历史整体膨胀到阈值时，才做一次集中压缩——旧的裁剪结果和摘要被合并进新摘要，过时内容删掉。这是“必要时集中压缩”而不是“每轮都总结”的原因。

## 裁剪不等于摘要

- **裁剪**：少给一些文字，不理解内容。按位置切，不知道切掉的中间有没有关键报错。
- **摘要**：理解之后提炼重点，保留结论和关键细节。

例如 DeepSeek Harness 的裁剪插件默认把超过 **8,192 个字符**的结果缩成**前 4,096 + 后 1,024 个字符**。这属于裁剪，不能当成“智能摘要”。

## 三家的实际做法

工具结果太长时（都不需要模型理解内容）：

| Agent | 处理方式 |
|---|---|
| **DeepSeek Harness** | 两层：①工具执行后，长结果落盘存文件，返回头尾预览 + 路径 + 补读提示（基础配置已启用）；②上下文压力大时，再裁剪历史里的长工具结果，本地留头尾删中间，不调模型，完整原文仍在会话日志 |
| **Codex** | 代码按长度预算截断工具输出，`tool_output_token_limit` 控制单条结果进历史的预算，并附截断提示。**入口即截断**，不能假设所有工具结果都有可重读的原文文件 |
| **Claude Code** | 以 Bash 为例：正常结果过长时返回保存文件的路径 + 开头预览，模型按需读取；失败结果过长时可能只返回头尾片段、没有文件路径 |

因此“进入上下文的是头尾 + 路径”这个描述对 Codex 更准确（入口即截断）；对 DeepSeek Harness 要分两阶段——入口时是预览 + 路径，压力大时才把历史里的长结果裁成头尾。

整段上下文太长时（对应“整体历史压缩”层）：

| Agent | 处理方式 |
|---|---|
| **DeepSeek Harness** | 裁剪后仍太长，才额外调模型把旧历史换成摘要，近期消息保留原文 |
| **Codex** | 有模型生成文字摘要和远端压缩路径；远端结果可能含加密压缩项，不一定是人能读懂的摘要 |
| **Claude Code** | 官方说明：先清理旧工具输出，再按需总结对话 |

注意：**“省略”首先指不把全部内容交给模型**。原文是否落盘、能否重新读取，取决于具体工具和保存机制——落盘是 DeepSeek Harness 和 Claude Code 正常结果的常见做法，不是普遍保证。

## 自己实现的四步流程

以下为实现建议，不是三家的统一流程。处理位置放在**Agent 接到工具结果之后、送入主模型之前**：

1. **先保存原文。** 完整结果写入文件或日志，留下可再次读取的位置。
2. **先用代码减量。**（见下节）测试日志提取失败项、搜索结果限制条数、大文件按行读取。已经够短就直接返回。
3. **需要理解时，再单独调用模型。**（见“单条摘要怎么调用”）输入是“当前任务 + 相关工具结果 + 摘要要求”。可以用同款模型或另一个模型；主会话只接收整理后的短结果。原文超出摘要模型窗口时，先检索相关片段或分块处理。
4. **保存结果并复用。** 单条工具摘要仍作为对应的 `tool` 结果，保留工具调用 ID。不要每轮重新生成，也不要把原文和摘要一起塞回上下文。

### 什么是代码减量

指工具返回结果后，先用**不调用模型的程序逻辑**把结果变短，能解决就不必动用更贵的手段：

- 测试日志：正则/解析提取失败项和错误堆栈，丢掉 118 条通过记录的详细输出；
- 搜索结果：超过 20 条就只留前 20 条；
- 大文件：不整份返回，按行号范围返回需要的片段；
- 结果本来就不长：什么都不做，直接进上下文。

“优先”是因为它便宜、快、规则写死不依赖模型判断，也不产生摘要模型的调用成本。

### 代码减量不够的四种情况

代码减量的前提是**能用明确规则判断“哪些部分不要”**。规则失效的场景就是“减量不够”：

1. **需要理解，而不是筛选。** 任务是“读 50 页设计文档，评估方案是否可行”。关键内容可能在任何一段，没有“失败项”这种可正则匹配的标记。写死的规则不知道该留哪段，只能整份保留——这就超预算了。
2. **结果本身就是关键内容，删哪块都疼。** 数据库查询返回 500 条记录，任务是“找出异常趋势”。按“限条数”留前 20 条，恰好把异常切没了。**位置上没有信息量差异**，靠位置裁就是瞎裁。
3. **需要全量统计，片段不足以支撑结论。** 任务是“统计日志里每个错误码出现多少次”。取头尾 4K 字符只能覆盖开头和结尾的记录，中间几十万行全丢——程序减量后数字必然是错的。
4. **格式不可预知。** 输出是一大坨自由文本，不是日志也不是表格，正则写不出来，不知道怎么减。

判断口诀：**有明确垃圾标记 → 代码减量；要按内容重要性取舍 → 需要理解 → 升级到模型摘要。**

### 单条摘要怎么调用

关键细节：**它不是主模型的一次工具调用，而是程序在后台额外发起的一次独立 API 调用**；返回的摘要**作为那次工具调用的结果**进上下文。

流程（说明步骤，非某家实现）：

```
1. 工具执行完毕，拿到原文（比如 200K 字符的报告）
2. 程序发现代码减量不够（需要理解整份报告）
3. 程序自己构造请求发给摘要模型：
   - 消息 = 当前任务 + 摘要要求（保留结果、数字、错误原文、位置、未解决问题）
   - 内容 = 工具原文（超窗口就先分块或检索相关片段）
4. 摘要模型返回短文本（比如 800 字符）
5. 程序把短文本作为 tool 结果写回主会话，沿用原 tool_call_id
6. 主模型下一轮看到的就是这段摘要，不是原文
```

伪代码示意（**说明示例，非可运行实现**）：

```python
# 工具执行后、写入历史前，由程序插入
def handle_result(tool_call_id, raw_output, task):
    if len(raw_output) <= BUDGET:
        return raw_output                     # 够短，直接进
    save_to_file(raw_output)                  # 先落盘
    if not needs_understanding(raw_output):   # 能用规则减量
        return rule_based_reduce(raw_output)
    summary = call_model_api(                 # 单独调一次 API
        messages=[{"role": "user",
                   "content": f"任务：{task}\n要求：保留结果、关键数字、错误原文、文件位置、未解决问题\n\n原文：{raw_output}"}]
    )
    return f"{summary}\n完整原文：{path}，可按需读取"
    # 这个返回值连同原 tool_call_id 一起进主会话历史
```

两个要点：

- **对主模型透明。** 主模型只看到 `tool` 角色的一条结果，不知道程序背后调过一次摘要模型。摘要模型可以是同款，也可以是更便宜的小模型——这正是“本地筛选优先、需要理解才调模型”的成本考虑。
- **和“重读原文”的区别。** 重读是主模型**自己**发起 `read`/`grep` 工具调用（主会话里可见的一轮工具交互）；单条摘要是**程序**在结果进入主会话前抢先做好的加工，主模型全程没有参与，也没有选择权。

### 摘要要保留什么

主模型可以拿到这样的结果：

```text
执行结果：120 项测试，118 项通过，2 项失败。
失败位置：login.test.ts:42、session.test.ts:87。
关键错误：实际返回 401，预期为 200。
完整日志：logs/test-017.txt，可按需读取。
```

**必须保留**：结果、关键数字、错误原文、文件位置、未解决问题。
“测试失败，需要修复”虽然短，但不足以继续工作。

## 摘要何时会变

“压缩后不再变化”的准确含义是：**这次摘要生成后保持稳定，直到下一次整体压缩。**

DeepSeek Harness 采用此方式：后续压缩会合并旧摘要和新信息、删除过时内容，再生成新摘要。这样既避免反复总结，也避免大量小摘要最终塞满上下文。

与缓存的关系：**缓存不只认 `system`**。已固定的用户消息、模型回复和工具结果都能构成稳定前缀。替换旧历史会失去从修改位置开始的缓存复用——所以平时只追加新消息，必要时集中压缩一次。

## 证据不足时怎么补查

核心规则：**先补读原文，不是必然调用模型摘要。** 这发生在结果已以预览/摘要形式进入上下文之后，与“进入前的单条摘要”是并列的两条路径。

DeepSeek Harness 会提示模型用 `read` 按范围读取，或用 `grep` 搜索已保存文件；Claude Code 官方也说明可按需读取或搜索保存的输出。

按当前需要选方法：

| 当前需要 | 更合适的处理 |
|---|---|
| 找一个错误、函数、字段或数值 | 搜索这份原文，读命中位置附近的内容 |
| 了解长报告的主要结论 | 带任务目标对原文做摘要 |
| 找全所有失败项、统计全部记录 | 完整解析或分段检查，不能只靠头尾和普通摘要 |

例：任务是“找出测试失败原因”，应先在完整日志里搜索失败记录，再读错误堆栈。直接总结整份日志会额外消耗输入 token，还可能漏掉关键细节。

两个必须记住的限制：

1. **会话压缩不会自动找回被省略的原文。** DeepSeek Harness 明确：工具结果裁剪后，后续会话摘要读的是裁剪后的历史。重要内容必须通过补读重新进入上下文。
2. **不能把“模型觉得够了”当成保证。** 程序判断“有没有截断”是确定的（可记录原文长度、保留范围、文件位置）；模型判断“证据够不够”依赖任务，可能出错。只看头尾没发现错误，最多说“当前片段未发现”，不能说“完整日志没有错误”。

## 可靠补查的设计

以下是针对“模型可能漏掉中间内容”的设计建议，**不是三家已统一提供的能力**：

1. **长结果必须留下可恢复入口**：结果编号、原文位置、截断标记，让模型始终知道自己只看了一部分。
2. **先检查同一份原文**：当前任务依赖的被截断结果缺证据时，程序先安排检索/检查原文，再让主模型决定下一步。
3. **必要时才调用摘要服务**：只处理指定原文，带明确问题，产出“相关结论 + 原文位置 + 尚未找到的信息”，不让它自由搜索别处。
4. **确实不足再扩大范围**：记录已检查什么、还缺什么；达到检查预算就明确说“未检查完”，避免反复检索，也避免把“没找到”当成“不存在”。

可封装成一个工具（**该函数需要自己实现，API 不会因为名字叫“检查结果”就自动具备这些行为**）：

```text
inspect_result(
  result_id="test-017",
  question="找出全部失败测试，以及各自的直接报错"
)
```

主模型调用后，程序读取对应原文 → 先搜索或解析 → 必要时单独请求模型摘要 → 把证据返回主模型。若想少依赖主模型的自觉，程序可在关键结果被截断后**直接执行检查**，再把整理结果交给主模型——这样“先查原文”由代码保证。

## 边界

- **能保证**：处理顺序、检查范围、证据来源。
- **不能保证**：任意长文本上模型永远不漏信息。
- 要求“找全”或“确认不存在”时，必须做覆盖完整原文的检查，预览和摘要都不能代替。
