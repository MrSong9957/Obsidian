# 终端重复绘制：原因与备用屏方案

**本质是：旧画面没擦干净，新画面又画上去了。** 重画本来就是正常操作，问题出在“擦哪里”的判断错了。

例如：

1. 程序记住：“上一帧占了 10 行，下次退回 10 行擦掉。”
2. 窗口变窄，终端自动换行，原来的内容变成了 15 行，部分还被挤进滚动历史。
3. 程序仍按旧位置清理，留下几行旧内容，再画新界面。反复缩放，副本就越积越多。

**更深层原因：程序记录的画面位置，与终端实际位置不一致。** 终端只认识字符格和光标，不知道哪些文字属于“同一个输入框”，不会自动帮程序替换旧组件。

所以，终端里确实多了残留文字，但通常不是聊天数据多了一份，而是**同一份数据留下了多份画面**。如果聊天消息本身也重复，那是另一个需要修复的问题。

**主屏也能全量重画，难点是清除范围和恢复来源。**

- 只清当前窗口：已经被挤进上方滚动历史的旧副本还在。
- 连滚动历史一起清：旧副本能清掉，但启动 CLI 前的命令和输出也可能一起消失。

启动前的内容通常由终端保存，CLI 没有完整副本，清掉后无法自行恢复。主屏把这些历史和 CLI 界面放在一起，清理起来就比较麻烦。

**推荐方案：CLI 运行期间一直使用备用屏，缩放时清屏并完整重画。**

备用屏是一块与主屏分开的画布。让整个界面留在这块可控区域，缩放后清空它，再按新尺寸画一次，就省去了追着旧位置擦除的麻烦，也不必清掉原主屏历史。

| 时机 | 怎么做 |
|---|---|
| 启动 CLI | 进入备用屏 |
| 普通内容变化 | 沿用框架的正常更新方式，可以只更新变化的部分 |
| 窗口缩放 | 在同一备用屏内，清屏、按新尺寸排版、完整重画 |
| 退出 CLI | 恢复原主屏、光标和输入模式，包括 Ctrl+C 和强制退出兜底 |

主屏、备用屏决定“画在哪里”；增量、全量决定“怎么更新”。**不是缩放时才切去备用屏，也不需要每输出一个字就清屏。**

缩放时先暂停旧画面的输出，再清屏、把光标放回起点，并让绘制框架放弃旧帧记录，完整画出新帧。连续拖动以最新尺寸为准，不能把新旧画面混着画。允许短暂空白，但消息和键盘输入不能丢。

**清屏只擦画面，聊天仍保存在会话里。**

屏幕只显示当前看得见的内容：先给输入框、状态栏、正在输出的正文和交互卡分配空间，剩余位置放历史。内容再长，也不能把界面撑出窗口。

备用屏没有自己的终端滚动历史，因此翻阅聊天要由应用负责。首版用 PgUp/PgDn/Home/End 翻页；用户正在看旧消息时，新输出不能把人拉回底部。

代价是退出后不自动把整段聊天留在 shell 中，之后通过会话恢复查看。当前可见文字仍可用终端原生选择复制；全文搜索、滚轮浏览和退出时打印整段聊天暂不属于首版。

**落到本项目，保留现有 Ink，主要改布局、历史浏览和终端管理。** 会话与工具逻辑继续沿用。终端由一个入口负责绘制和切屏；`/trace` 在同一备用屏里换内容，不再自行切屏。

先通过开关试用，历史浏览、全部测试和实屏验收通过后再切换默认；保留短期退路，观察通过后单独删除旧主屏修复。具体代码由 Agent 按现有正式设计执行。

**验收要看真实 Windows Terminal，不能只看文本计数或缩放后的最后一屏。**

- 连续拖动窗口，过程中和结束后都只有一份输入框、状态栏，没有新旧画面混杂。
- 长聊天完整可翻阅；草稿、焦点、问题卡、取消后的续聊都正常，缩放期间输入不丢。
- 正常退出和强制兜底都恢复原主屏，光标、键盘和粘贴正常；聊天是否保存另行核对。

本文是方案说明；完整实施与验收仍以现有正式设计和门禁为准。
