**Agent 既要知道刚才发生了什么，也要记住用户长期有用的信息，因此需要区分原始记录和长期记忆，再选择合适的存储格式。**[^1]

记忆设计有三个问题：**放哪里、怎么存、存什么**。这里先讨论前两个。

**轨迹和长期记忆，承担不同职责。**

| 层次                 | 保存什么                   | 怎样维护              | 用来做什么               |
| ------------------ | ---------------------- | ----------------- | ------------------- |
| **轨迹（Trajectory）** | 一次运行中的用户消息、模型回复、工具执行结果 | 按时间顺序追加，原始事件不直接改写 | 理解当前任务，追查发生过什么，调试问题 |
| **用户长期记忆**         | 从多次对话中提取的偏好、个人信息、交互摘要等 | 持续更新、合并和淘汰        | 跨会话、跨运行实例继续了解同一个用户  |

可以把轨迹理解为**流水账**，长期记忆理解为**持续整理的用户档案**。

长期记忆通常与用户 ID 绑定，可用键值对保存，例如“语言偏好 → 中文”。Agent 可以通过记忆工具读取和更新它，让下一次对话继续使用这些信息。

有些系统还单独保存**业务状态**，表示任务进行到了哪一步，例如“需要澄清”“等待付款”“请求完成”。它记录当前阶段，在依靠事件推动任务的系统中尤其有用。

**原始轨迹与实际发给模型的上下文，要分开理解。**

原始轨迹采用 **append-only，即新事件只往末尾追加**。但每轮发给模型的上下文可以压缩、重组，或用摘要替换较早的内容。

因此，压缩上下文不等于改写原始记录。原始记录是否长期完整保留，还取决于系统的数据保留要求。

**同一条用户信息，可以用四种方式保存。** 它们主要区别在于：拆得多细，以及是否明确保存人物、关系和背景。

| 格式                           | 怎么存                                        | 优点                   | 代价                                 |
| ---------------------------- | ------------------------------------------ | -------------------- | ---------------------------------- |
| **Simple Notes：简单笔记**        | 一条笔记只存一个事实，如“公司是 TechCorp”“职位是高级工程师”       | 内容短，生成和维护成本低         | 如果拆分时没保留关联，回答复杂问题时就要重新拼接           |
| **Enhanced Notes：完整段落**      | “用户在 TechCorp 任高级工程师，负责推荐系统。”              | 上下文完整，容易理解各事实的联系     | 信息可能重复；同一事实变化时，可能要改多个段落；长段落也更难精确检索 |
| **JSON Cards：结构化卡片**         | 按“类别 → 子类别 → 键值”保存，如 `work.position.title` | 字段明确，可以只更新某一项        | 固定分类可能难以表达同时属于多个类别的信息              |
| **Advanced JSON Cards：增强卡片** | 在事实外，增加来源背景、人物、关系和时间                       | 更容易区分人物、理解情境、关联跨会话信息 | 生成、更新和保持各字段一致的成本更高                 |

这里有两个容易误解的地方：

* **简单笔记不天然保证 O(1)。** O(1) 指操作量不随数据量增长；能否做到，取决于底层数据结构和访问方式。把事实拆短，不代表按内容检索就能固定耗时完成。
* **分类僵硬来自卡片设计。** 例如“周末用 Python 做个人项目”同时涉及时间、技术和活动。强制只放进一个分类会损失关联，但 JSON 本身允许设计多个标签或关系。

JSON Cards 的局部更新很直观：职位变化时，只修改 `work.position.title`，公司名称 `work.company.name` 可以保持原值。

**增强卡片解决的关键问题，是“这条信息到底说的是谁，又是在什么情况下得到的”。**

原文中，“张医生”可能指用户的牙医，也可能指用户父亲的心脏科医生。只记一个名字，后续就容易用错。

增强卡片用这些信息帮助区分：

* **`backstory`：来源背景。** 当时聊了什么，为什么记下这条信息。
* **`person`：主体身份。** 这条信息描述的是谁。
* **`relationship`：人物关系。** 相关人物与用户是什么关系。
* **时间信息。** 帮助判断记录属于哪个时期。

这样，用户说“安排家人的年度体检”时，系统才能关联家庭成员及各自的相关记录。能否正确关联，仍取决于这些字段是否提取、更新准确。

实际选型可以混用：**大量简单事实用轻量笔记；适合固定字段的信息用普通 JSON；关键且需要区分人物、关系或来源的信息用增强卡片。**

**实验 3-2 比较了四种模式，原文报告了定性观察，没有给出具体分数。**

配套项目 `user-memory` 为每种模式实现了两部分：

1. **记忆生成**：分析会话，把信息写入记忆。
2. **记忆检索**：根据当前问题，取回相关记忆。

通过配置切换模式，在同一套三层评估集上测试，比较生成的记忆内容和最终回答得分。

原文报告：

* **Simple Notes**：生成成本最低，能通过第一层“基础回忆”的多数用例；需要综合多条信息或区分同名人物时，经常失分。
* **Advanced JSON Cards**：在区分人物和跨会话关联的用例中表现最好，但每次会话结束后的记忆维护更贵、更慢。

原文没有提供另外两种模式的具体成绩，也没有给出费用、耗时和得分数值。由于每种模式同时包含生成与检索实现，这些观察反映的是**整套实现的效果**，不能把差异全部归因于存储格式。
