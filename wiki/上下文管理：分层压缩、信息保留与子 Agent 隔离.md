**管理上下文，要先判断信息是否值得进入、需要保留多久，再决定保存原文、生成摘要还是直接移除。** 对于过程很长、结论很短的任务，还可以让子 Agent 独立处理，减少主上下文需要接收的材料。[^1]

## 五种可以组合的处理方式

| 方式           | 具体怎么做                                   |
| ------------ | --------------------------------------- |
| **控制工具结果大小** | 大段输出存到文件，模型先看简短预览和文件位置，需要细节时再读取         |
| **直接移除噪声**   | 网页导航、广告、无关重复内容直接从模型输入中移除，省去摘要调用         |
| **API 层清理**  | 使用服务端支持的上下文编辑功能，清除旧工具结果；本地仍可保留完整历史      |
| **归档式摘要**    | 按轮次或阶段分别记录做了什么、为什么这样做、得到了什么结论，保留事情的发展过程 |
| **全量压缩**     | 先整理已有会话摘要；仍不足时，再总结大段历史，形成能继续任务的交接摘要     |

这里的“移除”，指从发给模型的上下文中移除，不等于必须删除外部保存的原始资料。

**工具结果一旦以预览形式进入历史，应保持这条历史记录的呈现方式稳定。** 不要每轮根据剩余空间，反复把同一条消息改成全文或预览，否则容易破坏缓存。

服务端清理也有缓存代价：虽然本地消息不变，模型实际收到的内容变了，相关缓存仍需要重建。接口需要支持和配置这项能力；一次清理足够多的内容，才更可能抵得上重建成本。[上下文编辑文档](https://platform.claude.com/docs/en/build-with-claude/context-editing)

全量压缩还应设置**熔断机制**：连续失败，或压缩后马上又超限，达到重试上限就停止自动重试，保留进度并报告问题。Claude Code 也会停止反复触发却无法缓解问题的自动压缩。[官方说明](https://code.claude.com/docs/en/how-claude-code-works#when-context-fills-up)

## 压缩时怎样保住关键知识

**第一，按任务价值取舍。** 优先保留目标、限制、关键结论和必要证据。证据是否重要，要看它是否支撑后续判断，不能只留下没有依据的结论。

**第二，保留完整意思。** 原文中的“Sutskever 于 2024 年 5 月离开 OpenAI”，如果缩成“Sutskever 离开”，就丢失了时间和对象。关键条件、否定和不确定性也不能随意省略。

**第三，同一材料可以有不同摘要。** 找创始人名单，要检查人员是否列全；分析职业变化，要保留时间和依据；做人物介绍，则可能需要背景经历。摘要应该服务于当前问题。

**第四，压缩方法要匹配材料难度。** 简单筛选、去重可以用代码；复杂材料需要能够保住关键含义的模型。是否够用，应看摘要有没有遗漏重要事实，以及后续任务能否正确完成。

压缩是否划算，还要合计摘要调用、缓存重建和后续处理的成本，不能只看文字缩短了多少。

## 哪些内容应该另存为进度记录

最容易在反复摘要中丢失的，往往是：

* **已经作出的决定，以及为什么这样决定。**
* **必须遵守的限制，以及限制背后的原因。**
* **试过但失败的方法，以及失败原因。**
* **当前进度、未解决的问题和下一步。**
* **关键证据或原始资料的位置。**

这些内容适合随任务推进更新到简短文档中。例如，“方案 A 不采用，因为无法保留终端滚动历史”，比单独写“采用方案 B”更能帮助后续接手。

文档只是保存信息的地方；模型需要继续使用时，框架仍要读取并提供相关内容。本次任务的进度记录，与跨任务积累的长期经验，可以分别管理。

## 什么时候适合用子 Agent 隔离

**子 Agent 上下文隔离，就是让一个独立工作的 Agent 处理大量中间材料，只把需要的结果交回主 Agent。**

沿用原文的示例：任务是在代码库中找到支付回调函数。

主 Agent 亲自搜索，可能会把十几个文件的大段代码都带进上下文。交给搜索子 Agent 后，中间的搜索结果留在子 Agent 的上下文里，主 Agent主要接收结论，例如：

```text
入口：src/payment/callbacks.py 中的 handle_callback
调用关系：列出找到的两处调用位置
依据：说明哪些代码证明它处理支付回调
未确认项：还有哪些路径没有排除
```

这是结果格式示例，不是对某个实际仓库的检查结论。主 Agent 拿到结果后，可以按位置读取必要代码，不必接收全部搜索过程。

派发任务时，要写清楚：

1. **目标**：具体要查明什么。
2. **范围与限制**：在哪个仓库、哪些目录搜索，是否只读。
3. **必要背景**：已有线索、相关决定和排除项。
4. **返回要求**：结论、证据位置和未确认事项。

不要依赖子 Agent 自动知道主会话中的全部背景。Claude Code 的子 Agent 由 `Agent` 工具调用，旧名称是 `Task`；独立上下文和简短结果回传是其主要用途之一。[子 Agent 文档](https://code.claude.com/docs/en/sub-agents)

## 隔离的收益与边界

隔离适合**中间输出很多、任务边界清楚、最终结果较短**的工作，例如搜索代码、分析日志和整理测试失败信息。需要频繁来回沟通、共享大量背景的小任务，留在主上下文中可能更简单。

它减少了主上下文的负担，但仍有三项代价：

* 子 Agent 自身也消耗 token 和时间，总成本不一定更低。
* 回传摘要仍可能遗漏细节，需要保留证据位置和不确定项。
* 子 Agent 的上下文也可能变长，必要时仍需压缩。

当主 Agent 只追加任务调用和结果、没有改动原有前缀时，已有缓存可以保持稳定。**隔离保护的是主上下文的简洁性，并没有消除信息提炼和验证的工作。**
