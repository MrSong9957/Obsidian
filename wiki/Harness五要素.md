# 核心关系

全书只有一套总骨架：

```text
Agent = LLM + 上下文 + 工具
```

而：

```text
Agent = Model + Harness
```

不是另一套体系。

它只是把生产环境里的“上下文 + 工具”进一步拆开看：

```text
Harness
├─ 上下文管理
├─ 工具接口
├─ 约束
├─ 验证
└─ 纠正
```

所以可以理解成：

> **第一套公式告诉你 Agent 由什么组成；Harness 五要素告诉你工程上具体要负责什么。**

# 五要素对应什么

| Harness 要素 | 主要内容                | 典型风险         |
| ---------- | ------------------- | ------------ |
| 上下文管理      | Prompt、状态、压缩、Skills | 提示注入、上下文污染   |
| 跨会话上下文     | Memory、RAG、知识库      | 隐私、敏感信息泄露    |
| 工具接口       | 工具定义、MCP、工具发现       | 工具误用         |
| 约束         | 权限、审批、操作限制          | 越权、不可逆操作     |
| 验证与纠正      | 测试、规则、失败修复          | 错误完成、身份与责任问题 |

其中“工具接口”和“约束”通常会一起讨论，因为：

```text
给 Agent 一个工具
≠
允许 Agent 随便使用这个工具
```

# 不要把所有 Agent 能力都硬塞进五要素

五要素只是在解释**怎么构建单个 Agent 的 Harness**。

其他内容属于不同层面：

```text
交互
→ 扩展 Agent 能看到什么、什么时候行动

评估与进化
→ 判断 Harness 建得好不好，以及怎么改进

多 Agent
→ 从单个 Agent 扩展到 Agent 之间协作
```

因此五要素不是万能分类表。

> **一个分类如果什么都能塞进去，就等于失去了分类价值。**

# 安全不是第六个要素

安全属于 **Cross-cutting Concern（横切关注点）**：

> 它不是单独一个模块，而是横跨所有模块。

例如：

```text
上下文管理 → 防提示注入
工具调用   → 防越权操作
数据访问   → 数据层权限控制
```

因此安全应该继续使用前面的三层模型：

```text
上下文层
执行层
数据层
```

而不是再往 Harness 五要素里硬加一个“安全”。

# 长任务为什么特别依赖 Harness

模型自身有两个天然问题：

1. **上下文有限**
2. **容易过早认为任务已经完成**

Anthropic 在长时 Agent 中采用了类似分工：

```text
初始化 Agent
→ 准备环境
→ 拆任务
→ 建立任务状态

执行 Agent
→ 每次会话推进一部分
→ 保存清晰交接结果
→ 下一次继续
```

本质上是在用 Harness 给模型增加**外部持续状态**。

这样即使：

```text
当前上下文耗尽
→ 新会话启动
```

任务也不会从头失忆。

# 最值得记住的模型

```text
Agent = LLM + 上下文 + 工具
              ↓
        生产化以后
              ↓
Harness =
上下文管理
+ 工具接口
+ 约束
+ 验证
+ 纠正
```

一句话：

> **LLM 决定“想什么、下一步做什么”；Harness 负责让它长期有信息可用、有工具可做事，同时不能乱做，并且做错后能被发现和纠正。**
