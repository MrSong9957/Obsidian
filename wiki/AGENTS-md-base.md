# AGENTS.md 双层架构模板

> 来源：
> - 全局层：[andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) — Karpathy 四条行为准则
> - 项目层：自建

规则正文统一保存在 `AGENTS.md`。Codex、ZCode、MiMo Code 等 Agent 工具原生支持该文件；`CLAUDE.md` 仅用于适配 Claude Code 的加载机制，不维护另一套规则正文。[^codex][^zcode][^mimo]

`CLAUDE.md` 的全部内容只有一行：[^claude]

```markdown
@AGENTS.md
```

全局的 `~/.claude/CLAUDE.md` 导入同目录的 `~/.claude/AGENTS.md`，项目级的 `./CLAUDE.md` 导入同目录的 `./AGENTS.md`。相对导入路径以所在的 `CLAUDE.md` 为基准；调查与文档依据见 [[wiki/agents-md-claude-md|AGENTS.md 与 CLAUDE.md 配置关系]]。[^claude]

# 第一层：全局 AGENTS.md

> 默认示例位置：`~/.codex/AGENTS.md`（Codex 用户级，跨项目生效）。设置了 `CODEX_HOME` 时使用其目录内的 `AGENTS.md`。[^codex]

全局层放**行为准则 + 个人偏好**，不放项目特定配置。下方 Karpathy 四条准则供各 Agent 复用；项目层为自建规范。[^karpathy]

### 不同 Agent 的全局规则入口

| Agent 工具 | 规则正文位置 | 加载方式 |
|---|---|---|
| Codex（默认） | `~/.codex/AGENTS.md`，或 `$CODEX_HOME/AGENTS.md` | 原生读取；同目录非空 `AGENTS.override.md` 优先于 `AGENTS.md`。[^codex] |
| Claude Code | `~/.claude/AGENTS.md` | 适配文件 `~/.claude/CLAUDE.md` 仅含一行 `@AGENTS.md`。[^claude] |
| ZCode | `~/.zcode/AGENTS.md` | 原生读取用户全局与当前 Workspace 的 `AGENTS.md`；不展开 `@import` / `@include`。[^zcode] |
| MiMo Code | `<实际全局配置目录>/AGENTS.md`；Linux 通常为 `~/.config/mimocode/AGENTS.md` | 原生读取；也可在用户配置的 `instructions` 数组中显式指定共享规则文件的绝对路径。[^mimo] |

`~` 表示运行该 Agent 的用户主目录。规则目录与程序安装目录是两回事；其他支持 `AGENTS.md` 的工具，按其实际用户配置目录放置相同规则正文。

MiMo Code 的 Windows / XDG 路径应以当前版本实际解析的配置目录为准；设置 `MIMOCODE_HOME` 时使用 `<MIMOCODE_HOME>/config/AGENTS.md`，设置 `MIMOCODE_CONFIG_DIR` 时优先检查该目录下的 `AGENTS.md`。不要把项目级 `.mimocode/` 当成用户全局目录。[^mimo]

同时使用多个工具时，将下方 `AGENTS.md` 正文放入各工具的原生入口，或使用其明确支持的共享文件配置。`CLAUDE.md` 的单行适配仅用于 Claude Code。[^claude][^zcode][^mimo]

### 全局规则正文

````markdown
# AGENTS.md

## Karpathy 编码准则

减少常见编码错误，与项目指令配合使用。这些准则偏向谨慎；小任务可适当简化流程。

### 1. 编码前思考

**不擅自猜测，把疑问和取舍说清楚。**

- 修改前，先读相关实现和测试。
- 说清假设；有疑问先问清，再实现。
- 有多种理解时，列出差别，不擅自选。
- 有更简单的办法，主动提出；必要时指出当前方案的问题。

### 2. 极简主义

**用最少的代码解决问题，不为猜测中的需求做准备。**

- 不添加需求之外的功能、灵活性或配置项。
- 只用一次的代码，不必包装成通用接口或框架。
- 不处理不可能发生的错误。
- 能用 50 行解决，就别写 200 行。

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

### 3. 精准修改

**只改任务需要的内容，只清理自己造成的问题。**

- 先查看已有的未提交改动，不覆盖或回滚用户及其他 Agent 的工作。
- 不顺手修改无关代码、注释或格式，不重构没坏的代码。
- 遵循项目现有风格。
- 清理本次修改造成的无用导入、变量和函数。
- 发现原有且与任务无关的废弃代码，只提醒，不删除。

**检验标准：** 每一处修改，都能说清与当前任务的关系。

### 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

- 添加校验：先写无效输入的测试，再让它通过。
- 修复 bug：先写能复现问题的测试，再修到通过。
- 重构代码：确认修改前后测试都通过。

对于多步骤任务，说明一个简短的计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```
同一办法反复失败时，先补证据、查原因，再继续修改。
完成条件要具体，不能只写“让它工作”。

````

# 第二层：项目级 AGENTS.md

> 文件位置：`./AGENTS.md`（项目根目录，项目特有）

项目层放**开发规范 + 项目配置**。每个项目独立定制。

```markdown
# AGENTS.md — 项目规则

## 1. 项目原则

- 用简化技术规范（ASD-STE100 中文版）解释或写作，要求极简、说人话。
- 默认采用最小实现和必要验证。不得删减需求；未经要求，不得自动增加功能、通用接口、性能优化，或为未来做兼容。
- 优先复用经过验证的成熟开源方案，只实现必要部分。通过调研核实适用性，不得仅凭模型记忆或仓库星数选择。
- 用户确认关键需求和取舍。查清仓库事实，在授权范围内决定普通实现细节。已明确的事项不得重复澄清。

## 2. 项目文档

写计划前，读取并遵守 `rules/规格文档模板.md`。代码审查前，读取并遵守 `rules/REVIEW.md`。

功能规格和证据记录与代码放在同一仓库，统一存放在 `docs/`：

| 目录 | 要求 |
|---|---|
| `docs/specs/` | 一个功能一份规格，不合并不同功能。文件名为 `编号-功能英文名.md`，如 `001-daily-checkin.md`。 |
| `docs/logs/` | 存放设计依据和验证证据。 |

实现前按模板编写或更新规格，并由用户确认。规格写清本轮目标、输入输出、边界、约束和可观察的验收结果；已有规格更新原文件，不建重复文档。简单任务可简写，但约束内容必须完整。

规格与已确认的要求一致，沿用既有名称和说法，必要术语就地解释。写清触发条件、执行动作和可观察结果，不用抽象术语代替具体行为。不得擅自增删要求、改变取舍，或把未确认问题写成结论。用户只看规格，即可核对是否忠实表达了讨论结果。

规格保留调研汇总及各专家原始输出的链接。实现变化后，更新相关规格、验收时的实测记录、文档和注释。局部取舍的原因写在代码附近。将草稿中的有效结论提炼进正式文档。

## 3. 开发流程

任务分两步。第一步最小实现走最小路径，跑通产出候选版本。第二步查缺补漏走完整路径，补齐边界，产出最终候选版本。所有开发任务，包括简单任务，都必须完成共同准备。

### 共同准备

```text
ce-brainstorm（按需）
→ 计划前调研
→ 讨论
→ 第一步规格并由用户确认
→ 第一步计划并由用户确认
→ Agent 准备任务分支
```

- 用户未想好需求，或目标、预期行为、关键取舍不清时，使用 `ce-brainstorm`；需求清楚时直接调研。
- 计划前调研：按 `rules/计划前调研.md` 执行。查阅官方文档、上游实现和项目现状，选择符合当前约束的最佳实践。结论附出处，区分事实与推断；资料不足时说明。不得自动扩大功能；额外调查须解决当前决策的具体疑问。
- 讨论：与用户共定方案，只谈核心问题。普通执行由 Agent 负责，已约定的要求不得简化。新增功能先调研再讨论；每完成一步，先汇报完成的工作，再定下一步。
- 规格：按第 2 节执行。
- 计划：用 `ce-plan` 写计划并落盘，结构如下；经用户确认后才开始实现。
  - 整体级：本轮范围与不做的部分；步骤清单，每步一个模块或一个函数；必要的依赖及原因。
  - 每步：改动对象与不碰的部分。实现前写入正常场景（场景、给定与输入、期望输出／状态／报错、测试文件与用例名、按名称过滤的命令），先确认失败再实现，跑通即过。实现要点一两句，取舍引用调研结论。完成定义为正常场景全部通过并逐条对照期望。
  - 第二步增补：第一步候选版本经用户验收后，按增量规格把边界、异常场景补进计划，经用户确认后再走完整路径。场景要素与第一步相同。场景先确认失败暴露缺口，再补实现，通过即完成。
  - 替代规则：重构步不新增场景，行为变化按新行为补场景；无测试可能的改动写明替代验证（命令与可观察结果）。
  - 不写入：完整代码、调研过程、未来兼容、与规格重复的目标。简单任务的计划可简写，但范围、步骤、测试场景（含输入与期望）不得省略。

### 第一步：最小路径

```text
ce-work
→ ce-simplify-code
→ ce-code-review
→ 最小验证
→ 候选版本经用户验收
```

### 第二步：完整路径（第一步候选版本经用户验收后进行）

```text
增量规格并经用户确认
→ 计划增补并经用户确认
→ ce-work
→ comprehensive-testing
→ Security Testing（适用时）
→ ce-simplify-code
→ ce-code-review
→ 全量验证和修复
→ ce-compound
→ 最终候选版本
```

- 执行按计划小步推进：可测步骤先写测试、确认失败，再实现、确认通过；通过该步验证后再做下一步，不得攒到最后一起验证。每步改动保持可审查、可回退。
- 疑难问题使用 `ce-debug`。同一方法反复失败时，先补充证据，再继续处理。
- `comprehensive-testing` 覆盖规格验收、边界、异常和受影响的回归测试，检查实际结果、状态及副作用。
- 两条路径都须按风险执行安全测试：已识别安全风险，或新增安全敏感的部分时，执行 `Security Testing`。执行或跳过均说明依据；执行时必须通过。
- 安全测试通过或确认不适用后，才执行 `ce-simplify-code`。简化改变代码时，先重跑受影响的检查，包括相关安全检查，再进入代码审查。
- 两步各自完成其路径的最终验证和适用检查。之后再改影响结果的代码时，重跑受影响的检查和受影响范围的局部验证。

### 实现方式：模块灰盒法

开发任务默认按模块灰盒法实现，细则见 `rules/模块灰盒法.md`：一次做一个函数或模块，接口先行，Agent 只填模块内部实现。一次性脚本和随手试的原型不适用。

两步的划分见本节开头；灰盒法下，第一步逐块跑通，第二步按增量规格补齐边界。

- 接口由用户定：用户自己写，或 Agent 起草后经用户确认；Agent 不得定接口。
- 用户定的接口和验收测试，Agent 不得改动。
- 不得为跑通加绕路；发现按接口写不下去，停下报告，不得糊过去。
- Agent 跑编译和测试须附命令和实际输出，不得只报「通过」。第一步每块经用户验收后再做下一块。第二步全量验证后，经用户验收收尾。

## 4. 场景与验证方法

| 场景 | 验证方式 |
|---|---|
| Web | 启动真实项目，用无头浏览器模拟操作，检查页面结果和相关数据。 |
| 普通 CLI | 启动真实进程，检查标准输出、错误输出、退出码和文件变化。 |
| 交互式 CLI / TUI | 用伪终端模拟输入和按键，检查渲染后的屏幕、光标和状态。Windows 使用 ConPTY，优先采用 `node-pty` 和 `@xterm/headless`。 |
| 终端缩放、滚动历史等宿主行为 | 在目标终端补充验证。模拟屏幕通过仅算部分证据。 |
| Bug 修复 | 在最低可复现层增加或更新回归测试，确认修复前失败、修复后通过。 |
| 行为或接口变更 | 补充或复用回归测试；涉及对外接口、Schema 或持久化数据时，执行适用的兼容性检查。 |
| 关键测试或高风险模块 | 保持断言不变，用前后对照或临时破坏被测行为，证明测试能检出错误。已有有效证据时不重复证明。高风险模块按需做变异测试。 |
| 完整、稳定的输出 | 使用聚焦快照或黄金文件。先检查差异，确认符合需求后才更新预期，并说明原因。 |
| 外部 API 或网络服务 | 按需录制并回放响应，使测试可离线复现，不依赖真实密钥。去除录制内容中的敏感信息。 |
| 并行、随机或时间相关测试 | 隔离环境，固定影响断言的输入，保留失败种子或输入。时间逻辑使用可控时钟；真实计时设置超时和容差，不断言精确耗时。 |
| CI | 核对触发事件、分支和平台。设置并核验取消过时任务的机制，避免重复触发。重跑前检查目标提交已有结果，优先补跑失败或未完成任务。不得用旧任务验证新版本。用日志核对耗时、缓存命中和保存的产物（artifacts）。超时先区分正常耗时与卡死。 |
| 静态质量检查 | 按改动范围执行项目已有的类型检查、代码检查及确定性检查。 |

缺少工具时，先尝试自动化替代方案，不得直接转交用户手测。仍无法验证时，说明未验证范围、原因和影响，不得计为通过。
