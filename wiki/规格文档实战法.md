# 规格文档实战法

## 核心思想

**一条主线：每个功能 = 一份规格文档。文档写完，经验就留下了，代码随用随生成。**

规格是母版，代码是渲染结果：你攒母版，AI 负责渲染——这就是"用规格代替代码"。规格文档同时承担**学习**（预测→实测→坑记录的完整认知闭环）与**编程**（以文档驱动 AI 生成代码）两个职能。代码会过时、语言会换，但"为什么这么写、踩过什么雷"永远跟着你——这就是 AI 时代的资深。

## 详细说明

### 原则：两层，别混

- **文档**：规格、判断、坑记录——跨语言、跨项目，永久资产。
- **注释**：某段代码的局部解释——就近写，改代码顺手改。

| 内容 | 放哪 |
|---|---|
| 输入、输出、边界、约束 | 文档·第1节 |
| 风险点 & 关键判断（为什么） | 文档·第2、3节 |
| 预测 & 实测结果、坑记录 | 文档·第4节 |
| 某段代码为什么这么写 | 注释 |
| 临时草稿 | 事后提炼进文档，别当垃圾堆 |

### 流程：五步，就是"把文档填出来"的过程

以 **"每日签到"接口**（每天一次，返回连续签到天数）为例。

**第 1 步 想清楚（不碰 AI）→ 填进「目标 & 风险」**
输入用户 ID，输出今日状态 + 连续天数。哪里会挂？并发重复签、23:59 跨天怎么算、断签怎么归零。

**第 2 步 先预测，再让 AI 写 → 填进「预测」**
不写注释了，直接写进文档："并发签两次会插两条 → 多算一天"。然后让 AI 分步写（建表→插入→统计），每步能跑、你能讲明白，才走下一步。

**第 3 步 实测 → 填进「实测」**
并发 2 请求插进 2 条——预测对了。又测出服务器 UTC、用户东八区，晚 8 点被算成"明天"——**预测漏了，补记**。

**第 4 步 出 bug 先自己判断 → 填进「关键判断」**
① 并发不能靠"先查后写"，要 DB 唯一索引；② 日期按用户时区算好再入库；③ 连续天数用计数字段，不实时 count。

**第 5 步 抽坑 → 填进「坑记录」**

### 最终成品：这份文档长这样

```markdown
# 规格：每日签到

## 1. 目标 & I/O
- 输入：user_id
- 输出：{今日已签, 连续天数}
- 约束：每天一次；按用户时区算"天"

## 2. 边界 & 风险
- [x] 并发重复签到
- [x] 跨时区跨天（东八区 vs UTC）
- [x] 断签归零
- [x] 高频查询性能

## 3. 关键判断（为什么）
- 并发挡重：用唯一索引（user_id+日期），不用"先查后写"——查插之间有竞态
- 时间：按用户时区算好日期再入库，不存服务器本地时间
- 性能：连续天数存计数字段+断签重置，不实时 count

## 4. 坑记录（跨语言可复用）
- 坑001：凡"每天一次/不能重复"，必须 DB 唯一约束，代码级查重不可靠
- 坑002：凡"哪一天"，先定清楚用谁的时区
- 坑003：凡"累计/连续次数"，用计数字段，别每次 count

## 5. 预测 → 实测
- 并发 2 请求 → 期望插 1 条 → 实测 2 条 ❌ → 加唯一索引后 ✅
- 20:00（东八区）签到 → 期望算今天 → 实测算成"明天" ❌ → 按用户时区 ✅
```

> 注意第 5 节：**❌ 不是丢人，是经验**。预测对了长信心，预测错了长经验，漏测的（时区）更是捡到宝。

### 怎么转成任意技术栈

拿这份文档投喂 AI，改一个词就行：

> "按这份规格，用 Go + MySQL 实现" / "用 Python + Postgres 实现" / "用 Java 重写"

**规格是母版，代码是渲染结果。** 你攒母版，AI 负责渲染——这就是"用规格代替代码"。

### 三条提醒

1. **一页纸为限**，写不动的文档等于没写。
2. **坑记录是核心资产**——规格喂给 AI 会越用越平，坑记录越攒越值钱。
3. **代码改、文档必改**，否则文档就是骗子。

# 目录结构：分两处放，一处跟项目走，一处跟你走

**核心思路：规格跟项目走（放 `docs/`），坑记录跟人走（放自己的 obsidian 知识库）。**

理由很简单——**项目会结束，你会一直在。** 把最值钱的坑记录埋在某个项目里，等于埋了就忘。

---

## 一、项目内：`docs/` 目录（跟代码同仓库）

```
project/
├── src/
├── docs/
│   ├── index.md              # 目录导航，一句话列出所有规格
│   ├── specs/                # 规格文档（核心）
│   │   ├── 001-daily-checkin.md      # 每日签到
│   │   ├── 002-user-auth.md          # 用户认证
│   │   └── 003-order-payment.md      # 订单支付
│   ├── decisions/            # 重大技术决策（可选）
│   │   └── 001-why-postgres.md
│   └── pitfalls.md           # 本项目踩坑汇总（同步一份到全局）
└── README.md
```

**命名规范：**
- 文件名 = `编号-功能英文名.md`，编号保证顺序、便于引用。
- 一个功能一份文档，**不合并**——将来换技术栈重写某个功能，直接拎这一份走。

---

## 二、个人知识库：`obsidian`（跟人走，跨项目）

**关键设计：坑按"主题"归类，不按项目归类。**
比如"坑001 唯一约束"写进 `db-integrity.md`，将来做电商、做社交、做工具，全都能搜到。

---

## 三、规格文档的内部结构（就是之前那五节，固定不变）

```markdown
# 规格：每日签到

> 状态：草稿 / 实现中 / 已上线     更新：2026-xx-xx

## 1. 目标 & I/O
## 2. 边界 & 风险
## 3. 关键判断（为什么）
## 4. 坑记录 → 同步到 ~/dev-notes/pitfalls/
## 5. 预测 → 实测
```

**固定五节的好处**：AI 读起来格式稳定，你自己填的时候也不用想"该写点啥"，照格子填就行。
