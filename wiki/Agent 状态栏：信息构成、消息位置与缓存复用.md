**状态栏把任务进度、事件背景和当前环境整理好，让模型每次行动前都能看到最新情况。** 框架负责维护这些信息，再把它们放进发给模型的消息中。[^1]

## 状态栏包含什么

| 类型         | 记录什么                     | 怎样更新                 |
| ---------- | ------------------------ | -------------------- |
| **任务规划**   | 用户目标、核心限制、待办步骤及完成情况      | 随任务进展更新，提醒模型还有什么没做   |
| **事件辅助信息** | 某次事件发生的时间、当时的位置、距上次回复的间隔 | 跟着对应事件一起保存，帮助理解当时的情况 |
| **当前状态摘要** | 当前时间、工作目录、累计调用次数、重复操作提醒  | 根据最新情况更新，帮助模型决定下一步   |

原文把事件辅助信息称为**侧信道信息**：它不是事件的主要内容，但能补充理解所需的背景。

例如，工具正文是“电话未接通”，辅助信息是“这次拨打发生在 10:30”；当前状态摘要则可以写“已经拨打三次，达到上限”。前者描述某次事件，后者概括截至现在的情况。

## 在消息列表中放在哪里

原文采用的方式是：**保留开头的系统指令，把状态栏作为一条 `user` 消息追加到末尾。**

下面是消息结构示意，中间省略了三次通话的具体记录：

```javascript
messages = [
  {
    role: "system",
    content: "你是客服助手。对同一商家最多拨打三次电话。"
  },
  {
    role: "user",
    content: "帮我取消 Xfinity 套餐。"
  },

  // 此处省略已有的模型回复、工具调用和工具结果

  {
    role: "user",
    content: "再打一次催一下。"
  },
  {
    role: "user",
    content: `<agent_status>
当前任务：取消 Xfinity 套餐
任务进度：尚未完成
拨打次数：3/3，已达上限
下一步：向用户说明限制，讨论其他处理方式
</agent_status>`
  }
];
```

最后一条消息由框架生成。这里借用了 `user` 角色的消息格式，**并不表示这些文字是真实用户输入的**。

`<agent_status>` 只是帮助模型识别状态区域的文本标记，不会自动赋予这段内容系统指令的权限。这也是一种实现方式，具体消息格式仍需符合所用接口的要求。

## 为什么适合追加在末尾

一是集中提供最新状态，方便模型在作出下一步决定时使用。放在末尾可以突出这些信息，但**不能保证它们一定获得最高注意力权重**。

二是便于复用 **KV Cache，也就是模型对前文计算结果的缓存**。复用依赖相同的前缀——从上下文开头算起，连续不变的那段内容。

* **末尾追加状态**：前面的内容没变，已有计算结果仍有机会复用。
* **修改开头的系统指令**：从首次变化的位置开始，后面的缓存通常需要重新计算。因此，不适合把每轮变化的时间、进度和计数反复写进开头。

这里的关键是**追加，而不是改写历史**。如果下一轮删除、移动或修改了旧状态栏，就只能复用首次变化之前的那段前缀；不能仅凭“新状态仍放在末尾”，就认为全部旧缓存都能保留。
