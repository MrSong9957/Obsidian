## 一句话理解

**工具让 Agent 从“会说”变成“会做”。**

没有工具：

> Agent 只能给建议。

有了工具：

> Agent 才能读取真实信息、执行操作、影响外部世界。

---

## 工具的 5 类

| 类型     | 作用             | 例子                      |
| ------ | -------------- | ----------------------- |
| 感知工具   | 获取外部信息         | 搜索、读文件、数据库、API          |
| 执行工具   | 改变外部状态         | 写文件、跑代码、系统命令、API 操作     |
| 协作工具   | 和人或其他 Agent 配合 | 子 Agent、人工确认、多 Agent 协作 |
| 事件触发工具 | 外部事件主动唤醒 Agent | 邮件、定时器、Webhook          |
| 用户沟通工具 | 主动向用户传递信息      | 消息、电话、邮件                |

前两类最好记：

```text
感知工具：世界 → Agent
执行工具：Agent → 世界
```

## Tool Calling 怎么工作

基本流程只有 4 步：

```text
1. 告诉模型有哪些工具
        ↓
2. 模型决定要不要调用、调用哪个、传什么参数
        ↓
3. Harness 真正执行工具
        ↓
4. Tool Result 加回上下文
        ↓
模型继续决定下一步
```

例如：

```text
用户：北京天气怎么样？

模型：
get_weather(city="北京")

工具：
{"temp": 28, "sky": "晴"}

模型：
北京今天 28°C，晴。
```

关键点：

> **模型负责“决定调用”，真正执行工具的是外部 Harness / Environment。**

这个循环也是 ReAct 的基础。

## 工具设计为什么重要

模型与外部世界之间，主要就是靠工具接口沟通。

因此：

```text
工具定义模糊
→ 模型容易调错

错误处理差
→ Agent 可能反复失败

权限太大
→ 一次错误可能造成严重后果
```

所以 Agent 强不强，不只看模型，还看：

> **给了什么工具，以及工具设计得好不好。**

MCP 的价值之一，就是让不同工具更容易以统一协议接入 Agent。

# 工具该做多专，还是多通用？

核心原则：

> **先给最窄、够用的能力，确实需要时再扩大。**

### 简单任务：专用工具

例如只做四则运算：

```text
calculator(a, b, operation)
```

比直接给 Python 更简单、更安全。

---

### 复杂探索：通用工具

如果任务变成：

```text
读取 Excel
↓
清洗数据
↓
统计分析
↓
画图
```

与其设计几十个工具，不如提供：

> **受控的 Python Code Interpreter**

因为代码更容易自由组合。

---

## 通用工具的代价

能力越通用：

```text
能力范围 ↑
灵活性 ↑
同时
错误范围 ↑
攻击面 ↑
```

所以代码执行器必须放进沙箱，例如限制：

* 默认不能访问网络；
* 只能访问授权目录；
* CPU / 内存限制；
* 执行时间限制；
* 输出大小限制。

核心思想：

> **给 Agent 能力，同时限制能力能影响的范围。**

---

## 长程任务为什么需要工作目录

短任务：

```text
日志
```

可能就够了。

但几小时甚至几天的任务，需要保存：

```text
计划
中间结果
日志
最终产物
```

因此可以给 Agent 一个受控工作目录：

```text
workspace/
├─ plan.md
├─ data/
├─ logs/
└─ output/
```

这样 Agent 下次运行还能继续。

但同样要限制：

* 可访问路径；
* 文件大小；
* 总容量；
* 文件类型；
* 防止 `../` 路径越界。

# 高风险操作不要做成通用能力

有些操作即使通用工具能完成，也不应该直接开放。

例如：

* 支付；
* 删除数据；
* 发邮件；
* 生产部署。

更好的做法：

```text
专用工具
+
明确参数
+
权限限制
+
审计日志
+
必要时预览
+
人工确认
```

例如不要让 Agent 自己写任意脚本操作支付系统，而应提供：

```text
refund_order(
    order_id,
    amount,
    reason
)
```

这样业务规则可以直接写进工具。

## 最重要的工具设计原则

可以压缩成一句：

> **通用工具负责探索，专用工具负责约束。**

即：

```text
低风险 + 组合性强
→ 通用工具

高风险 + 业务规则强
→ 专用工具
```

再进一步：

> **先从最窄能力开始，随着任务需要再逐步扩大动作空间。**

这样既保留 Agent 的能力，也不会一开始就把整个系统权限交给模型。
