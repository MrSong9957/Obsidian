# 第二章：上下文工程 章节结束的深度思考题[^1]

> **1. ★★★** 实验 2-3 发现，滑动窗口对话历史会导致 Agent 反复执行相同的工具调用。但完整保留历史又会让上下文不断膨胀。设计一种策略，既能避免信息丢失，又能控制上下文长度，且不破坏 KV Cache 前缀。

**大白话：** 怎么让 Agent 记得以前做过什么，又不用每次重读全部聊天记录，还能尽量复用之前的计算？

**解答：** 先区分：**资料保存在哪里，与模型这次需要看到什么，是两回事。**

可以分三层：

* **完整档案：** 原始对话、工具结果存在外部文件或数据库，随时可查。
* **当前笔记：** 上下文只保留目标、约束、已完成事项、失败原因和原文位置，防止重复劳动。
* **最近现场：** 保留最近几轮必要细节，需要旧资料时再取回。

系统提示词和固定工具定义保持不变；平时追加消息，在阶段结束时批量压缩历史。

**边界：** 无限增长的历史，不可能同时做到“全部留在有限窗口里”和“永远不改已有内容”。能保住的是不变的前部；被压缩位置之后的缓存仍需重建。[缓存机制说明](https://code.claude.com/docs/en/prompt-caching)

> **2. ★★** Qwen3 的 Chat Template 思维链保留机制只保留“最后一个真实用户消息之后”的思考。如果一个 ReAct 循环跨越了上百轮工具调用，累积的思考内容可能消耗大量上下文。你会如何修改这个机制来应对超长循环？DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部 reasoning_content——对比这两种相反的策略，各有什么利弊？这个反转说明了什么？

**大白话：** Agent 一直“想一想、调用工具、再想一想”，思考草稿越积越多，怎么办？为什么有的模型要求删掉旧草稿，有的却要求保留？

**解答：** Chat Template 是“把消息整理成模型输入的格式规则”；ReAct 就是“判断下一步 → 使用工具 → 根据结果继续”。

**旧思考有两部分：有用的中间结论，以及已经用不上的草稿。** 长循环应该分别处理：

* 不只等用户发新消息才清理，增加“达到长度上限”或“完成一个阶段”的清理时机。
* 把关键结论、依据、失败原因和下一步写成简短交接记录。
* 保留仍在进行的步骤所需细节，避免删断工具调用与结果的对应关系。

这是可自行修改模板时的设计方案，修改后需要验证效果。[Qwen3 模板源码](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/tokenizer_config.json)

两种策略的取舍是：

| 策略     | 好处           | 代价              |
| ------ | ------------ | --------------- |
| 删除历史思考 | 输入更短，减少旧草稿干扰 | 中间结论可能丢失，容易重新推导 |
| 保留历史思考 | 推理更连贯，方便接着做  | 占用上下文，也可能延续旧错误  |

早期 R1 接口确实要求移除历史 `reasoning_content`。[早期接口说明](https://deepseek.apidog.io/reasoning-model-deepseek-reasoner-835841m0)

题目对新规则需要补充条件：按当前 DeepSeek 文档，**思考模式下，请求携带 `tools` 时需要完整回传历史思考；不携带时，历史思考会被忽略。** 因此不能随意删除接口要求的字段；必要时应完成阶段，再用交接记录启动新的独立任务。[当前接口说明](https://api-docs.deepseek.com/guides/thinking_mode/)

**这个反转说明：保留策略依赖模型训练和接口设计，没有适用于所有模型的固定答案。**

> **3. ★★** 上下文感知压缩实验中，从约 148K 个字符压缩到约 2,000 个字符，这种极端的压缩是否存在“不可逆信息损失”的风险？如何解决？

**大白话：** 把十几万字压成一小段，会不会把以后需要的东西删没了？怎么补救？

**解答：** **摘要只能保留部分信息，无法保证回答未来所有问题。**

例如，把巡查记录压成“90 只黑猫、10 只白猫”，能回答数量，却无法回答“第 37 个笼子里是什么猫”。

所以：

* 原文另存，摘要附上能定位原文的位置。
* 优先保留当前任务需要的事实、时间、约束、理由和未确定事项。
* 新问题超出摘要范围时，回查原文，不能凭摘要猜。

**摘要丢掉的细节，无法靠摘要本身恢复；保留原文，才能让整个系统仍有补救能力。** 重要网页最好保存副本，单留链接可能遇到内容变化或失效。

> **4. ★★** Agent 状态栏将隐式状态显式化。但如果状态栏本身包含了错误信息（比如工具计数器出了 bug），Agent 可能基于错误的信息做出有害的决策。这种“元信息可靠性”问题如何缓解？

**大白话：** 如果给 Agent 看的进度表写错了，它照着做就会出错。怎么避免？

**解答：** **状态栏是根据事实制作的报表，不能让报表成为唯一依据。**

* **从真实记录生成：** 根据工具实际执行的日志统计，不能根据模型说“我做了”就算完成。
* **能够核对：** 每次操作有唯一编号，避免重复计数；发现状态与日志不一致时重新计算。
* **关键限制由代码执行：** “最多打三次电话”应在拨号前检查，不能只靠模型记住。

例如，状态栏误写“已打两次”，但执行记录已有三次，拨号程序仍应拒绝第四次。

> **5. ★★** 提示工程消融实验表明，信息组织的混乱导致成功率下降 30% 以上。但在实际开发中，系统提示词往往由多人在不同时间维护。你会用什么工程实践来防止系统提示词的“熵增”？

**大白话：** 很多人不断往提示词里加要求，最后重复、冲突、看不懂。怎么防止它越改越乱？

**解答：** “熵增”在这里就是**规则越积越多，关系越来越乱**。要像维护代码一样维护提示词：

* **固定结构：** 目标、约束、工作流程、输出格式各放各的位置。
* **一条规则只有一个正式版本：** 新规则替代旧规则时，删除过时内容，说明冲突时谁优先。
* **修改有记录、有审查：** 能看出谁改了什么、为什么改，也能退回旧版本。
* **用固定任务检查效果：** 看改完后是否更容易完成任务、是否违反约束。

题中的“下降 30% 以上”应理解为原文报告的实验结果，不能当成所有系统都会出现的固定幅度。

> **6. ★★★** 本章提出“上下文学习本质上是检索而非推理”。如果这个论断成立，当前所有基于“把更多信息塞进上下文”的优化方向都需要重新审视。你认为应该如何突破这一局限？

**大白话：** 如果模型只是擅长翻资料，给它更多资料也不等于让它更会思考，那应该怎么改进？

**解答：** 先修正前提：**“上下文学习本质上只是检索”说得太绝对。** 模型也能从示例中归纳新规律，这方面的内部机制仍在研究中。[相关研究](https://arxiv.org/abs/2507.16003)

但这道题的工程提醒是有用的：**信息已经放进去，不等于结论已经算出来。**

可以把工作拆开：

* **找资料：** 只取当前问题相关的内容。
* **做计算：** 计数、排序、金额计算等交给代码。
* **做判断：** 让模型根据整理后的事实分析关系、提出方案。
* **查结果：** 用原始证据或实际执行结果验证结论。

例如，查销售情况时，先用程序算出各月销量，再让模型分析变化原因，就不用每次都从几万条订单重新数起。

> **7. ★★★** Skills 的渐进式披露只在 Agent 判断需要时才加载完整内容。但这个判断本身依赖模型的能力——如果模型不知道自己不知道什么，就无法正确触发 Skill 的加载。这个“元认知”问题如何解决？

**大白话：** Agent 连“这件事需要查操作手册”都没意识到，手册写得再好也没用。怎么办？

**解答：** **不能把“是否需要帮助”完全交给模型自己判断。**

可以提供几条入口：

* **清楚的目录：** 每个 Skill 写明“解决什么问题、什么时候用”，让模型知道有什么可选。
* **明确的触发规则：** 已知工作流程由框架加载对应 Skill；用户点名的 Skill 直接加载。
* **遇阻时查目录：** 缺少步骤、工具或知识时，先搜索相关 Skill，再决定怎么继续。
* **检查漏用情况：** 用真实任务测试，发现“该用却没用”就改描述或触发规则。

例如，用户明确要求生成 PDF，可以由框架触发对应制作流程，不必等待模型自己意识到需要学习。

Skills 规范也支持由模型或用户选择后激活，并非只能依靠模型自发判断。[Skills 加载机制](https://agentskills.io/client-implementation/adding-skills-support)

> **8. ★★** Skills 机制中，Agent 从 SKILL 文件中动态读取提示词之后，后续的操作能否正确遵从这些指令？不同的模型对 Skills 模式的支持有什么区别？

**大白话：** Agent 读完操作手册，就一定会照着做吗？换个模型，效果会有什么不同？

**解答：** **读到了、理解了、做对了，是三件不同的事。** Skill 是操作说明，不能像程序一样保证每一步都会执行。

框架负责发现并读入 Skill；模型负责理解和执行。不同模型主要差在：

| 能力     | 容易出现的差别          |
| ------ | ---------------- |
| 选择能力   | 能否选中正确的 Skill    |
| 指令遵循能力 | 能否记住约束，按顺序完成多步操作 |
| 工具使用能力 | 能否填对参数，并根据错误调整行动 |

所以不能仅凭“支持读取 SKILL.md”就认为支持得好。应当用同一组任务检查：有没有选对、漏步骤、违反约束、完成目标。

对表现较弱的模型，可以缩短说明、拆小步骤、由框架推动流程；必须满足的限制则由代码检查。[Skills 集成说明](https://agentskills.io/client-implementation/adding-skills-support)

> **9. ★★★** 本章强调动态信息（如系统时间戳、工具列表顺序）的变化会破坏 KV Cache 前缀命中。在一个拥有大量工具且工具集频繁变动的生产系统中，你会如何设计上下文布局来最大化缓存命中率？

**大白话：** 工具越来越多、还经常变化，怎么避免每变一点东西，就把前面已经算过的内容重新算一遍？

**解答：** **缓存能复用的前提，是之前那段输入保持一致。越容易变化的内容，越应该往后放。**

可以这样安排：

| 位置    | 放什么                |
| ----- | ------------------ |
| 最前面   | 稳定的系统规则、少量固定工具入口   |
| 后面    | 对话、已经加载的工具说明与结果    |
| 最新追加处 | 当前时间、最新状态、新发现的工具信息 |

具体做法：

* **工具按需加载：** 使用接口支持的工具搜索；不支持时，可设计固定的“查找工具”和“执行工具”入口，完整工具库放在程序端。
* **保持顺序和版本稳定：** 工具定义不随机排序，也不每轮改写描述；普通更新尽量在任务边界切换。
* **动态信息只写新记录：** 时间戳写入对应事件后就固定，不每轮刷新历史时间。
* **权限实时检查：** 缓存里的旧工具说明不能代替执行时的权限判断。

支持延迟加载的接口可以减少工具变化对前缀的影响；若直接修改已经放在前缀里的工具定义，仍需承担缓存重建成本。[工具搜索机制](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)、[工具变化与缓存](https://code.claude.com/docs/en/prompt-caching)
