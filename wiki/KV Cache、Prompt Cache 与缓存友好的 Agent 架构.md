**两层缓存分别减少生成过程和多次请求之间的重复计算。**

模型先把输入拆成 token，也就是处理文字的基本单位，再计算每个 token 的 K、V 数值。K 帮助判断该关注哪些内容，V 提供这些内容的信息。

| 缓存               | 怎样工作                              | 主要节省什么                 |
| ---------------- | --------------------------------- | ---------------------- |
| **KV Cache**     | 保存已经算好的 K、V；生成下一个 token 时，复用前文的结果 | 单次生成过程中，对旧 token 的重复计算 |
| **Prompt Cache** | 服务端匹配不同请求的相同前缀，直接复用此前保存的 KV Cache | 多次请求之间，对相同输入的重复计算      |

模型处理输入、建立 KV Cache 的阶段叫 **prefill（预填充）**；随后逐个生成 token 的阶段叫 **decode（解码）**。Prompt Cache 主要减少重复的预填充，模型仍需处理新增内容并生成回复。

两者是上下层关系：**Prompt Cache 把 KV Cache 的复用范围扩展到了多次请求。**

缓存读取通常比重新计算便宜。原文用 Anthropic、DeepSeek、GPT-5“约十分之一”说明差价，但这不是统一价格：GPT-5 的缓存输入价格确为普通输入的十分之一，其他厂商和模型的比例会不同；启用方式、有效期和计费应查对应文档。[GPT-5 定价](https://developers.openai.com/api/docs/models/gpt-5)、[DeepSeek 定价](https://api-docs.deepseek.com/quick_start/pricing/)

**缓存能否复用，取决于前缀是否保持一致。**

前缀就是输入从开头起连续的一段内容。常规因果注意力模型中，后面的 token 会受到前文影响，因此：

* 从首个不同的 token 开始，其后 KV 通常需要重新计算。
* 此前没有变化的前缀仍可复用。
* 在末尾追加内容，可以保留已有前缀。

原文“改一个字节，后面的缓存就全废”是工程上的简写。更准确地说，要看**实际输入的 token、位置和影响缓存的配置**；实际命中还受缓存分块、有效期等条件限制。

**按组装顺序，完整上下文等于“相对稳定的前缀 + 持续追加的后缀”。**

以 Codex 这类终端编程 Agent 为例：

```text
完整上下文
= 相对稳定的前缀
  〔初始工具定义
   + Codex 模型基础指令
   + 开发者／运行规则
   + 用户／会话／项目规则
   + 初始环境与能力说明〕
+ 持续追加的后缀
  〔交互记录
   + 后续规则、环境、工具更新
   + 本轮新增输入〕
```

相对固定的工具定义应放进可复用前缀。Codex 源码有直接证据：Responses Lite 路径先放 `AdditionalTools`，再放基础指令，最后接已有消息；普通路径则通过独立的 `tools` 字段提供工具。[请求构造代码](https://github.com/openai/codex/blob/2fdf047c9631c9ed01a31b62efb7891718a931a8/codex-rs/core/src/client.rs#L971-L998)。所以 **JSON 字段顺序和模型最终读取的顺序要分开看**。

结合 KV 缓存，上下文还有另一条等式：

```text
完整上下文
= 命中 KV 缓存的连续前缀
+ 本次需要重新处理的后缀
```

由此有两个容易忽略的推论：

* **缓存边界不等于静态／动态边界。** 已经发生、保持原样的聊天和工具记录，也可以进入缓存前缀；判断标准是前缀是否连续一致，不是内容是否还会变化。
* **缓存省计算，不省窗口容量。** 例如输入有 20k token、命中缓存 18k，这次输入仍占 20k 窗口；省去的只是那 18k 前缀的重复处理，窗口还要容纳本次回答和推理。[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)

**缓存成为架构约束，是因为提示词、子 Agent 和历史消息的设计都会影响复用成本。**

原文以 Claude Code 为例，给出了三个相关设计。

**① 通用内容放前面，用户和会话内容放后面。** 原文介绍的方案用一个**缓存边界标记**，把系统提示词中的通用部分与用户、会话部分分开。这个标记告诉服务端：希望保存并复用到这里为止的完整前缀。

| 相对边界的位置 | 放什么                  | 目的                |
| ------- | -------------------- | ----------------- |
| 边界之前    | 多个用户、多个会话都相同的通用规则    | 让更多请求共享同一段缓存      |
| 边界之后    | 操作系统、当前模式、用户偏好、会话信息等 | 让这些差异尽量不影响前面的通用缓存 |

以 Anthropic 为例，可以通过 `cache_control` 标记可复用内容的末尾。**边界之后的内容也能通过后续缓存点继续缓存**，例如复用同一会话的历史消息。[缓存边界说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#explicit-cache-breakpoints)

原文所说的“全局缓存”需要限定范围：跨用户、跨会话复用仍受服务商的隔离规则约束，不能理解成所有客户共享。Anthropic 当前 Claude API 的缓存按工作区隔离。[缓存共享范围](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#cache-storage-and-sharing)

动态条件越早出现，共用前缀就越短。例如，把下面三个条件放进原本通用的前缀：

* macOS／Linux；
* 普通／调试模式；
* 中文／英文。

如果所有组合都可能出现，就有 \(2\times2\times2=8\) 种前缀版本。一般地，\(N\) 个独立二值条件最多形成 \(2^N\) 种组合，缓存复用也随之分散。

**② 子 Agent 若想复用父 Agent 的缓存，就要保持共享前缀一致。** 子 Agent 是主 Agent 派生出来处理子任务的执行者；旁路查询则是在主流程之外额外发起的模型请求。

当它们继承父 Agent 的上下文时，需要检查系统提示词、工具定义及顺序、历史消息前缀，以及模型和影响缓存的思考配置。共享部分保持不变，再在后面追加新任务。

原文的“字节级对齐”强调内容一致性，适用范围是**想复用的那段前缀**。子 Agent 可以使用独立提示词或不同模型，只是不能指望继续复用同一段缓存；也并非请求中的所有参数都必须相同。

**③ 工具输出一旦替换为摘要，就保存并复用同一份文本。** 大型工具结果可能被缩成摘要预览。摘要第一次进入历史消息时，就应持久化保存，后续请求和会话恢复都读取原来的字符串。

原因是：重新生成的摘要即使意思相同，措辞、空格或顺序也可能不同，从而改变历史前缀。

这只能避免不必要的缓存失配；会话重启后能否命中，还取决于服务端缓存是否仍然存在。

**研究延伸：KV Cache 可能成为可编辑、可组合的中间结果。**

Bojie Li 的论文 *Models Take Notes at Prefill: KV Cache Can Be Editable and Composable* 把 KV Cache 比作模型阅读时留下的“笔记”。这里的笔记是数值形式的中间结果。

论文的观察是：模型读取某个字段时，会把基于它形成的结论写入后续 token 的内部状态。因此，字段变了，**只修改字段自身的 KV，后面仍可能保留旧结论**。论文特定决策实验中，字段自身 KV 的直接贡献不到 1%，主要影响来自下游状态。[论文原文](https://arxiv.org/html/2606.17107v1)

由此产生两类操作：

| 操作                 | 核心思路                                 | 关键边界                             |
| ------------------ | ------------------------------------ | -------------------------------- |
| **编辑 Editing**     | 刷新字段自身的 KV，让后续推理重新读取新值；或在末尾追加明确的更正信息 | 廉价的字段编辑依赖后续计算是否重新读取字段，效果与模型、任务有关 |
| **组合 Composition** | 预先算好一段规则或工具说明的 KV，调整位置后接入新上下文        | 调整位置不能自动补齐所有跨段依赖，不能保证任意内容拼接都等价   |

编辑实验中的 **CoT（思考链）**，指模型逐步推理的过程。在部分实验中，它使模型重新读取更新后的字段，以约 1% 的计算量恢复正确决策。**原文“只要有 CoT 就能成功”的表述过于绝对**；论文明确指出效果仍依赖模型，缺少重新读取时，编辑可能被忽略。末尾追加更正是论文研究的另一条路径。[编辑实验与条件](https://arxiv.org/html/2606.17107v1#S4)

组合使用 **RoPE（旋转位置编码）**调整缓存中的位置信息，可以理解为把一页预先写好的笔记重新编号，再放进新文档。论文比较的操作从整段重算的 \(O(L^2)\) 降到缓存重定位、拼接的 \(O(L)\)，其中 \(L\) 是处理的 token 数。这个复杂度比较针对相应操作，不能理解成整个 Agent 的所有计算都变成线性。

原文涉及的研究数字需要分开看：

| 实验            | 报告结果                                            | 能说明什么                          |
| ------------- | ----------------------------------------------- | ------------------------------ |
| 特定 CoT 字段编辑实验 | 约 1% 计算量，恢复与重算一致的决策                             | 部分任务可以廉价更新状态                   |
| 12 个模型上的缓存组合  | logit 余弦相似度为 0.90–0.999                         | 下一 token 的打分较接近，不能据此保证所有输出逐字一致 |
| vLLM 在线服务实验   | 前缀缓存命中率约 98.5%；p90 首 token 延迟缩短至基线的约 1/53–1/398 | 在该负载下，保留前缀、末尾追加更正能显著降低等待时间     |

**logit** 是模型对候选 token 的原始打分；**p90 首 token 延迟**是 90% 请求开始输出所需时间的上界。vLLM 是运行模型推理服务的引擎。

核验补充：上表 vLLM 的高收益主要来自**末尾追加更正，使已有前缀继续命中缓存**，不能直接当成任意 KV 编辑或拼接都能获得的加速效果。论文也承认跨块关联信息可能降低组合质量，仍需更广泛的真实任务验证。[组合与服务实验](https://arxiv.org/html/2606.17107v1#S9)

这项研究指向一种可能：更新记忆、切换工具或注入状态时，保留更多已有计算结果。**它仍是研究方向；生产设计应继续以稳定前缀、追加历史、确定性恢复为默认原则。**

理解缓存后，上下文设计还需要解决以下问题：

| 方向            | 解决什么问题                                                      |
| ------------- | ----------------------------------------------------------- |
| 提示词、工具定义与按需加载 | 清楚说明行为规则和工具用法；防范外部内容夹带指令的提示注入；内容过多时，用 Agent Skills 按需加载相关说明 |
| Agent 状态栏     | 在上下文末尾追加任务进度、环境观察、工具调用计数等文字信息，帮助模型掌握当前状态                    |
| 上下文压缩         | 决定何时压缩、保留什么，以及改写历史时如何处理已有缓存                                 |
