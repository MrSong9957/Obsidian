**工具定义是给模型看的使用说明。** API 请求中的 `tools` 字段通常声明工具名称、用途和参数要求。模型据此选择工具、生成调用参数；执行系统运行工具，再把结果返回给模型。[^1]

其中，**schema（结构约束）**说明参数有哪些、是什么类型、哪些必须填写；文字描述进一步说明参数含义和使用条件。例如，仅规定 `timezone` 是字符串，仍不足以说明应该填 `"纽约"` 还是 `"America/New_York"`。

好的工具说明应覆盖以下内容。表中是原文列举的使用约定，并非所有 Agent 都必须采用的规则：

| 说明内容    | 具体示例                                       | 解决的问题          |
| ------- | ------------------------------------------ | -------------- |
| 使用边界    | 文件搜索使用专用 Grep 工具，不通过 Bash 调用 `grep` 或 `rg` | 避免选错操作入口       |
| 参数含义与示例 | `timezone` 使用 `"America/New_York"` 这样的时区名称 | 避免类型正确、含义或格式错误 |
| 工具之间的依赖 | 编辑文件前，先用 Read 读取内容                         | 避免缺少必要信息就修改    |
| 效率要求    | 没有依赖关系的调用可以批量提交                            | 减少不必要的串行等待     |

“批量调用”需要保留依赖关系：必须先读取才能确定修改内容时，读取和修改就不能同时执行。

**工具较多时，可以先提供搜索入口，再按需加载完整定义。** 一开始把全部工具说明交给模型，会占用上下文，也可能增加选择工具的难度。

这就是**渐进式披露**：先给完成当前判断所需的少量信息，需要细节时再展开。它与 Skills 按需读取详细说明采用相同思路。

工具按需加载通常经过以下过程：

1. **提供入口**：模型先看到工具搜索功能，以及必要的工具名称、工具分组或服务器说明。
2. **搜索工具**：模型根据当前任务请求查找相关工具。
3. **加载定义**：系统返回匹配工具的完整说明和参数 schema。
4. **调用工具**：模型根据新获得的定义填写参数，执行系统运行工具并返回结果。

当前实现中的关键名称如下：

| 实现                    | 主要机制                                                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| OpenAI Responses API  | 在 `tools` 中加入 `tool_search`，用 `defer_loading: true` 标记延迟加载的工具；通过 `tool_search_call` 和 `tool_search_output` 完成发现与加载。[官方文档](https://developers.openai.com/api/docs/guides/tools-tool-search) |
| Anthropic Tool Search | 搜索结果包含 `tool_reference` 引用块，API 将引用展开为完整工具定义供模型读取。[官方文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)                                                   |
| Claude Code           | 默认按需加载 MCP 工具，开始时提供工具名称和服务器说明；是否可用还受模型、代理和部署平台支持情况影响。MCP 是连接外部工具的统一协议。[官方文档](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)                                               |
| Codex CLI             | Apps/Connectors 的工具发现模板使用 `tool_search`，通过 BM25——一种按关键词相关度排序的方法——搜索并加载匹配工具。[源码](https://github.com/openai/codex/blob/main/codex-rs/core/templates/search_tool/tool_description.md)         |

**延迟加载指的是“模型何时看到定义”。** 完整定义仍可能需要随 API 请求提交。例如，Anthropic 要求在 `tools` 中提供对应定义，再由 API 根据历史中的引用进行展开；不能把“暂不进入模型上下文”理解成“完全不用提交工具定义”。

这类原生机制需要模型和服务端协议支持。文档列出的支持范围包括 OpenAI 的 GPT-5.4 及之后型号，以及 Anthropic 的 Claude 4.5 系列及后续支持型号。自托管模型能否使用类似机制、是否需要额外训练，应根据现有能力和框架适配效果判断。

**新定义追加到历史中，可以保留已有前缀的缓存。** KV Cache 保存模型处理前文时的中间计算结果。因果注意力意味着：处理一个位置时，只能利用当前位置及此前内容，后面新增的内容不会改变前面已经算出的结果。

因此，在原有上下文末尾加入新工具定义，可以保留此前的计算结果。下面展示的是模型看到的上下文顺序：

| 阶段     | 上下文顺序示意                        |
| ------ | ------------------------------ |
| 首次发现工具 | 固定前缀 → 已有历史 → 新工具定义            |
| 随后继续执行 | 固定前缀 → 已有历史 → 同一工具定义 → 后续调用与结果 |

**工具定义只在发现时追加，此后保留在历史中的原位置。** 随着新消息增加，它自然成为上下文中间的一部分，不需要每轮搬到最新末尾。Anthropic 的引用块也应保留在历史中，由 API 在后续请求中继续展开。[历史保留机制](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool#understanding-the-response)

这里依靠的是“已有内容保持不变、后续内容继续追加”。跨请求能否实际命中 Prompt Cache，还取决于缓存有效期、最低长度、配置和历史是否被改写；不能保证工具定义只计算一次后就永久命中。

**提示词是否有效，需要用对照实验判断。** 消融实验（Ablation Study）通过移除或削弱某个部分，观察结果变化，从而判断它的贡献。

Tau-Bench 是面向工具调用与用户交互的评测框架，包含航空和零售模拟业务。Agent 需要与模拟用户沟通、遵守业务规则并调用工具；任务完成情况主要通过最终数据库状态与目标状态比较来判断。[Tau-Bench 论文](https://arxiv.org/abs/2406.12045)

原文中的 `prompt-engineering` 实验以“结构化系统提示词＋完整工具描述＋专业中立语气”为基线，分别改变一个方面：

| 实验维度  | 改动                                  | 原文报告的结果                    |
| ----- | ----------------------------------- | -------------------------- |
| 语气与风格 | 换成夸张自信的 Trump 风格，或轻松、多表情的 Casual 风格 | 表达明显变化，任务完成率变化相对有限         |
| 信息组织  | 保留规则，去掉标题层次，将流程拆成零散规则               | 任务成功率下降超过 30%，更容易违反业务规则    |
| 工具描述  | 保留函数名和参数结构，删除描述性文字                  | 工具调用错误率增加 45%，容易误解参数或填写无效值 |

这些数字是**原文实验的报告值**，不能推广为所有模型和任务的固定变化幅度；原文也未明确百分比采用相对变化还是百分点口径。

设计这类实验时，应固定模型、任务集、初始数据、工具实现和评判标准，并重复运行。信息组织实验还应保留规则的完整含义：例如，“先验证身份，再退款”的先后要求不能被删除，否则同时改变了组织方式和业务规则。除完成率外，还可以记录错误调用、交互轮次和耗时；用户满意度需要另行定义评估方法。
