Skill 是供 Agent 按需读取的任务说明，也可以附带脚本、模板和参考资料。

**一份可用的 Skill，要让 Agent 知道：什么时候用、按什么顺序做、遇到什么情况需要确认、什么结果才算完成。** 只介绍背景知识，或保存一次成功对话，还不足以让它稳定复用经验。[^1]

### 1. 把经验写成具体要求

正文可以从四个方面组织。这是写作建议，不是必须照搬的文件格式。

| 部分    | 应该写清什么                       |
| ----- | ---------------------------- |
| 角色与读者 | 服务谁、处理什么任务、结果要达到什么标准。        |
| 核心原则  | 保留最重要的 3–5 条判断，关键处配正例和反例。    |
| 禁止清单  | 哪些错误经常发生、哪些动作越权，以及什么情况下允许例外。 |
| 参考资料  | 术语表、模板、范文和详细方法，需要时再读取。       |

另外，要把实际工作顺序写出来，例如：**检查输入、选择处理方法、执行、验证结果**，并在对应步骤说明何时停止或询问用户。

一条规则尽量包含：

**适用场景 + 具体动作 + 例外 + 检查方法。**

自拟示例：

> 给新手写教程时，首次出现的术语要用一句大白话解释；代码和 API 名称保持原样；写完检查是否还有未解释、又影响理解的术语。

* **反例**：“请优化缓存命中率。”
* **正例**：“缓存命中，就是复用之前算过的内容。让请求开头保持不变，更容易复用缓存。”

正反例让模型看到具体差别，比反复要求“自然一点”“专业一点”更容易落实。

### 2. 用真实任务改进 Skill

写作型 Skill 可以这样起步：

1. **选样本**：找 3–5 篇自己满意的原创文章。
2. **提炼初版**：让 Agent 归纳用词、句式、段落和语气，先写约 20 行。
3. **实际使用**：用它完成一项真实写作任务，再由作者逐句修改。
4. **比较差异**：查看哪些词被删掉、哪些句子被拆开、哪些地方补了事实。
5. **更新规则**：把反复出现的修改写回 Skill，保留适用范围和正反例，再换任务验证。

这些篇数和行数是起步建议，不是验收指标。**真正要看的是：换一项任务后，是否仍能产出符合要求的结果。**

只属于某篇文章的修改，不必升级成通用规则；否则 Skill 会越来越长，也越来越容易误用。

详细资料、模板和脚本可以独立存放，由 `SKILL.md` 说明何时使用。整个 Skill 也可以单独测试、记录版本和分享，方便持续积累经验。[Skill 文件组织规范](https://agentskills.io/specification#optional-directories)

### 3. 目录和正文放在哪里，由框架决定

先区分两种内容：

* **元数据目录**：名称、描述等简短信息，帮助模型选择 Skill。
* **完整正文**：选中 Skill 后才加载的操作说明。

共同原则是“先看摘要，再按需读正文”。OpenAI 的官方说明也采用这一机制。[OpenAI Skills 文档](https://learn.chatgpt.com/docs/build-skills)

至于把内容放进哪种消息，由 **Harness（负责组装上下文、调用工具的程序）** 决定。下面是原文记录的实现示例，具体方式可能随版本变化：

| 实现示例        | 元数据目录                      | 完整正文                                             |
| ----------- | -------------------------- | ------------------------------------------------ |
| Claude Code | 作为运行时上下文消息提供               | 在调用位置追加为 `user` 消息。                              |
| Codex       | 每轮构造上下文时，生成 `developer` 片段 | 显式选中的正文用 `<skill>` 包裹，加入 `user` 片段；其他情况也可通过工具读取。 |

原文中，Claude Code 自动激活 Skill 的过程是：

1. 模型发出 `Skill(skill: "pptx")` 调用。
2. 工具返回“正在启动 Skill”之类的提示。
3. 框架另外追加一条包含完整 Skill 正文的 `user` 消息。

用户直接输入 `/pptx` 时，客户端可以直接展开正文，省去这次激活工具的往返。

这里的 `user` 是消息角色，不表示文字一定由用户亲手输入。**Skill 属于工作指引，也不意味着它必须放在 `role: "system"` 中。**

选择接入方式时，应遵循目标模型和框架支持的接口；实际效果仍要用任务验证，不能仅凭“同一厂商生态”就判定最佳。

### 4. 只追加一次，不等于永久免费

原文中的 **emit-once**，指框架把某段内容加入会话历史一次。后续消息继续往末尾追加，无需反复插入同一份正文。

但需要分清三件事：

| 问题         | 实际情况                        |
| ---------- | --------------------------- |
| 是否重复插入？    | 可以只向历史中插入一次，后续沿用已有内容。       |
| 是否占上下文？    | 只要后续请求仍包含它，就继续占用上下文长度。      |
| 是否重复计算和收费？ | 缓存有效且前缀匹配时可以复用计算；缓存读取仍可能收费。 |

例如，加载 PPTX Skill 后，再读取 PDF、写出 HTML，只要旧内容保持不变，后续请求就有机会复用之前的计算。

这种**跨请求复用**属于 Prompt Cache（提示缓存）。它有有效期，也有匹配和计费规则。以 Claude API 为例，缓存写入和读取分别计费，因此不能把命中理解成永久免费。[缓存机制与计费](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

还有两个容易混淆的地方：

* **每轮重新生成目录，不一定破坏缓存**：关键看最终生成的内容、顺序及其前面的内容是否保持一致。
* **正文仍在历史里，不代表缓存仍有效**：缓存可能过期；修改前文、压缩或重组历史，也可能影响复用。

编写 Skill 时，仍应让目录简短、核心流程集中、详细资料按需读取。缓存减少重复计算，精简内容才能减少上下文占用。
