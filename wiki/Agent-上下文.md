## 一句话理解

**上下文就是 Agent 这一次做决定时，手里实际掌握的全部信息。**

LLM 再聪明，也只能根据当前上下文做判断。看不到的信息，就不能可靠利用。

## 上下文的 5 个部分

| 组成                 | 大白话                | 主要作用                 |
| ------------------ | ------------------ | -------------------- |
| System Prompt      | 岗位说明书              | 规定身份、权限、规则           |
| Tool Definitions   | 工具说明书              | 告诉模型有哪些工具、怎么调用       |
| User Messages      | 用户给的任务和资料          | 告诉 Agent 要做什么        |
| Assistant Messages | Agent 之前说过、想过、做过什么 | 保持前后连贯               |
| Tool Results       | 工具真正执行后的结果         | 告诉 Agent “刚才实际发生了什么” |

其中：

```text
静态前缀
├─ System Prompt
└─ Tool Definitions

动态历史
├─ User Messages
├─ Assistant Messages
└─ Tool Results
```

生产系统里，工具完整 schema 也可以**按需动态加载**，不一定全部长期塞进静态前缀。

## 为什么 Tool Results 特别重要

Agent 的基本工作循环其实是：

```text
看到上下文
   ↓
做决定
   ↓
调用工具
   ↓
得到 Tool Result
   ↓
根据真实结果继续决定
```

所以：

**reasoning 记录“为什么这么做”，Tool Result 记录“实际上发生了什么”。**

后者才是 Agent 闭环行动的关键。

例如：

```text
Agent：删除文件
↓
工具：删除失败，权限不足
↓
Agent：知道失败，换方案
```

如果没有工具结果：

```text
Agent：删除文件
↓
不知道成功还是失败
↓
继续按照自己的猜测行动
```

很容易进入盲目重试。

## 消融实验说明了什么

所谓 **Ablation Study（消融实验）**，就是：

> 一次拿掉一个组件，看系统坏在哪里。

实验结果大致是：

| 去掉什么         | 后果                  |
| ------------ | ------------------- |
| 工具定义         | 不知道怎么调用工具           |
| reasoning    | 决策可能不够连贯，但有时可以从结果重建 |
| 历史记录         | 容易重复操作、重复犯错         |
| Tool Results | 不知道工具到底执行得怎样，容易盲目循环 |

一个重要结论是：

> **不同上下文信息的重要程度并不一样，关键看丢失的信息能不能从其他地方重新推出来。**

例如 reasoning 丢失后，有时可以根据历史操作和 Tool Results 推测出来；但工具执行结果丢了，Agent 就失去了对真实环境的观测。

## 最重要的工程洞察

### 1. 上下文决定 Agent 的能力边界

```text
Agent 能力
≠ 单纯的 LLM 智力

实际表现
≈ LLM + 当前能看到的信息
```

模型不知道的，不代表现实中不存在，只代表**这次调用没有给它看**。

### 2. “回答了”不等于“任务完成了”

上下文残缺时，最危险的情况通常不是报错，而是：

> **模型照样生成一个非常像正确答案的答案。**

例如工具定义不存在，模型无法真正查询数据，它仍可能直接根据训练记忆回答。

因此：

```text
有答案
≠
有证据
≠
任务真的完成
```

### 3. Agent 设计的核心工作之一，就是管理上下文

工程上不能只问：

> 模型够不够聪明？

还要问：

> **做这个决定时，我们到底让模型看到了什么？**

很多所谓的“模型犯错”，实际上可能是**上下文设计出了问题**。
