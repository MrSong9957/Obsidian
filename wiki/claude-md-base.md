# 第一层：全局 CLAUDE.md

> 文件位置：`~/.claude/CLAUDE.md`（用户级，跨项目生效）

全局层放**行为准则 + 个人偏好**，不放项目特定配置。

```markdown
# AGENTS.md

---

## Karpathy 编码准则

减少常见编码错误，与项目指令配合使用。这些准则偏向谨慎；小任务可适当简化流程。

### 1. 编码前思考

**不擅自猜测，把疑问和取舍说清楚。**

- 修改前，先读相关实现和测试。
- 说清假设；有疑问先问清，再实现。
- 有多种理解时，列出差别，不擅自选。
- 有更简单的办法，主动提出；必要时指出当前方案的问题。

### 2. 极简主义

**用最少的代码解决问题，不为猜测中的需求做准备。**

- 不添加需求之外的功能、灵活性或配置项。
- 只用一次的代码，不必包装成通用接口或框架。
- 不处理不可能发生的错误。
- 能用 50 行解决，就别写 200 行。

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

### 3. 精准修改

**只改任务需要的内容，只清理自己造成的问题。**

- 先查看已有的未提交改动，不覆盖或回滚用户及其他 Agent 的工作。
- 不顺手修改无关代码、注释或格式，不重构没坏的代码。
- 遵循项目现有风格。
- 清理本次修改造成的无用导入、变量和函数。
- 发现原有且与任务无关的废弃代码，只提醒，不删除。

**检验标准：** 每一处修改，都能说清与当前任务的关系。

### 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

- 添加校验：先写无效输入的测试，再让它通过。
- 修复 bug：先写能复现问题的测试，再修到通过。
- 重构代码：确认修改前后测试都通过。

对于多步骤任务，说明一个简短的计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```
同一办法反复失败时，先补证据、查原因，再继续修改。
完成条件要具体，不能只写“让它工作”。

```

# 第二层：项目级 AGENTS.md

> 文件位置：`./AGENTS.md`（项目根目录，项目特有）

项目层放**开发规范 + 项目配置**。每个项目独立定制。

```markdown
# AGENTS.md

## 1. 项目原则

- 中文交流。
- 优先复用项目已有代码、工具、API、状态管理和成熟方案，只实现无法复用的最小部分。

---

## 2. 日志

按需记录到 `logs/*.md`，由 Agent 自主收集。

只保留关键设计依据、测试要点、失败原因和验证结果。最终报告引用同一份证据，不重复抄写。

---

## 3. 测试实现规范

**验证真实行为，不绑定内部写法。**

- 测试彼此独立，不依赖执行顺序，不污染真实环境。
- 涉及用户目录、配置、缓存或文件时，使用独立临时目录，覆盖相关路径环境变量，结束后清理；禁止读写真实用户环境。
- 不为覆盖率或形式完整增加低价值测试。
- 先确认相关测试的原有状态，再验证本次改动；涉及公共逻辑时扩大范围。
- 完成规定检查后，不重复运行没有新增信息的检查。

### 单元与集成测试

- 单元测试：检查输入输出、状态变化、边界和异常。
- 集成测试：检查模块之间的数据流、接口调用、状态同步和外部交互。
- 优先真实代码和组件。Mock（测试替身）只用于系统边界，不替代本次要验证的核心逻辑、状态变化或业务判断。
- Bug 修复必须在能稳定复现问题的最低层补回归测试。

### 端到端测试（E2E）

覆盖关键用户流程，不替代低层测试。主要检查用户最终看到的结果，日志只辅助定位和交叉验证。

| 场景 | 验证方式 |
|---|---|
| Web | 启动真实项目，用无头浏览器（如 Playwright）模拟操作，检查页面结果和相关数据。 |
| 普通 CLI | 启动真实进程，检查标准输出、错误输出、退出码和文件变化。 |
| 交互式 CLI / TUI | 使用伪终端模拟输入和按键，检查渲染后的屏幕、光标和状态。 |

Windows 交互测试使用 ConPTY，优先用 `node-pty` 启动真实进程、`@xterm/headless` 解析 ANSI 输出并检查屏幕状态。

涉及终端缩放、滚动历史等宿主终端行为时，增加目标终端验证；模拟屏幕通过只能作为部分证据。

不得仅因缺少 `tmux`、`script` 等工具就让用户手测。确实无法自动验证时，按第 9 节报告验证缺口。

---

## 4. 测试质量

按“准备输入 → 执行动作 → 检查结果”组织测试。

- 输入要有代表性、可复现，覆盖关键边界。
- 按需检查结果、状态和副作用，例如文件是否被改动。
- 证明目标路径确实执行，防止测试空跑。
- 关键新增或回归测试须证明能发现错误：保持断言不变，通过修复前后对照，或临时破坏被测行为，确认出错时失败、恢复正确行为后通过。
- 需求未变时，不得靠删除测试、放宽断言或绕过检查过关。

高风险模块按需做变异测试（故意改坏代码，检查测试能否发现）。与本任务有关却未被发现的错误必须调查；不改变实际行为的改动可说明后排除，不追求 100% 的分数。

---

## 5. 外部依赖

API、网络服务按需使用 VCR（录制并回放响应）或等价方案。

- 测试可离线运行，不依赖真实密钥。
- 响应固定、可复现。
- 录制的请求和响应必须去掉密钥、令牌等敏感信息。

---

## 6. 静态质量

按第 7 节已核实的命令执行类型检查（typecheck）和代码检查（lint）。

- 对应检查应通过，不引入未使用的代码、未处理的异步调用等明显问题。
- 区分原有失败与本次新增问题；检查失败或未执行，不能报告全部通过。

---

## 9. 审核报告与端到端场景

### `/goal` 自治执行合同

`/goal` 指最终交付目标。任务分级、技能选择、暂停条件和 Git 操作权限，以本次任务指令为准。

连续完成任务要求的 implementation、TDD、comprehensive-testing、Security Testing、code-review、修复和验证。阶段、Skill、Task/Ticket 或一次测试完成，都不构成返回理由。普通失败和可按第 8 节解决的工具缺失，自行处理后继续，不询问是否继续。

自治执行不扩大已有授权；合并、推送和发布按当前授权执行。

只在以下情况返回：
1. 满足全部完成条件，写好一份最终审核报告。
2. 命中本次任务规定的暂停条件，写好阻断报告，说明已完成内容、阻断原因和需要决定的事项。

### 文档角色

- `CONTEXT.md`、`docs/specs/*`：给 Agent 的执行约定，写清范围、行为和验收要求。
- `docs/reports/*-review.md`：给人看的审核报告，用大白话写结论并引用证据。
- 面向人的需求摘要先写【这是什么】【不做什么】【怎么算完成】。

### Test Spec 顺序

单独建立的测试规格按下列顺序写；范围外和禁止项写清楚，不用“本阶段暂不实现”代替。不要用未解释的 RED、GREEN、L1 等术语作章节标题。

```markdown
# <名称> Test Spec Gate

【这是什么】
【不做什么】
【怎么算完成】

## 1. 正常用法
成功时用户看到什么。

## 2. 必须挡住什么
每条异常或攻击先用一句人话解释，再列用例。

## 3. 禁止事项
不能触碰的边界。

## 4. 证据要求
各层测试需要提供什么证据。

## 5. 附录
完整约定、用例清单和冻结细节。
```

### 最低端到端场景

功能代码改动按下表验收，优先自动化：

| 等级 | 最少场景 |
|---|---|
| S / A | 至少 3 个，覆盖主流程和最易出错的边界。 |
| B | 1 个主流程，加关键异常。 |
| C | 1 个最小闭环。 |

纯文档、注释或格式修改可用对应检查替代 E2E，在报告中说明。

### 最终审核报告

路径：`docs/reports/<日期>-<任务短名>-review.md`。

正文尽量控制在一屏，详细输出引用日志或证据文件。

```markdown
# 审核报告：<任务名>

等级：S / A / B / C
状态：完成 / 卡住需你实测 / 需你决策

## 1. 做完了什么
用几句话说明结果。

## 2. 改了哪里
- 路径：为什么改。

## 3. 完成条件与证据
| 完成条件 | 命令、结果或证据路径 |
|---|---|
| … | … |

## 4. 端到端场景
| 场景与输入 | 期望 | 实际 | 结果 |
|---|---|---|---|
| … | … | … | 通过 / 失败 / 未验证 |

无法自动验证：写明原因，并提供手测步骤，每步包含输入和通过标准。
不适用 E2E：写明原因与替代检查结果。

## 5. 需要关注
未完成项、风险和需要决定的事项；没有则写“无”。
```

返回大脑时，只给报告路径和一句结论。

是否完成以实际测试输出、命令结果和文件状态为准。必做验证尚未完成时，不得标为完成。

```
