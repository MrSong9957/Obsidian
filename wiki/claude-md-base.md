# 第一层：全局 CLAUDE.md

> 文件位置：`~/.claude/CLAUDE.md`（用户级，跨项目生效）

全局层放**行为准则 + 个人偏好**，不放项目特定配置。

```markdown
# CLAUDE.md

---

## andrej-karpathy-skills

行为准则，减少常见 LLM 编码错误。与项目特定指令合并使用。

**权衡：** 这些准则偏向谨慎而非速度。对于琐碎任务，请自行判断。

### 1. 思考先行

**不要假设。不要隐藏困惑。呈现权衡。**

实现前：
- 明确陈述你的假设。如果不确定，询问。
- 如果存在多种解释，展示它们——不要默默选择。
- 如果存在更简单的方法，说出来。必要时提出异议。
- 如果某事不清楚，停下来。指出困惑之处。询问。

### 2. 极简主义

**解决问题的最少代码。不做推测性实现。**

- 不添加超出要求的功能。
- 不为一次性代码做抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不处理不可能场景的错误。
- 如果你写了 200 行而 50 行就能解决，重写它。

问自己："资深工程师会说这过于复杂吗？"如果是，简化。

### 3. 精准修改

**只触碰必须修改的。只清理自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有风格，即使你自己会做得不同。
- 如果发现无关的死代码，提及它——不要删除它。

当你的更改产生孤儿代码时：
- 删除你的更改导致未使用的导入/变量/函数。
- 除非被要求，否则不要删除预先存在的死代码。

检验标准：每一行更改都应直接追溯到用户的请求。

### 4. 目标驱动

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写重现它的测试，然后让它通过"
- "重构 X" → "确保测试在重构前后都通过"

对于多步骤任务，简要说明计划：
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]

强有力的成功标准让你能独立循环。弱标准（"让它工作"）需要不断澄清。

---

```

# 3. 测试实现规范

核心目标：
> 验证真实行为，不验证实现细节。

测试层级：
```text
单元测试 → 集成测试 → E2E
```

原则：
* 低层测试保护核心逻辑，高层测试保护关键用户流程。
* 测试必须独立，不依赖执行顺序，不污染真实环境。
* 禁止为覆盖率、实现细节或形式完整增加低价值测试。
* 涉及用户目录、配置、缓存或文件系统状态时，使用独立临时目录并覆盖对应环境变量，结束后清理，禁止读写真实用户环境。

## Unit / Integration

单元测试用于单函数、单模块和核心业务逻辑，重点验证：
* 输入输出；
* 状态变化；
* 边界与异常。

优先真实代码。Mock 仅用于系统边界，不得 Mock 本次需要验证的核心逻辑、状态转换或业务判断。

集成测试用于模块协作，重点验证：
* 数据流；
* API 调用；
* 状态同步；
* 外部交互。

优先真实组件，避免单模块通过但组合失败。

Bug 修复必须增加能够稳定复现问题的最低层回归测试。

## E2E

E2E 只覆盖关键用户流程，不替代低层测试。

主要断言用户最终可见结果；日志只用于交叉验证和定位。

### Web

使用真实项目和无头浏览器（如 Playwright）模拟用户输入、点击等行为。

验证链路：
```text
操作 → DOM → 请求 → 数据 → 页面
```

最终以 DOM / 用户可见结果为主。

### CLI / TUI

使用真实伪终端启动完整 CLI/TUI，模拟命令输入、组合键等行为。

验证链路：
```text
TTY → 输入 → ANSI → 屏幕 / 光标 / 状态
```

要求：
* 自动校验 ANSI 渲染后的最终用户可见结果；
* 不得因缺少 `tmux`、`script` 等工具直接退化为人工验证；
* Windows 使用 ConPTY；
* 优先使用 `node-pty` 启动真实进程；
* 优先使用 `@xterm/headless` 消费 ANSI、维护终端缓冲区，并断言最终屏幕、光标和状态；
* 可按需使用 `@commander-cli/test-utils`、`expect-cli` 等辅助工具。

Windows CLI/TUI 的优先方案：
```text
node-pty / ConPTY
→ 真实进程
→ ANSI 输出
→ @xterm/headless
→ 最终屏幕 / 光标 / 状态断言
```

## 4. 测试质量

测试采用 AAA：
```text
Arrange → Act → Assert
```

关键测试应按需验证：
```text
结果 + 状态 + 副作用
```

要求：
* 使用真实、动态输入；
* 覆盖关键边界；
* 必须证明目标路径确实执行，防止测试空跑；
* 关键新增 / 回归测试应证明失败敏感性：临时破坏被测行为或关键断言时应 RED，恢复后应 GREEN。

高风险模块按需使用 Mutation Testing：
* 与当前功能契约直接相关的 surviving mutation 必须调查；
* 不以全局 100% mutation score 为目标；
* 等价 mutation 可说明原因后排除。

---

## 5. 外部依赖

API / 网络服务按需使用 VCR 或等价方案。

要求：
* 测试可离线运行；
* 不依赖真实 Key；
* 响应可固定和复现。

---

## 6. 静态质量

涉及对应技术栈时必须保证：
* typecheck 通过；
* lint 通过；
* 无新增 unused；
* 无 floating promise；
* 无明显代码异味。

# 8. 工具可用性

## open-code-review

已安装且可调用时直接使用，不重复安装。

缺失时：
```bash
npm install -g @alibaba-group/open-code-review
npx skills add alibaba/open-code-review --skill open-code-review
```

验证：
```bash
ocr version
```

首次配置或异常时：
```bash
ocr llm test
```

---

## Superpowers

官方仓库：`https://github.com/obra/superpowers`

目标 Skill 不可用时：
1. 先确认当前 Agent 是否已经安装且可实际调用。
2. 缺失时优先通过当前 Agent 原生插件 / Skill 机制，在 `user` / `global` 作用域安装官方 Superpowers。
3. 原生机制不可用时，再使用用户级共享 Skill 目录；最后才使用当前 Agent 自身的用户级 Skill 目录。禁止安装到项目级目录，禁止猜测路径。
4. 安装后必须验证目标 Skill 可以被发现并实际调用；当前 Agent 确实不支持时明确报告，不得伪装执行或静默跳过。
