**要让 Agent 换一场对话后仍能利用已有信息，就要把有用的信息保存下来，并在需要时取回。** 只放在当前对话中的内容，不能保证下次仍然可用。[^1]

**1. 用户记忆和知识库，分别记什么？**

Agent 是能回答问题、调用工具办事的 AI 助手。它会用到三类信息：

| 类别 | 解决什么问题 | 例子 |
|---|---|---|
| 当前会话的上下文 | 这次正在做什么？ | 用户刚提出的订票要求、工具返回的航班 |
| 用户记忆 | 这个用户有什么偏好和需求？ | 喜欢靠窗、吃素、常用航空会员号 |
| 知识库 | 完成任务需要哪些可共享的知识？ | 行业法规、公司流程、技术文档 |

用户记忆围绕一个人，知识库围绕一类业务或一个领域。两者都需要长期保存信息、按需查找，也都会遇到信息冲突、内容过期和查找不准的问题。

**2. 一段对话，怎样变成记忆？**

沿用原文的虚构订票情境：用户想下周五去东京，说明自己喜欢靠窗、吃素，并提供 United MileagePlus 会员号 `12345678`。工具返回了 3 个航班选项。

对话结束后，原文方案会**额外调用一次大语言模型（LLM），专门整理记忆**：读取对话，挑出以后可能有用的事实，压缩并审查，再按字段保存。这是原文采用的流程，并非所有记忆系统都必须固定调用一次模型。

| 对话中的信息 | 提取结果 | 为什么这样处理 |
|---|---|---|
| “我喜欢靠窗” | 座位偏好：靠窗 | 下次订票仍可能有用 |
| “我吃素，需要特殊餐食” | 饮食限制：素食；乘机需要素食餐 | 会影响之后的餐食安排 |
| United MileagePlus 号码 `12345678` | 会员计划与对应号码 | 以后使用该会员身份时可以查找 |
| 下周五去东京 | 近期出行计划 | 近期有用，但不能当成长期偏好 |
| 搜索返回 3 个选项 | 不提取为长期记忆 | 只是这次搜索的临时结果 |

之后再次订票时，系统还要**找出相关记忆，放进本次交给模型的上下文**。这样，即使用户没重说“我吃素”，模型也能根据取回的信息考虑素食餐。

**3. 提取记忆的三条规则**

- **选择性：只留以后有用的。** 保存饮食限制，丢掉“搜索返回 3 个选项”这类临时细节。
- **抽象化：提炼能复用的意思。** 把“我喜欢靠窗”整理成“座位偏好：靠窗”，下次换了目的地也能用。
- **结构化：按明确字段保存。** 把会员计划和会员号对应保存，方便以后准确查找，而不是埋在整段聊天里。

**抽象化不能凭空猜。** 原文明确说“我喜欢靠窗”，才有依据记为偏好；如果用户只是这次选了靠窗座位，还不足以认定他长期喜欢靠窗。东京行程属于近期计划，也不能一直当成当前有效的信息。

**4. 信息多了，怎样取用？**

用户记忆和知识库可以共用检索、压缩等技术。例如，向量检索按意思寻找相近内容，关键词检索按词匹配，混合检索结合两者。

**RAG（检索增强生成）就是先查相关资料，再把查到的内容交给模型，帮助它回答。** 这套方法既能查知识库，也能查用户记忆。

本章预告的“双层记忆架构”把信息分成两层：

- **概览常驻：** 把简短的结构化记忆卡片（Advanced JSON Cards）放进上下文，让模型先掌握关键信息。
- **细节按需查：** 根据当前任务，再找出相关的详细记忆。

这样既能保留必要概览，也能减少每次塞进上下文的细节。原文在这里仅介绍方向，尚未展开具体实现。
